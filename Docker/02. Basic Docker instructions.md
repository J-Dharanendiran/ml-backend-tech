# 🐳 The Recipe Card for Your Container: The 80/20 of Writing a Dockerfile

> *"Docker has enough vocabulary already; no need to make it worse."*
> You don't need every instruction. You need the few that carry almost everything.

---

## 🍳 The Question That Starts Everything

You've just finished a FastAPI project. It runs on your laptop. Now you want to put it inside a container, and you open the Dockerfile reference page.

It lists **eighteen instructions**: `ADD`, `ARG`, `CMD`, `COPY`, `ENTRYPOINT`, `ENV`, `EXPOSE`, `FROM`, `HEALTHCHECK`, `LABEL`, `MAINTAINER`, `ONBUILD`, `RUN`, `SHELL`, `STOPSIGNAL`, `USER`, `VOLUME`, `WORKDIR`.

And a thought arrives:

> **"Do I really have to memorize every Docker instruction known to humanity before I can containerize my ML project?"**

No. And the reason is the **80/20 rule**: roughly **20% of the concepts cover 80% of real-world use**. You are learning FastAPI and building ML applications, so the goal is not a Docker encyclopedia. The goal is a Dockerfile you can write from memory, read without fear, and fix when it breaks. 🎯

A Dockerfile is, at heart, a **recipe card**. 📜 You write the steps once, in order, and Docker follows them every time to produce the same dish: an **image**.

So which steps go on the card?

---

## 🗂️ The Eight Things Worth Knowing First

Here is your priority list. Six are Dockerfile instructions or files you will write on day one. Two more make the container actually usable from the outside.

| Priority | Concept | What you need to know |
| -------- | ------- | --------------------- |
| 🔥 1 | `FROM` | Choose the base image |
| 🔥 2 | `WORKDIR` | Set the working directory inside the container |
| 🔥 3 | `COPY` | Copy your application files into the image |
| 🔥 4 | `RUN` | Execute commands while building the image |
| 🔥 5 | `CMD` | Specify the default command when the container starts |
| 🔥 6 | `.dockerignore` | Prevent unnecessary files from entering the build context |
| ⭐ 7 | Port mapping | Make your application's port accessible from your machine |
| ⭐ 8 | Environment variables | Configure your application without hardcoding settings |

**Master these first.** Add `EXPOSE`, dependency caching, and non-root users as you become comfortable.

Now let's walk the recipe in the order Docker reads it. Five instructions do the heavy lifting, and each one answers a single plain question.

---

## 🏠 ① `FROM`: Where Do You Start?

Every Docker image starts from **a base image**. You never build from absolute nothing; you pick a foundation.

```dockerfile
FROM python:3.12-slim
```

This tells Docker: *start with an image that already contains Python 3.12 on a slim Linux environment.*

Think of it as **choosing the foundation for your house**. 🏠 You don't pour concrete from raw minerals. You start from a plot that's already level.

**Remember:**

* `python:3.12-slim` is a relatively lightweight Python base image.
* Your application gets its runtime environment from this image.
* Choose a Python version **compatible with your project's dependencies**.

---

## 📁 ② `WORKDIR`: Where Will Your Application Live?

Once you have a foundation, you need a room to work in.

```dockerfile
WORKDIR /app
```

This sets `/app` as the working directory inside the image.

Subsequent relative paths in instructions such as `COPY`, `RUN`, and `CMD` are generally interpreted relative to this directory. For example:

```dockerfile
WORKDIR /app
COPY requirements.txt .
```

That little `.` means "here", and "here" is now `/app`. So the requirements file lands at `/app/requirements.txt`.

**Remember:** you don't need to write `cd /app` before every command. `WORKDIR` already moved you in. 🚪

---

## 📦 ③ `COPY`: How Do Your Files Enter the Image?

Your project lives on your laptop. The image is a sealed world. Something has to carry files across the border.

```dockerfile
COPY requirements.txt .
COPY . .
```

* The **first** line copies your dependency list into `/app`.
* The **second** copies the remaining files from the build context into `/app`, subject to exclusions in `.dockerignore`.

And now a worry surfaces, the kind that matters in real projects:

> **"If `COPY . .` grabs everything, what exactly is 'everything'? Is copying my whole project actually fine?"**

Here is the important part: **copying your entire project blindly is usually a bad idea.** 🚫

Look at what might be sitting in your project folder:

* `.venv/`
* `.git/`
* `__pycache__/`
* Large datasets
* Model checkpoints
* API keys or `.env` files

You usually don't want any of these inside the image. A virtual environment from your laptop doesn't belong in a Linux container. A `.env` file with secrets definitely shouldn't be baked into something you might share.

The fix is a small file called **`.dockerignore`**, and it's the sixth item on your priority list. We'll return to it when we assemble the project.

---

## 🔨 ④ `RUN`: What Happens While Building?

The files are in place. Now the room needs furniture: your Python libraries.

```dockerfile
RUN pip install --no-cache-dir -r requirements.txt
```

This installs the packages listed in `requirements.txt` **while Docker builds the image**.

For an ML API, your dependencies might look like this:

```text
fastapi
uvicorn[standard]
scikit-learn
pandas
numpy
```

Docker executes the installation command and **saves its filesystem changes in an image layer**. Each `RUN` leaves a layer behind, like a page added to a notebook that you can't un-write.

Now comes the distinction that trips up almost every beginner:

> **"What's the actual difference between `RUN` and `CMD`? They both run commands!"**

**Key distinction:**

| Instruction | When it runs | Purpose |
| ----------- | ------------ | ------- |
| `RUN` | During **image building** | Prepare the image (install packages, etc.) |
| `CMD` | When a **container starts** | Say what the container does by default |

Confusing these two is a classic beginner mistake. 😅 Docker has enough vocabulary already; no need to make it worse.

A mental picture helps: **`RUN` is cooking in the kitchen, `CMD` is what the waiter does when the customer sits down.** 🍽️ The cooking happens once, before any customer arrives. Serving happens every time someone shows up.

---

## 🚦 ⑤ `CMD`: What Happens When the Container Starts?

The dish is cooked and plated. When a container starts from this image, what should it actually *do*?

Suppose your FastAPI application is in `main.py` and your FastAPI instance is named `app`. You might use:

```dockerfile
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

That line is dense, so let's unpack it:

| Component | Meaning |
| --------- | ------- |
| `uvicorn` | Starts the ASGI server |
| `main:app` | Looks for the `app` object in `main.py` |
| `--host 0.0.0.0` | Listens on all network interfaces inside the container |
| `--port 8000` | Listens on port 8000 inside the container |

Read `main:app` as *"file `main`, object `app`"*. The part before the colon is the module, the part after is the FastAPI instance inside it.

And then the question every FastAPI beginner eventually asks:

> **"Why `0.0.0.0` instead of `127.0.0.1`? On my laptop, `127.0.0.1` always worked."**

Here's the explanation. Inside a container, binding to `127.0.0.1` restricts the server to **the container's own loopback interface**, meaning only processes inside that same container can reach it. Binding to `0.0.0.0` allows connections **through the container's network interface**, including connections enabled by port mapping.

Picture a shop that only talks to its own staff (`127.0.0.1`) versus a shop with a front door open to the street (`0.0.0.0`). 🏪 If you want customers (your browser) to reach the API, the front door has to be open.

For a web application, this one detail matters. It's the reason a "perfectly working" container sometimes refuses every connection.

## 🚀 Your First Practical Dockerfile

You now have all five instructions. Time to cook with them. 🔥

Let's containerize a simple FastAPI application.

### The project structure

```text
ml-api/
├── main.py
├── requirements.txt
├── Dockerfile
└── .dockerignore
```

Four files. That's the entire kitchen.

### `main.py`: the dish

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def home():
    return {"message": "My ML API is running!"}
```

### `requirements.txt`: the shopping list

```text
fastapi
uvicorn[standard]
```

### `Dockerfile`: the recipe card

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**That's it.** You've written a functional Dockerfile for a basic FastAPI application. ✅

Read it top to bottom and notice how each line answers one of our questions:

1. 🏠 `FROM`: *where do I start?* → a slim Python image
2. 📁 `WORKDIR`: *where do I live?* → `/app`
3. 📦 `COPY requirements.txt .`: *what do I need first?* → the shopping list
4. 🔨 `RUN pip install ...`: *what do I prepare?* → the libraries
5. 📦 `COPY . .`: *what else comes in?* → the rest of the project
6. 📢 `EXPOSE 8000`: *what port does the app use?* → 8000
7. 🚦 `CMD`: *what happens at startup?* → launch Uvicorn

You may have noticed that `requirements.txt` is copied **before** the rest of the project, rather than copying everything in one go. That ordering is deliberate. The lesson holds that part back for later, listing *dependency caching* among the things to add as you get comfortable. For now, keep the order exactly as written.

## 🙈 The `.dockerignore` File

The lesson promised: *"We'll fix that with `.dockerignore` shortly."* And the fourth file in your project tree is exactly that.

A `.dockerignore` file excludes files and directories from the **build context**, which is the set of files Docker can see when it builds your image. Everything on the "worry list" from the `COPY` section is a candidate for it.

> 📝 **Supplement (assembled from the lesson's own list, not part of the source):** a minimal `.dockerignore` for the project above could simply name the items the lesson warned about.

```text
.venv/
.git/
__pycache__/
.env
```

For an ML project you would extend it with your own large datasets and model checkpoint folders, if you don't want them inside the image.

## 🔬 Sanity Check: Does This Actually Run?

A recipe you've never tasted is a rumor. So the app and command from this chapter were run in a clean Python 3.12.3 virtual environment (outside Docker; see the limits below):

* `main.py` and `requirements.txt` exactly as shown above
* Installed versions at the time of the check: **fastapi 0.143.0**, **uvicorn 0.54.0**
* Started with `uvicorn main:app --host 0.0.0.0 --port 8000`
* Uvicorn logged: `Uvicorn running on http://0.0.0.0:8000`
* `GET /` returned: `{"message":"My ML API is running!"}`
* `pip install --help` lists `--no-cache-dir` ("Disable the cache.")

So the Python side of the recipe is sound. The Docker-specific side (building the image, running the container) was **not** tested here, because Docker isn't available in that environment.

## 🌉 ML Bridge: From a Hello-World API to a Model Behind a Door

That `home()` function returns a greeting. Swap in a model and the same skeleton serves predictions:

* `requirements.txt` grows: `scikit-learn`, `pandas`, `numpy` (the lesson's own example dependencies).
* `COPY . .` becomes the moment your model-serving code enters the image, and `.dockerignore` becomes your gatekeeper for **large datasets and model checkpoints** that shouldn't ride along by accident.
* `CMD` still launches Uvicorn the same way, because the server doesn't care whether the route inside it returns a greeting or a prediction.
* `FROM python:3.12-slim` is where "choose a Python version compatible with your project's dependencies" bites hardest: ML libraries are picky about versions.

Your Stroke Prediction system is exactly the kind of project this recipe is built for: a trained model, a FastAPI layer in front of it, and a container that makes it run the same way everywhere. 🧠➡️🐳

## 🌀 Deepest Realization

A Dockerfile is not a list of commands to memorize. It is a **sequence of answers** to five questions that any program needs answered before it can live somewhere new:

*Where do I start? Where do I live? What do I bring? What do I prepare? What do I do when I wake up?*

`FROM`, `WORKDIR`, `COPY`, `RUN`, `CMD`. Once you see the five questions, the syntax is just spelling.

---

## ✅ Final Takeaway

> **"Five instructions answer five questions, `.dockerignore` keeps the junk out, and `0.0.0.0` opens the front door. Learn those, and you can containerize your first ML API without memorizing the rest of Docker."**
