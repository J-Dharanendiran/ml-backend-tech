# The Small Machines Inside MySQL

Every table you build is, in the end, just a pile of rows sitting quietly on disk. Rows don't summarize themselves. Rows don't count themselves, average themselves, or reformat themselves into something readable. Something has to *do* that work — and that something is a **function**. ⚙️

Picture it as the simplest machine imaginable:

```text
Input → Function → Output
```

Feed it a table, and it hands back an answer:

```sql
SELECT COUNT(*) FROM users;
```

```text
users table
    ↓
COUNT(*)
    ↓
26
```

That's the whole idea in miniature. Functions exist for **computation**, for **analyzing data**, for **transforming data**, for **summarizing data**, and for building calculated fields that never existed in the table to begin with.

## Why Bother With a Machine at All?

Imagine a `users` table:

| id | name  | gender | date_of_birth | salary |
|---:|-------|--------|----------------|-------:|
| 1  | Rahul | Male   | 2001-05-10     | 50000  |
| 2  | Priya | Female | 2000-08-15     | 70000  |
| 3  | Arun  | Male   | 1999-03-20     | 60000  |

With three rows, you could total the salaries by hand. Now imagine a million rows.

> "Let me count these one by one," says the human, already regretting it.

> "Please stop making this unnecessarily difficult," replies MySQL, and hands you a function instead.

## The Counting Guard: `COUNT()`

`COUNT()` counts rows or values.

```sql
SELECT COUNT(*)
FROM users;
```

If the table holds 26 people:

```text
COUNT(*)
--------
26
```

That `*` simply means *"count the rows."* It matters because eyeballing a table can lie to you — rows get deleted, gaps appear, and a glance at the last visible ID tells you nothing reliable. `COUNT(*)` always reports the *current* truth.

Pair it with a condition, and it gets sharper:

```sql
SELECT COUNT(*) FROM users WHERE gender = 'Male';
SELECT COUNT(*) FROM users WHERE gender = 'Female';
```

```text
                    users
                      ↓
                  WHERE gender
                 ↙           ↘
              Male          Female
                ↓              ↓
             COUNT           COUNT
                ↓              ↓
               13             13
```

**`WHERE` decides which rows get considered. `COUNT()` just counts whoever's left standing.**

## The Extremes: `MIN()` and `MAX()`

Two functions, opposite instincts.

```sql
SELECT MIN(salary) FROM users;
```

Given `50000, 70000, 60000, 45000, 90000` as salaries, `MIN()` answers *"what's the lowest?"* — `45000`. Flip the function, and `MAX()` answers the mirror question — `90000`.

Run them side by side:

```sql
SELECT MIN(salary), MAX(salary) FROM users;
```

But raw output from a function often arrives with an ugly, auto-generated column name. That's where `AS` steps in — a small but important idea: it doesn't rename anything in the *table*, only in the *result you're looking at right now*.

```sql
SELECT
    MIN(salary) AS min_salary,
    MAX(salary) AS max_salary
FROM users;
```

| min_salary | max_salary |
|-----------:|-----------:|
| 45000      | 90000      |

## Adding It All Up: `SUM()` and `AVG()`

`SUM()` is exactly what it sounds like:

```sql
SELECT SUM(salary) AS total_salary FROM users;
```

Add `50000 + 70000 + 60000 + 45000`, and you land on `225000`. `AVG()` takes that same idea one step further:

$$
Average = \frac{\text{Sum of all values}}{\text{Number of values}}
$$

$$
\frac{50000+70000+60000}{3} = 60000
$$

```sql
SELECT AVG(salary) AS average_salary FROM users;
```

## The Question That Changes Everything: `GROUP BY`

*What if you don't want one average — you want the average salary for men and the average salary for women, separately, in a single query?*

This is where SQL stops feeling like arithmetic and starts feeling like analysis.

```sql
SELECT
    gender,
    AVG(salary) AS average_salary
FROM users
GROUP BY gender;
```

| gender | average_salary |
|--------|----------------:|
| Male   | 65000           |
| Female | 62000           |

`GROUP BY gender` splits the table into two silent piles before the function ever runs:

```text
                 USERS
                   │
             GROUP BY gender
              /           \
           Male          Female
            │               │
        AVG(salary)     AVG(salary)
            │               │
          65000           62000
```

This is arguably **the most important concept in SQL** — a function no longer runs once over the whole table; it runs once *per group*.

*Could you `GROUP BY id` instead?* You could, but it wouldn't mean much — if every `id` is unique, each row becomes its own lonely group of one, and you've gained nothing over just looking at the raw rows. `GROUP BY` only earns its keep when the column actually repeats across rows — like `gender` does, and `id` never will.

The same pattern works with `SUM()`:

```sql
SELECT
    gender,
    SUM(salary) AS total_salary
FROM users
GROUP BY gender;
```

```text
Male users        Female users
   ↓                   ↓
SUM(salary)        SUM(salary)
   ↓                   ↓
Total male salary  Total female salary
```

This is the moment SQL quietly becomes a data-analysis tool rather than a storage box.

## Functions That Speak in Words, Not Numbers

Not every function does arithmetic. Some reshape **text**.

`LENGTH()` measures a string:

```sql
SELECT name, LENGTH(name) AS name_length FROM users;
```

`LENGTH('Dharan')` comes back as `6`. `LOWER()` flattens case:

```sql
SELECT name, LOWER(name) AS lower_name FROM users;
```

```text
Dharan
   ↓
LOWER()
   ↓
dharan
```

And `CONCAT()` glues strings together:

```sql
SELECT CONCAT(name, '123') AS username FROM users;
```

```text
Dharan + 123
      ↓
Dharan123
```

*Can you nest one function inside another?* Yes — and this is where things get genuinely powerful:

```sql
SELECT CONCAT(LOWER(name), '567') AS username FROM users;
```

```text
name
 ↓
LOWER()
 ↓
CONCAT()
 ↓
username
```

`Dharan` becomes `dharan`, and `dharan` becomes `dharan567` — one function feeding directly into the next. **Functions compose.** That single fact is worth more than memorizing all their names individually.

## Functions That Read a Calendar

`NOW()` returns the current date and time:

```sql
SELECT NOW() AS current_time;
```

`CURDATE()` gives just the date, dropping the clock entirely:

```text
NOW()      → 2026-09-18 17:27:00
CURDATE()  → 2026-09-18
```

`YEAR()`, `MONTH()`, and `DAY()` each pull one piece out of a stored date:

```sql
SELECT YEAR(date_of_birth), MONTH(date_of_birth), DAY(date_of_birth)
FROM users;
```

For `2002-08-15`, that unpacks to `2002`, `8`, and `15` — with months always sitting somewhere between `1` (January) and `12` (December).

And then there's the function that actually *compares* two dates: `DATEDIFF()`, which returns the gap between them in days.

```sql
SELECT DATEDIFF('2026-09-18', '2026-09-10');
```

```text
September 10
      ↓
      8 days
      ↓
September 18
```

*What if you wanted to know exactly how many days someone has been alive — not their age in years, but the literal day count?* Combine `CURDATE()` with `DATEDIFF()`:

```sql
SELECT
    name,
    DATEDIFF(CURDATE(), date_of_birth) AS age_days
FROM users;
```

```text
CURRENT DATE
     ↓
CURDATE()
     ↓
DATEDIFF()
     ↑
DATE OF BIRTH
```

## Functions That Do Arithmetic With Attitude

`ROUND()`, `FLOOR()`, and `CEIL()` all round numbers — but each with a different personality.

```sql
SELECT ROUND(10.6);   -- 11
SELECT ROUND(10.4);   -- 10
SELECT ROUND(10.567, 2);  -- 10.57
```

`ROUND()` rounds the *sensible* way — nearest neighbor. `FLOOR()` has no such nuance; it always drops down:

```sql
SELECT FLOOR(10.9);  -- 10
SELECT FLOOR(10.1);  -- 10
```

`CEIL()` is its mirror opposite — always pushing up:

```sql
SELECT CEIL(10.1);  -- 11
SELECT CEIL(10.9);  -- 11
```

Line the three up against the same number:

```text
ROUND(10.6) → 11
FLOOR(10.6) → 10
CEIL(10.6)  → 11
```

Then there's `MOD()`, which isn't about rounding at all — it's about what's *left over* after division:

$$
10 \div 3 = 3 \text{ remainder } 1 \quad\Rightarrow\quad MOD(10,3) = 1
$$

$$
8 \div 2 = 4 \text{ remainder } 0 \quad\Rightarrow\quad MOD(8,2) = 0
$$

A practical trick built on this: `MOD(id, 2)` tells you instantly whether an ID is even or odd.

## The Function That Makes a Decision

Everything so far has *calculated*. `IF()` is the first one that *decides*.

```sql
SELECT
    name,
    gender,
    IF(gender = 'Female', 'Yes', 'No') AS is_female
FROM users;
```

For Arun:

```text
gender = Female?
      ↓
     NO
      ↓
    "No"
```

For Priya:

```text
gender = Female?
      ↓
     YES
      ↓
    "Yes"
```

| name  | gender | is_female |
|-------|--------|-----------|
| Arun  | Male   | No        |
| Priya | Female | Yes       |

## The Quiet Rule Underneath All of This

Here's something worth connecting back to constraints, since that idea lives in the same neighborhood: when you write

```sql
SELECT LOWER(name) AS lower_name FROM users;
```

you are **not** adding a permanent column to the table. You're creating a calculated column that exists only in the *result* of that one query.

```text
Actual table                    Query result
┌────┬────────┐                 ┌────┬────────┬────────────┐
│ id │ name   │      SELECT     │ id │ name   │ lower_name │
├────┼────────┤  LOWER(name)    ├────┼────────┼────────────┤
│ 1  │ Dharan │  ────────────>  │ 1  │ Dharan │ dharan     │
└────┴────────┘                 └────┴────────┴────────────┘
```

`lower_name` never touches the disk. It's born, displayed, and gone the moment the query finishes — which is exactly why functions are safe to use freely for analysis without ever risking the underlying data.

## Everything Composes

The real lesson hiding inside all of this isn't any single function — it's that they **stack**:

```text
CONCAT(LOWER(name), '567')

AVG(salary) + GROUP BY gender

DATEDIFF(CURDATE(), date_of_birth)
```

SQL functions were never meant to be isolated tools used one at a time. They're meant to be layered.

## The Whole Cast, Sorted by Job

| Category | Functions | Purpose |
|---|---|---|
| Aggregate | `COUNT()` | Count rows/values |
| Aggregate | `MIN()` | Minimum value |
| Aggregate | `MAX()` | Maximum value |
| Aggregate | `SUM()` | Total |
| Aggregate | `AVG()` | Average |
| String | `LENGTH()` | String length |
| String | `LOWER()` | Convert to lowercase |
| String | `CONCAT()` | Join strings |
| Date/Time | `NOW()` | Current date + time |
| Date/Time | `CURDATE()` | Current date |
| Date/Time | `YEAR()` | Extract year |
| Date/Time | `MONTH()` | Extract month |
| Date/Time | `DAY()` | Extract day |
| Date/Time | `DATEDIFF()` | Difference between dates |
| Math | `ROUND()` | Round number |
| Math | `FLOOR()` | Round down |
| Math | `CEIL()` | Round up |
| Math | `MOD()` | Remainder |
| Conditional | `IF()` | Simple condition |

## One Model, Instead of Twenty Names to Memorize

Skip the memorization. Ask what job each one does. 🦜

- *"How many?"* → `COUNT()`
- *"Smallest? Largest?"* → `MIN()` / `MAX()`
- *"Total? Average?"* → `SUM()` / `AVG()`
- *"How long is this text?"* → `LENGTH()`
- *"Lowercase it."* → `LOWER()`
- *"Join these."* → `CONCAT()`
- *"Right now?"* → `NOW()` / `CURDATE()`
- *"Year, month, day?"* → `YEAR()` / `MONTH()` / `DAY()`
- *"Days between these two dates?"* → `DATEDIFF()`
- *"Round this."* → `ROUND()`
- *"Always down. Always up."* → `FLOOR()` / `CEIL()`
- *"What's left over?"* → `MOD()`
- *"If this, then that."* → `IF()`

## The Bigger Shape of a Query

This lesson is really about a quiet upgrade happening underneath the syntax — from:

```text
SELECT data
```

to:

```text
SELECT calculated_data
```

and eventually to something like:

```sql
SELECT
    gender,
    AVG(salary) AS average_salary
FROM users
WHERE salary > 30000
GROUP BY gender;
```

```text
SELECT → AVG() → FROM → WHERE → GROUP BY
```

That's much closer to how SQL actually behaves inside real backend systems and data pipelines.

## What Not to Do: Memorize Everything

The instructor is explicit here, and it's worth taking at face value: don't try to memorize every MySQL function that exists. Learn the commonly useful ones, and learn how to look the rest up — documentation, search, or otherwise — when a new need arises. Finishing the lesson isn't the same as finishing the learning; practice and reference material still have work to do.

For backend and API work specifically, the functions worth making second nature are:

```text
COUNT()  SUM()  AVG()  MIN()  MAX()
GROUP BY

LENGTH()  LOWER()  CONCAT()

NOW()  CURDATE()  YEAR()  MONTH()  DAY()  DATEDIFF()

ROUND()  MOD()

IF()
```

And more than the functions themselves — how they sit inside the full sentence:

```text
SELECT → WHERE → GROUP BY → ORDER BY → HAVING → JOIN
```

Because knowing what `AVG()` does is trivial. Knowing *when* to reach for `AVG()` alongside `GROUP BY`, `WHERE`, and `HAVING` — together, in the right order — is the point where SQL stops being vocabulary and starts being a tool. 😄

> **The takeaway:** *"A function never asks the table to change. It only asks a question — count this, average that, round this, compare these dates — and hands back an answer that lives just long enough for you to use it."*
