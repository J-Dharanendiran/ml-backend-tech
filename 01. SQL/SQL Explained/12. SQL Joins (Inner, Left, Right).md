# 🧩 The Answer Lives in Two Tables: INNER, LEFT & RIGHT JOIN in MySQL

> *"Good database design splits one story across many tables. A JOIN is how you ask for the story back in one piece."*

There is one idea underneath this entire chapter. Hold onto it:

> **A JOIN lets you build a result by combining rows from two tables, based on a related column.**

In the lecture's example, the `users` table holds user information and the `addresses` table holds address information. The bridge between them is:

```text
users.id  ↔  addresses.user_id
```

Think of a JOIN as telling MySQL:

> *"These two tables know different pieces of information about the same thing. Put the pieces together for me."*

Because apparently storing related information in separate tables and then making humans reconnect it wasn't complicated enough. 😄

---

## 🧭 The Question Nobody Table Can Answer

> *"Why do we even need JOINs?"*

Suppose you have two tables.

**`users`**

| id | name   | gender |
| -: | ------ | ------ |
|  1 | Aarav  | M      |
|  2 | Raj    | M      |
|  3 | Yash   | M      |
|  4 | Farhan | M      |

**`addresses`**

|  id | user_id | city      | state         |
| --: | ------: | --------- | ------------- |
| 101 |       1 | Mumbai    | Maharashtra   |
| 102 |       2 | Bengaluru | Karnataka     |
| 103 |       4 | Lucknow   | Uttar Pradesh |

The user's information sits in one table. Their address sits in another. But what you actually want is a single view:

| name   | gender | city      | state         |
| ------ | ------ | --------- | ------------- |
| Aarav  | M      | Mumbai    | Maharashtra   |
| Raj    | M      | Bengaluru | Karnataka     |
| Farhan | M      | Lucknow   | Uttar Pradesh |

That combined view is exactly where JOINs are used.

The relationship that makes it possible is the one you built in the last chapter:

```text
users.id
   ↓
addresses.user_id
```

`addresses.user_id` is the **foreign key** referring to `users.id`.

---

## 🎚️ Three JOINs, One Question

> *"How many kinds of JOIN are there, and how do they differ?"*

The lesson covers three:

```text
INNER JOIN
LEFT JOIN
RIGHT JOIN
```

They all combine rows from two tables. The fundamental difference is **which rows are guaranteed to appear in the result**:

| JOIN | Rows guaranteed |
| --- | --- |
| **INNER JOIN** | Matching rows only |
| **LEFT JOIN** | All rows from the left table + matches |
| **RIGHT JOIN** | All rows from the right table + matches |

Everything else in this chapter is just watching that one table play out on real data. Let's start with the strictest one.

---

## 🤝 The Strict One: INNER JOIN

> *"What does INNER JOIN actually keep?"*

An INNER JOIN returns only the rows where the join condition matches **in both tables**.

Take the same two tables and compare `users.id` against `addresses.user_id`:

```text
users.id       addresses.user_id
   1      =          1       ✓
   2      =          2       ✓
   3      =          ?       ✗
   4      =          4       ✓
```

So:

```text
1 → match
2 → match
3 → no match
4 → match
```

The result contains only the overlapping records:

| name   | city      |
| ------ | --------- |
| Aarav  | Mumbai    |
| Raj    | Bengaluru |
| Farhan | Lucknow   |

> *"Where did Yash go?"*

Yash disappears, because there is no `user_id = 3` in `addresses`. That is exactly how the instructor describes INNER JOIN: **only the overlapping, matching records are returned.**

## ✍️ Reading the Syntax One Piece at a Time

> *"Okay, so how do I actually write it?"*

```sql
SELECT users.name, addresses.city
FROM users
INNER JOIN addresses
ON users.id = addresses.user_id;
```

Four pieces:

**`SELECT users.name, addresses.city`** means: *"Give me the name from `users` and the city from `addresses`."* You can select columns from **both** tables.

**`FROM users`** means: *"Start with the `users` table."*

**`INNER JOIN addresses`** means: *"Combine `users` with `addresses`."*

**`ON users.id = addresses.user_id`** is the matching condition. You're telling MySQL:

```text
users.id
   =
addresses.user_id
```

Only when that condition is true should the rows be combined.

### 🧰 One nuance the lecture doesn't mention

In MySQL, `JOIN`, `INNER JOIN` and `CROSS JOIN` are syntactic equivalents and can replace one another. So `users JOIN addresses ON ...` behaves the same as `users INNER JOIN addresses ON ...`. In standard SQL they are not equivalent, which is why writing `INNER JOIN` when you mean an inner join is the clearer habit.

## 🧺 Picking Columns From Either Side

> *"Can I take any column from either table?"*

Yes. The instructor demonstrates this explicitly:

```sql
SELECT
    users.name,
    users.gender,
    addresses.city,
    addresses.state
FROM users
INNER JOIN addresses
ON users.id = addresses.user_id;
```

* From `users`: `name`, `gender`
* From `addresses`: `city`, `state`

So a JOIN does **not** mean:

> ❌ *"Combine the tables permanently."*

It means:

> ✅ *"For this query, give me a result containing columns from both tables."*

The original tables remain separate. We'll come back to this point, because it matters.

---

## 🏷️ Why `users.name` and Not Just `name`?

> *"Why do I keep writing the table name before the column name?"*

You'll constantly see:

```sql
users.name          instead of        name
addresses.city      instead of        city
```

This tells MySQL exactly which table the column belongs to. It matters most when both tables contain columns with the **same name**:

```text
users.id
addresses.id
```

These are two different columns that happen to both be called `id`.

### 💥 More than a readability habit

The lecture frames ambiguity as something a *human* might find confusing. In MySQL it is stricter than that. If you write an unqualified column name that exists in more than one joined table, MySQL doesn't guess. It raises error 1052, `Column '...' in field list is ambiguous`. The MySQL error reference gives the fix: qualify the column with its table name.

So `SELECT id FROM users INNER JOIN addresses ...` would fail, while `SELECT users.id ...` works.

---

## 🎭 Renaming What You See: Column Aliases

> *"What if both `id` columns come back and I can't tell them apart?"*

You can rename a column **in the result** using `AS`:

```sql
SELECT
    addresses.id AS address_id
FROM users
INNER JOIN addresses
ON users.id = addresses.user_id;
```

The result column will be called:

```text
address_id
```

instead of:

```text
id
```

The instructor points out why this helps: a bare `id` in a result could be the user's ID or the address's ID, and a reader can't tell which.

Now the important distinction:

> `addresses.id AS address_id` does **not** rename the actual database column. It only changes the name displayed in the query result.

One small extra from the manual, beyond the lecture: you can't refer to a column alias inside a `WHERE` clause, because the value might not be determined yet when `WHERE` runs.

## 👑 The Generous One: LEFT JOIN

> *"But what if I don't want Yash to vanish?"*

Now things get more interesting. An INNER JOIN says:

> *"Give me only the matching stuff."*

A LEFT JOIN says:

> *"Give me **everything from the left table**, even if there isn't a match on the right."*

> *"Which one is the 'left' table?"*

The instructor identifies the left table as **the table written first**. Here that is `users`:

```sql
FROM users
LEFT JOIN addresses
```

```text
LEFT TABLE
    ↓
  users        ← the priority table
```

### 🧪 Watching it work

Use the same data:

**`users`**

| id | name   |
| -: | ------ |
|  1 | Aarav  |
|  2 | Raj    |
|  3 | Yash   |
|  4 | Farhan |

**`addresses`**

| user_id | city      |
| ------: | --------- |
|       1 | Mumbai    |
|       2 | Bengaluru |
|       4 | Lucknow   |

Run:

```sql
SELECT
    users.name,
    addresses.city
FROM users
LEFT JOIN addresses
ON users.id = addresses.user_id;
```

Result:

| name   | city      |
| ------ | --------- |
| Aarav  | Mumbai    |
| Raj    | Bengaluru |
| Yash   | NULL      |
| Farhan | Lucknow   |

> *"Why is Yash still here, and why is his city NULL?"*

Because `users` is the left table, and a LEFT JOIN guarantees **all rows from the left table**. There is no address for Yash, so MySQL can't invent one. It fills the missing right-side columns with `NULL`. The instructor is explicit about this: missing columns from the right table become `NULL`.

### 🧠 The easiest way to remember it

```text
LEFT JOIN
    ↓
LEFT TABLE = PRIORITY
```

For `FROM users LEFT JOIN addresses`:

```text
users       ← priority
addresses   ← optional
```

Read it as: **all users, plus their matching addresses.** If an address doesn't exist, the address columns are `NULL`.

---

## 🪞 The Mirror: RIGHT JOIN

> *"And RIGHT JOIN? Is it something completely different?"*

No. RIGHT JOIN is the mirror image. The instructor explains it as:

> *Return all rows from the right table, plus matching rows from the left table. If there's no match, the left-side columns become NULL.*

For:

```sql
FROM users
RIGHT JOIN addresses
ON users.id = addresses.user_id
```

the right table is `addresses`, so:

```text
addresses = priority
```

Every address must appear in the result.

### 🧪 An address with no owner

Change the data so the mismatch is on the other side:

**`users`**

| id | name  |
| -: | ----- |
|  1 | Aarav |
|  2 | Raj   |
|  3 | Yash  |

**`addresses`**

| user_id | city      |
| ------: | --------- |
|       1 | Mumbai    |
|       2 | Bengaluru |
|       4 | Delhi     |

Notice that the address with `user_id = 4` has **no corresponding user**. Now:

```sql
SELECT
    users.name,
    addresses.city
FROM users
RIGHT JOIN addresses
ON users.id = addresses.user_id;
```

Result:

| name  | city      |
| ----- | --------- |
| Aarav | Mumbai    |
| Raj   | Bengaluru |
| NULL  | Delhi     |

Because `addresses` is the right table, every one of its rows survives. There is no user with `id = 4`, so `users.name` is `NULL`. This is the same rule as LEFT JOIN with the roles swapped: unmatched records produce `NULL` on the **other** side.

## 🎯 The Habit to Make Automatic: Who Gets Priority?

Suppose you write:

```sql
FROM A
LEFT JOIN B
```

Then `A` is the left table and `B` is the right table. The result is **ALL of A + matching B**.

```sql
FROM A
RIGHT JOIN B
```

Here `A` is still left and `B` is still right. The result is **matching A + ALL of B**.

```sql
FROM A
INNER JOIN B
```

The result is **only rows matching in both A and B**.

Notice that "left" and "right" never change meaning. Left is always the table written first, right is always the one after the JOIN keyword. Only the *priority* moves.

### 📋 The one table to memorize

| JOIN | Left table | Right table | Unmatched rows |
| --- | --- | --- | --- |
| **INNER JOIN** | Only matches | Only matches | Removed |
| **LEFT JOIN** | All | Matching only | Right side → `NULL` |
| **RIGHT JOIN** | Matching only | All | Left side → `NULL` |

This is the entire game. If you understand this table, JOINs stop looking like an ancient SQL ritual.

### 🏹 A mental shortcut

When you see `FROM users LEFT JOIN addresses`, put a giant arrow over `users`:

```text
          PRIORITY
             ↓
FROM users
LEFT JOIN addresses
```

When you see `FROM users RIGHT JOIN addresses`, put it over `addresses`:

```text
FROM users
RIGHT JOIN addresses
                 ↑
              PRIORITY
```

For INNER JOIN, forget priority. Just ask: **does a matching row exist in both tables?** If yes, it's in the result. If no, it's gone.

## ⚙️ What Actually Happens During a JOIN?

> *"But what is MySQL doing step by step?"*

Take the INNER JOIN from earlier:

```sql
SELECT users.name, addresses.city
FROM users
INNER JOIN addresses
ON users.id = addresses.user_id;
```

Conceptually, it goes like this:

**Step 1.** Look at `users.id`: `1, 2, 3, 4`.

**Step 2.** Look at `addresses.user_id`: `1, 2, 4`.

**Step 3.** Compare according to `users.id = addresses.user_id`.

**Step 4.** Check each:

```text
1 = 1  → match
2 = 2  → match
3 = ?  → no match
4 = 4  → match
```

**Step 5.** For INNER JOIN, keep only `1`, `2`, `4`.

**Step 6.** Build the requested result columns, `users.name` and `addresses.city`:

```text
Aarav   Mumbai
Raj     Bengaluru
Farhan  Lucknow
```

This matches how the instructor explains the matching process. Treat it as a **mental model**, not a description of the engine: MySQL's optimizer chooses its own strategy (from 8.0.18 it uses hash joins whenever possible), so the real execution isn't a literal six-step walk. The *result* is what these steps describe.

## 🧱 A JOIN Is Not a Merge

> *"So after a JOIN, are my two tables now one table?"*

No. When you write:

```sql
SELECT ...
FROM users
INNER JOIN addresses ...
```

you are **not** changing the database structure. You're asking MySQL to produce a **temporary query result** that combines information from both tables. The originals:

```text
users
addresses
```

remain separate. That is one reason relational databases are designed this way: related information lives in separate tables, and JOINs retrieve it together when needed.

## 🔗 Where the Foreign Key Fits

> *"Do I need the foreign key from last chapter to do a JOIN?"*

This is worth being precise about. The lecture connects the two ideas:

```text
users.id
     ↑
     │ referenced by
     │
addresses.user_id
```

`users.id` is the referenced primary key, and `addresses.user_id` is the foreign key. That relationship makes the JOIN condition natural:

```sql
ON users.id = addresses.user_id
```

The concepts chain together:

```text
Primary Key
     ↓
Foreign Key
     ↓
Relationship between tables
     ↓
JOIN
     ↓
Retrieve related data
```

But here is the correction. A JOIN does **not require** a foreign key. According to the MySQL manual, the `ON` clause accepts any conditional expression of the kind you could put in a `WHERE` clause. A foreign key is what makes the relationship *trustworthy* (no ghost users, as you saw), but MySQL will happily JOIN on any condition you write. The foreign key guards the data; the `ON` clause does the joining.

## 🕳️ Why NULL Appears

> *"What does that NULL in the result actually mean?"*

Understand this rather than memorize it. Suppose `users` contains `3 | Yash`, but `addresses` has no `user_id = 3`. With a LEFT JOIN, Yash must still appear, because `users` is the left table. But MySQL has no address information to put next to him:

```text
city  = NULL
state = NULL
```

`NULL` here means the value is unavailable in that result. The manual states the mechanism directly: when a LEFT JOIN finds no matching row on the right, it uses a row with all columns set to `NULL` for the right table.

## 🧮 "So It's Like Sets?"

Somewhere in the middle of all these diagrams, a thought arrives. You've seen this before:

> *"So it's more like the intersection, A − B and B − A. I already know these from sets, right?"*

Yes, you're reusing something real. But one small correction first: **A − B and B − A are set differences, not intersections.** Let's line the two vocabularies up.

Suppose:

```text
A = {1, 2, 3, 4}
B = {1, 2, 5, 6}
```

### 1️⃣ INNER JOIN ≈ Intersection

```text
A ∩ B = {1, 2}
```

```text
A             B
┌─────────┐ ┌─────────┐
│ 1       │ │       1 │
│ 2 ████████████ 2    │
│ 3       │ │       5 │
│ 4       │ │       6 │
└─────────┘ └─────────┘
```

Only the overlapping, matching records survive. That is exactly the idea the instructor explains for INNER JOIN.

### 2️⃣ LEFT JOIN ≈ all of A, plus the matching part of B

Conceptually `A ∪ (A ∩ B)`. But since `A ∩ B` is already inside A, this effectively means **keep ALL of A, plus whatever matches from B**:

```text
A LEFT JOIN B → {1, 2, 3, 4}
```

For `3` and `4`, the B-side columns are `NULL`.

### 3️⃣ RIGHT JOIN ≈ all of B, plus the matching part of A

```text
A RIGHT JOIN B → {1, 2, 5, 6}
```

For `5` and `6`, the A-side columns are `NULL`.

### 4️⃣ Where your A − B and B − A idea earns its keep

The set differences tell you **what gets excluded or NULL-padded**:

```text
A − B = {3, 4}     in A, not in B
B − A = {5, 6}     in B, not in A
```

* `A − B` are the records an INNER JOIN drops, but a LEFT JOIN keeps with `NULL`s on the right.
* `B − A` are the records an INNER JOIN drops, but a RIGHT JOIN keeps with `NULL`s on the left.

Put it all on one picture:

```text
             A              B
        ┌─────────┬─────────┐
        │ A − B   │ B − A   │
        │         │         │
        │    A ∩ B          │
        └─────────┴─────────┘
```

| SQL JOIN | Set-theory intuition |
| --- | --- |
| INNER JOIN | A ∩ B |
| LEFT JOIN | A + matching part of B |
| RIGHT JOIN | B + matching part of A |

### ⚠️ Where the analogy stops

SQL JOINs operate on **rows and matching conditions**, not literally on mathematical sets. Duplicates, multiple matches and `NULL` make real behavior more complicated than pure set theory. `NULL` is the easiest one to see: in MySQL, comparing anything with `NULL` using `=` yields `NULL`, not true. So a row whose join column is `NULL` will never satisfy `ON users.id = addresses.user_id`.

As a mental model while learning, your intersection idea is excellent. You're reusing something you already know instead of letting SQL invent yet another collection of symbols to torment you. 😄

## 🔦 Bonus: Finding Your A − B in Real SQL

> *"If A − B is 'users with no address,' can I actually ask MySQL for exactly that?"*

You can, and it uses the very fact you just learned. The manual notes that a LEFT JOIN produces a `NULL` row for unmatched left rows, and shows how to use that to find rows with no counterpart: add `WHERE` on a right-table column being `NULL`.

Applied to your tables (this is beyond what the instructor taught):

```sql
SELECT users.name
FROM users
LEFT JOIN addresses
ON users.id = addresses.user_id
WHERE addresses.id IS NULL;
```

On the lecture's first dataset this should return just **Yash**, the one user with no address. Test for `NULL` with `IS NULL`, not `= NULL`, because the manual says comparisons with `NULL` using `=` produce `NULL`.

The manual also recommends `LEFT JOIN` over `RIGHT JOIN` to keep code portable across databases. So to find your `B − A` (addresses with no user), the portable habit is to **swap the table order** and use LEFT JOIN, rather than reaching for RIGHT JOIN. Internally, MySQL does the same thing: it converts right outer joins into equivalent left joins at the parser stage.

```text
                SQL JOINs
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     INNER        LEFT        RIGHT
        │           │           │

    Matching     ALL LEFT    ALL RIGHT
```

Or even shorter:

```text

```

```sql

```

## 🔎 Checked Against the Documentation

Several claims in the lecture and these notes were checked against the MySQL manual. Here is exactly what could and could not be confirmed. All result tables in this chapter are **derived by hand from the lecture's sample data**; I did not run them on a live MySQL server.

**Confirmed, from the full text of [MySQL 8.4 Reference Manual, JOIN Clause](https://dev.mysql.com/doc/refman/8.4/en/join.html), which I opened in full:**

* In MySQL, `JOIN`, `CROSS JOIN` and `INNER JOIN` are syntactic equivalents and can replace each other. In standard SQL they are not equivalent.
* The condition used with `ON` is any conditional expression of the kind usable in a `WHERE` clause. Generally `ON` says how to join tables and `WHERE` restricts which rows appear in the result.
* In a `LEFT JOIN`, if no matching row exists for the right table, a row with all columns set to `NULL` is used for the right table.
* The manual shows the `LEFT JOIN ... WHERE right_tbl.id IS NULL` pattern for finding rows in one table with no counterpart in another.
* `RIGHT JOIN` works analogously to `LEFT JOIN`, and the manual recommends using `LEFT JOIN` instead for portability across databases.
* The syntax block lists `INNER`/`CROSS`/`STRAIGHT_JOIN`, `LEFT`/`RIGHT [OUTER]`, and `NATURAL` joins, with `ON` or `USING`. It does not list a `FULL OUTER JOIN`.

**Confirmed only from search-result excerpts, not from a page I opened in full:**

* Error 1052 (`ER_NON_UNIQ_ERROR`), "Column '...' in field list is ambiguous", is caused by an unqualified column in a select list or `ON` clause, with the fix of qualifying it with a table name. Source: [MySQL Server Error Message Reference](https://dev.mysql.com/doc/mysql-errors/en/server-error-reference.html) (9.7 excerpt; the 8.0 reference has the same entry).
* Column aliases are given in the `SELECT` list, `AS` is optional, and an alias cannot be referenced in a `WHERE` clause. Source: [MySQL 8.4 Reference Manual, SELECT Statement](https://dev.mysql.com/doc/refman/8.4/en/select.html).
* Right outer joins are converted to equivalent left joins at the parser stage. Source: [MySQL 8.4, Outer Join Simplification](https://dev.mysql.com/doc/en/outer-join-simplification.html).
* Any comparison with `NULL` using operators like `=` yields `NULL`, and `IS NULL` is the way to test for it. Source: [MySQL 8.4, Working with NULL Values](https://dev.mysql.com/doc/refman/8.4/en/working-with-null.html).
* From MySQL 8.0.18, hash joins are used whenever possible. Source: [MySQL 8.0, Hash Join Optimization](https://dev.mysql.com/doc/refman/8.0/en/hash-joins.html) (seen in a search excerpt; this is why the six-step walkthrough above is labeled a mental model).

**Not confirmed from the manual text I retrieved:**

* That a column alias only changes the displayed name and never the stored column. This follows from a `SELECT` not altering table structure, but the excerpt I read does not state it in those words.
* That one left-table row matching several right-table rows produces several result rows. The lecture notes allude to "multiple matches", and this is standard JOIN behavior, but I did not find it stated in the pages I read. A quick test: add a second address for one user and rerun the JOIN.
* The set-theory correspondences (INNER ≈ ∩, and so on) are teaching analogies, not documented definitions.
* I read the 8.4 manual; its version selector lists 9.7 as current. Behavior on your installed version may differ, so check the matching manual.

---

## ✅ Final Takeaway

> **"INNER JOIN keeps only what both tables agree on. LEFT JOIN keeps everything on the left and fills the gaps with NULL. RIGHT JOIN does the same from the other side. The only thing that ever changes is *which table gets priority*, and the only thing that ever fills the gaps is NULL."**
