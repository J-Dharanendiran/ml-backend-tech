# 🪞 The Table That Looked in the Mirror: Self Joins in MySQL

> *"A self join is not a new kind of `JOIN`. It is a normal `JOIN` where a table meets a copy of itself."*

The name sounds intimidating. **Self join.** It sounds like a special, advanced, slightly dangerous SQL creature. 🐉

The instructor's first move is to take that fear away. His main point is almost embarrassingly simple:

> **A self join is a regular `JOIN` where you join a table with itself.**

That is the entire idea. The rest of this chapter is about *why* you would ever want it, and *how* to keep your head straight while writing it.

---

## 🔁 First, a quick reminder of what a `JOIN` does

A `JOIN` combines **related data** from tables. You have seen it with `users` and `addresses`, or `users` and `orders`:

```text
users
   JOIN
orders
```

In every example so far, the related data lived in **two different tables**.

But now picture a table where the relationship lives **inside the same table**. Rows pointing at other rows of their own kind.

That sounds strange until you see it.

---

## 👥 The table that points at itself

Here is our `users` table. Notice the new column, `referred_by_id`:

| id | name   | referred_by_id |
| -: | ------ | -------------: |
|  1 | Aarav  |           NULL |
|  2 | Ananya |              1 |
|  3 | Sneha  |              2 |
|  4 | Yash   |           NULL |
|  5 | Imran  |              1 |

Now read it like a detective. 🕵️

```text
Ananya → referred by user 1
Sneha  → referred by user 2
Imran  → referred by user 1
```

> 💭 **"But what do those numbers actually mean? Who is user 1?"**

Look up `id = 1` in the **same table**: that is **Aarav**. And `id = 2` is **Ananya**.

So:

```text
Ananya was referred by Aarav
Sneha  was referred by Ananya
Imran  was referred by Aarav
```

Do you see what just happened? To decode `referred_by_id`, you had to look **back into the table you were already reading.** One column of `users` points at another row of `users`. That is the situation the instructor uses to introduce self joins.

```text
users
┌────┬─────────┬────────────────┐
│ id │ name    │ referred_by_id │
├────┼─────────┼────────────────┤
│ 1  │ Aarav   │ NULL           │◄──┐
│ 2  │ Ananya  │ 1              │───┘   (Ananya points at row 1)
│ 3  │ Sneha   │ 2              │───┐
│ 4  │ Yash    │ NULL           │   │   (Sneha points at row 2)
│ 5  │ Imran   │ 1              │   │
└────┴─────────┴────────────────┘   │
         ▲──────────────────────────┘
```

---

## 🤨 Why store an ID at all? Why not just write the name?

> 💭 **"Why not simply store `referred_by = 'Aarav'` and skip all this?"**

The instructor makes a database-design point here. You *could* store the name. But then the database would repeat the same text again and again:

```text
Aarav
Aarav
Aarav
Aarav
```

when it could store a tiny reference:

```text
1
1
1
1
```

He describes this as saving storage, with the ID acting as the **reference** to the person.

*(A related benefit, which is my own reasoning rather than the lecture's: if Aarav's name ever changes, you update one row instead of hunting down every copy.)*

But there is a catch, and you can feel it already. A human looking at `referred_by_id = 1` learns almost nothing. What you want to *see* is:

```text
referred_by_name = Aarav
```

Turning that ID back into a name is exactly the job of a **self join**. ✨

---

## 🧠 The mental model that makes everything easy

This is the most important idea in the lesson. Read it twice.

Do **not** think:

> ~~"I'm joining a table with itself, so this must be some terrifying special SQL creature."~~

Instead, think:

```text
users AS A
users AS B
```

as though they were **two separate tables.**

The instructor explicitly recommends this mental model. Pretend you have two copies of `users` on your desk:

```text
                 SAME TABLE
              ┌───────────────┐
              │     users     │
              └───────────────┘
                   ↙     ↘
             copy A       copy B
               │             │
         current user     the referrer
```

- **A** is the person you are looking at right now.
- **B** is the person they point to.

Once you see two tables, the rest is just an ordinary `JOIN`.

---

## 🏷️ Why the aliases are not optional

> 💭 **"If it's the same table, how does SQL know which copy I mean?"**

It doesn't, unless you tell it. That is the job of **aliases**.

```sql
FROM users AS a
INNER JOIN users AS b
```

Now:

```text
a → one instance of users
b → another instance of users
```

Physically, it is still one table. But SQL now treats `a` and `b` as two separate handles. So:

| You write | It means |
| --------- | -------- |
| `a.id` | the ID from the **a** instance |
| `b.id` | the ID from the **b** instance |
| `a.name` | the name from the **a** instance |
| `b.name` | the name from the **b** instance |

Imagine trying to write this **without** aliases:

```sql
users.id
users.name
users.referred_by_id
users.name
```

*Which* `users.name`? The current user's? The referrer's? SQL has no way to tell. Aliases are what make a self join **possible**, not just tidy. 🎯

---

## 🔧 Writing the actual query

Here is the query the instructor builds:

```sql
SELECT
    a.id,
    a.name AS user_name,
    b.name AS referred_by_name
FROM users AS a
INNER JOIN users AS b
    ON a.referred_by_id = b.id;
```

Take it apart one line at a time.

### `FROM users AS a`

> Take the `users` table and call this instance **a**.

### `INNER JOIN users AS b`

> Take the **same** `users` table again and call this instance **b**.

So now, conceptually, `A = users` and `B = users`.

### The line that does all the work

```sql
ON a.referred_by_id = b.id
```

> 💭 **"Why `a.referred_by_id = b.id`? What is this line actually saying?"**

Read it literally:

> Take the `referred_by_id` from **A** and match it with the `id` from **B**.

Watch it work for Ananya:

```text
A:  Ananya, referred_by_id = 1
        ↓
    look for B where B.id = 1
        ↓
B:  Aarav, id = 1
        ↓
    Ananya → Aarav
```

That is the entire trick. `a.referred_by_id` holds the ID of *another user*, and `b.id` is how you find that user in the second copy.

---

## 📤 What comes out

| id | user_name | referred_by_name |
| -: | --------- | ---------------- |
|  2 | Ananya    | Aarav            |
|  3 | Sneha     | Ananya           |
|  5 | Imran     | Aarav            |

Instead of the unreadable:

```text
2 → 1
3 → 2
5 → 1
```

you get something a human can actually use:

```text
Ananya → Aarav
Sneha  → Ananya
Imran  → Aarav
```

The ID relationship has become a **human-readable relationship**.

---

## 🕳️ Where did Aarav and Yash go?

Look at the output again. Five users in the table. Only three rows in the result.

> 💭 **"Why are Aarav and Yash missing? Did I lose them?"**

You didn't lose them by accident. Their `referred_by_id` is `NULL`:

```text
Aarav → NULL   (nobody referred him)
Yash  → NULL   (nobody referred him)
```

An `INNER JOIN` only keeps rows where a **match exists on the other side.** `NULL` matches no `id`, so those two rows are dropped.

The instructor uses `INNER JOIN` first for exactly this reason: he only wants to see users who *were* referred by someone.

---

## 🟢 Bringing them back with `LEFT JOIN`

But what if you want **everyone**, referred or not?

```sql
SELECT
    a.id,
    a.name AS user_name,
    b.name AS referred_by_name
FROM users AS a
LEFT JOIN users AS b
    ON a.referred_by_id = b.id;
```

| id | user_name | referred_by_name |
| -: | --------- | ---------------- |
|  1 | Aarav     | NULL             |
|  2 | Ananya    | Aarav            |
|  3 | Sneha     | Ananya           |
|  4 | Yash      | NULL             |
|  5 | Imran     | Aarav            |

Now Aarav and Yash are back, with `NULL` where a referrer would be. This is why the instructor ultimately uses `LEFT JOIN` in the handbook example: users whose `referred_by_id` is `NULL` stay visible.

```text
INNER JOIN  →  only users who HAVE a referrer
LEFT JOIN   →  ALL users, plus their referrer if one exists
```

The instructor also notes that other `JOIN` types can technically be used, depending on the use case. Same idea, different question being asked.

> 🔑 **The join *type* decides who is kept. The self-join *shape* (same table, two aliases) never changes.**

---

## 🎭 Same table, different roles

Here is a subtle point that becomes very useful when your SQL gets more complicated.

The **table** is the same in both copies:

```text
users
```

But the **role** each copy plays is different:

```text
A = the user being examined
B = the user that A points to
```

In *our* query, `b` is the person who **referred** `a`. So `b.name` is the referrer's name.

> ⚠️ **Roles are set by the `ON` line, not by the alias letters.** If you flipped it to `ON a.id = b.referred_by_id`, then `a` would be the referrer and `b` would be the person referred. The letters are just labels. The `ON` condition decides who is who.

*(The original notes worded this point loosely, saying `b` was "referred to / was referred by, depending on how you define the relationship." The precise version is the one above: in this specific query, `b` is the referrer.)*

## 🧭 The general pattern

The lesson generalizes into one rule:

> **Use a self join when a column in a table points to another record in that same table.**

```sql
SELECT ...
FROM table AS a
JOIN table AS b
    ON a.some_reference = b.id;
```

- The **table** is the same.
- The **aliases** are different.
- The **records** being related are different.

---

## 🏢 The same idea, wearing a different outfit

> 💭 **"Is this only for referrals?"**

Not at all. Take an employee table where each person points at their manager:

```text
employees
┌────┬──────────┬─────────────┐
│ id │ name     │ manager_id  │
├────┼──────────┼─────────────┤
│ 1  │ Raj      │ NULL        │
│ 2  │ Priya    │ 1           │
│ 3  │ Arun     │ 1           │
│ 4  │ Kiran    │ 2           │
└────┴──────────┴─────────────┘
```

`Priya.manager_id = 1` means **Priya → Raj**. `Kiran.manager_id = 2` means **Kiran → Priya**.

```sql
SELECT
    e.name AS employee,
    m.name AS manager
FROM employees AS e
LEFT JOIN employees AS m
    ON e.manager_id = m.id;
```

| employee | manager |
| -------- | ------- |
| Raj      | NULL    |
| Priya    | Raj     |
| Arun     | Raj     |
| Kiran    | Priya   |

Same concept. Different real-world relationship. Swap `e` and `m` for `a` and `b`, and `manager_id` for `referred_by_id`, and you are looking at the query from before.

This shape shows up in many places:

- 👤 User → the person who referred them
- 👔 Employee → manager (or supervisor)
- 👨‍👧 Parent → child
- 🗂️ Category → parent category
- 🏛️ Any hierarchical organizational data

## 🌳 Hierarchies

Self joins are especially natural when data has a **hierarchy**:

```text
Company
│
├── CEO
│   ├── Manager A
│   │   ├── Employee 1
│   │   └── Employee 2
│   │
│   └── Manager B
│       └── Employee 3
```

One table can hold the whole tree using just `id`, `name`, and `manager_id`. Each `manager_id` points back to another row in the same table. That is a classic self-join situation.

One honest boundary: **a single self join climbs exactly one level.** It shows each person next to their *direct* manager. To walk up several levels, you would chain more self joins, or use a recursive query. (That last point is beyond the lecture; MySQL's manual describes recursive common table expressions, linked in the Docs Check.)

## 🔬 The full walkthrough, step by step

Setup:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    referred_by_id INT
);
```

Data:

```text
1  Aarav   NULL
2  Ananya  1
3  Sneha   2
4  Yash    NULL
5  Imran   1
```

Query:

```sql
SELECT
    a.id,
    a.name AS user_name,
    b.name AS referred_by_name
FROM users AS a
LEFT JOIN users AS b
    ON a.referred_by_id = b.id;
```

**Step by step for Ananya:**

```text
A:  id = 2, name = Ananya, referred_by_id = 1
        ↓
Find B where B.id = 1
        ↓
B:  id = 1, name = Aarav
        ↓
Result:  Ananya | Aarav
```

**Step by step for Sneha:**

```text
A:  id = 3, name = Sneha, referred_by_id = 2
        ↓
Find B where B.id = 2
        ↓
B:  name = Ananya
        ↓
Result:  Sneha | Ananya
```

**Step by step for Yash (the `LEFT JOIN` case):**

```text
A:  id = 4, name = Yash, referred_by_id = NULL
        ↓
Find B where B.id = NULL  →  no match
        ↓
LEFT JOIN keeps Yash anyway
        ↓
Result:  Yash | NULL
```

No black magic. Just the same table given two names and treated like two tables. 😄

```text
─────────

A Self Join is a normal JOIN where the same
table is used twice.

Why?
→ When rows in a table are related to other
  rows in that same table.

How?
→ Give the same table different aliases.

    a.name AS user_name,
    b.name AS referred_by_name

    ON a.referred_by_id = b.id;
```

```text
users AS A          users AS B
    │                   │

    │                   │

```



**1. What is a self join?**

<details>
<summary>Answer</summary>

A join where a table is joined with itself, using different aliases. It is useful when rows in a table are related to other rows in the same table.

</details>

**2. Why do we need aliases?**

<details>
<summary>Answer</summary>

Because the same table is used twice. The aliases let SQL (and you) tell the two instances and their roles apart.

</details>

**3. Is a self join a separate `JOIN` type?**

<details>
<summary>Answer</summary>

No. It uses normal join types such as `INNER JOIN` or `LEFT JOIN`. "Self join" describes *what you are joining*, not a different mechanism.

</details>

**3 rows** (Ananya, Sneha, Imran). Aarav and Yash are missing because their `referred_by_id` is `NULL`, so there is no match.

## 💬 Final Takeaway

> **"When a column points at another row of its own table, don't look for a new kind of join. Give the table a second name, and it becomes an ordinary join between two tables that happen to be the same."**
