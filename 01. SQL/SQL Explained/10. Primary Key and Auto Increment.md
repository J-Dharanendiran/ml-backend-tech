# 🪪 The Number That Says Who You Are: Primary Key & AUTO_INCREMENT in MySQL

> *"A table with ten million rows is a city with ten million citizens. The database does not care what your name is. It cares which one you are."*

There is one idea underneath everything in this chapter. Hold onto it:

> **A Primary Key is the column (or combination of columns) that identifies each row uniquely in a table.**

The instructor connects three ideas in a single chain:

**Primary Key → the unique identity of a row → AUTO_INCREMENT to generate numeric IDs automatically**

But his explanation is simplified in a few places. Those places are marked as we go, so you learn the concept correctly instead of memorizing something that betrays you in an interview. SQL already has enough traps without volunteering for more. 😌

---

## 🏙️ The City With Ten Million Citizens

> *"Okay... but what actually **is** a Primary Key?"*

A **Primary Key** is a SQL constraint used to uniquely identify every row in a table.

Picture a small `users` table:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);
```

| id | name  | email           |
| -: | ----- | --------------- |
|  1 | Arun  | arun@gmail.com  |
|  2 | Ravi  | ravi@gmail.com  |
|  3 | Priya | priya@gmail.com |

Here `id` is the Primary Key. If you want Ravi's record, you don't wave your hands and say "the guy called Ravi." You say:

```sql
WHERE id = 2
```

That is an **unambiguous identity** for one row.

---

## 🔍 The Search for Something That Never Repeats

> *"Why do I even need a Primary Key? Can't I just find rows by some other column?"*

Imagine the `users` table now holds **10 million users**. You need to:

* 🔧 update one user
* 🗑️ delete one user
* 🔎 retrieve one user
* 🔗 relate that user to another table

Every one of those needs something that points at *that particular record*. So let's audition candidates:

| Candidate | Example | Why it fails |
| --- | --- | --- |
| **Name** | `name = 'Dharan'` | Multiple people can have the same name |
| **Date of birth** | `dob = '2003-05-20'` | Many people share a birthday |
| **Salary** | `salary = 50000` | Obviously, many users share a salary |
| **Email** | `email = 'abc@gmail.com'` | Often unique, but **not necessarily a good Primary Key** (see below) |

> *"But email **is** unique. Why can't email be the Primary Key?"*

Email is the tempting one. It can often identify a user, but business rules around email change. Your application may eventually allow:

```text
email = NULL
```

or let users change their email. So instead we create an independent identifier:

```text
id = 1
id = 2
id = 3
...
```

Now the user's identity no longer depends on their personal information. **That is the real usefulness of a Primary Key.**

There is a deeper version of this point. Technically, in some designs you *can* use a natural business attribute as a Primary Key. But many systems prefer a separate identifier such as `user_id`, because the identifier should represent the **entity itself**, not a piece of mutable business data. Watch:

```text
id = 1523
email = old@email.com
```

Later:

```text
id = 1523
email = new@email.com
```

The email changed. The identity didn't. It is still **1523**. This is a major reason *surrogate IDs* are so common.

## ⚖️ The Two Vows Every Primary Key Takes

A Primary Key makes two promises, and breaking either one gets your row rejected.

### Vow 1️⃣: "I will never repeat."

> *"Can a Primary Key have duplicate values?"*

No. The database must prevent two rows from having the same Primary Key value:

```text
id
--
1
2
3
2   ❌
```

### Vow 2️⃣: "I will never be empty."

> *"Can a Primary Key be NULL?"*

No.

```text
id
--
1
2
NULL   ❌
4
```

The purpose of the key is to identify a row. What would it even mean to identify a row by `id = NULL`? That is not an identity. That is the absence of one.

So:

```text
PRIMARY KEY
   ↓
UNIQUE
   +
NOT NULL
```

In MySQL, defining a column as `PRIMARY KEY` enforces both uniqueness and non-nullability.

---

## 👥 The Twin That Looks Identical: Primary Key vs UNIQUE

> *"If both stop duplicates, what's the actual difference between Primary Key and UNIQUE?"*

This is probably the **most important part of the lecture**. At first glance they are near-identical. Both prevent duplicate values:

```sql
id INT PRIMARY KEY
```

```sql
email VARCHAR(255) UNIQUE
```

But they serve different **roles**:

* 🪪 **Primary Key** → think: *"This is the main identity of the row."*
* 🚫 **UNIQUE** → think: *"This value must not be duplicated."*

That distinction is extremely important. Now let's see where the two actually diverge.

### 🔻 Difference #1: NULL

The Primary Key cannot contain NULL. A nullable column with a UNIQUE constraint can:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(255) UNIQUE
);
```

| id | email     |
| -: | --------- |
|  1 | a@gmail.com |
|  2 | b@gmail.com |
|  3 | NULL      |

Now here is the first place a common simplification lurks:

> ❌ *"UNIQUE allows exactly one NULL."*

**That's wrong.** In MySQL, a UNIQUE index generally permits **multiple NULL values**, because `NULL` represents an unknown or missing value and is not considered equal to another NULL for uniqueness purposes. So the correct picture is:

```text
PRIMARY KEY → no NULL
UNIQUE      → NULL can be allowed, if the column permits it
```

### 🔻 Difference #2: How many can a table have?

A table can have **only one Primary Key constraint**. This is invalid:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    username VARCHAR(50) PRIMARY KEY
);
```

You cannot have `id → Primary Key` **and** `username → Primary Key` as two separate Primary Keys.

But you *can* have as many UNIQUE constraints as you like:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(255) UNIQUE,
    username VARCHAR(50) UNIQUE,
    phone VARCHAR(20) UNIQUE
);
```

```text
Primary Key:
    id

UNIQUE constraints:
    email
    username
    phone
```

```text
1 table
 ├── 1 Primary Key
 └── many UNIQUE constraints
```

This is one of the easiest interview questions there is. 🎯

---

## 🔗 The Correction Hidden in "One"

> *"Wait. Does 'only one Primary Key' mean only one **column**?"*

Here the lecture takes a shortcut: the instructor says to think of the Primary Key as a single column *for now*. The precise truth is subtler:

> ❌ *"A table can have only one Primary Key column."*
> ✅ *"A table can have only one Primary Key **constraint**, which may contain **multiple columns**."*

A Primary Key can be one column:

```sql
PRIMARY KEY (id)
```

or several:

```sql
PRIMARY KEY (student_id, course_id)
```

The second kind is called a **Composite Primary Key**.

### 🎓 Seeing it with your own eyes

> *"When would one column ever fail to be enough?"*

Consider enrollments:

```text
student_id | course_id | grade
-----------|-----------|------
101        | CS101     | A
101        | MA101     | B
102        | CS101     | A
```

Look at each column alone:

* `student_id = 101` appears **twice**. Not unique.
* `course_id = CS101` appears **twice**. Not unique.

But the **combination** `(student_id, course_id)` is unique for every row. So:

```sql
CREATE TABLE enrollments (
    student_id INT,
    course_id VARCHAR(20),
    grade CHAR(1),
    PRIMARY KEY (student_id, course_id)
);
```

That is **one** Primary Key made from **two** columns.

## 🛠️ What the Key Is Actually For

> *"Okay, so how does the Primary Key help in day-to-day queries?"*

Take this table:

```text
id | name  | email
---|-------|-------------
1  | Arun  | a@gmail.com
2  | Ravi  | r@gmail.com
3  | Priya | p@gmail.com
```

To delete Ravi:

```sql
DELETE FROM users
WHERE id = 2;
```

To update Ravi:

```sql
UPDATE users
SET name = 'Ravi Kumar'
WHERE id = 2;
```

To retrieve Ravi:

```sql
SELECT *
FROM users
WHERE id = 2;
```

The Primary Key becomes the **stable identity** that your application and database operations lean on.

## 🤖 Enter AUTO_INCREMENT: Because Humans Forget

> *"What's this AUTO_INCREMENT thing that always shows up next to the Primary Key?"*

Suppose you only have:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY
);
```

Now you must provide every ID by hand:

```sql
INSERT INTO users VALUES (1);
INSERT INTO users VALUES (2);
INSERT INTO users VALUES (3);
```

That's annoying. Humans are perfectly capable of manually assigning integers, and humans are also perfectly capable of forgetting things. Hence automation.

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255)
);
```

Now insert **without** giving an `id`:

```sql
INSERT INTO users (name, email)
VALUES ('Arun', 'arun@gmail.com');
```

MySQL generates the ID itself:

| id | name | email          |
| -: | ---- | -------------- |
|  1 | Arun | arun@gmail.com |

Next:

```sql
INSERT INTO users (name, email)
VALUES ('Ravi', 'ravi@gmail.com');
```

| id | name | email          |
| -: | ---- | -------------- |
|  1 | Arun | arun@gmail.com |
|  2 | Ravi | ravi@gmail.com |

And then `3`, `4`, `5`... So:

```text
PRIMARY KEY
    +
AUTO_INCREMENT
```

is a very common combination for numeric surrogate IDs in MySQL.

---

## 🕳️ The Promise AUTO_INCREMENT Does *Not* Make

> *"Does AUTO_INCREMENT guarantee 1, 2, 3, 4, 5 with no gaps?"*

The lecture simplifies this, and it is tempting to believe:

```text
1
2
3
4
5
6
7
```

will **always** happen without gaps. It is not guaranteed. You can absolutely get:

```text
1
2
4
5
8
```

Reasons include deleted rows, failed or rolled-back inserts, and concurrent transactions. So AUTO_INCREMENT means:

> **MySQL automatically generates increasing numeric values for new rows.**

It does **not** mean:

> *"Every integer will be perfectly consecutive forever."*

> *"Then does AUTO_INCREMENT at least guarantee uniqueness?"*

Careful. When used for a Primary Key, the generated values are intended to provide distinct values for inserted rows. But don't mentally merge the two concepts:

```text
PRIMARY KEY
→ enforces uniqueness of the key

AUTO_INCREMENT
→ automatically generates numeric values
```

They solve **different problems**.

---

## 🤝 Why the Two Always Travel Together

They complement each other:

* **Primary Key says:** *"Every row must have a unique identity."*
* **AUTO_INCREMENT says:** *"I'll generate that numeric identity automatically."*

Together:

```sql
id INT AUTO_INCREMENT PRIMARY KEY
```

means, approximately:

> *"Create an integer column that is the table's unique, non-null identifier, and automatically generate its values for new rows."*

But the reverse also matters. Two more separations to keep straight:

**Primary Key does not have to be INT.** It can be `INT`, `BIGINT`, `CHAR`, `VARCHAR`, `BINARY`, UUID-style values, depending on design:

```sql
CREATE TABLE users (
    user_id VARCHAR(36) PRIMARY KEY
);
```

```text
Primary Key ≠ integer
AUTO_INCREMENT ≠ Primary Key
```

**AUTO_INCREMENT does not define uniqueness by itself.** Imagine:

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT
);
```

`AUTO_INCREMENT` is present here, but `id` is not acting as the table's Primary Key just because that word appears. Keep them conceptually apart:

```text
PRIMARY KEY
↓
constraint
↓
unique + non-null row identifier

AUTO_INCREMENT
↓
automatic value generation
↓
mainly used with integer numeric IDs
```

## 🚀 "What If I Want My IDs to Start at 1000?"

> *"Can AUTO_INCREMENT start from a different number?"*

Yes. The instructor's example is starting at `1000`:

```sql
ALTER TABLE users AUTO_INCREMENT = 1000;
```

If the table currently holds ids `1, 2, 3, ..., 99`, the next generated ID can be `1000`.

### ⚠️ The subtlety the lecture skips

Now suppose the table contains:

```text
id
---
1
2
3
100
```

and you run:

```sql
ALTER TABLE users AUTO_INCREMENT = 50;
```

Do **not** assume the next value becomes 50. MySQL considers the existing data and its AUTO_INCREMENT rules. You cannot simply rewind the counter below the relevant existing values and expect duplicates to be generated.

So the "set it to 1000" example is great for understanding the *purpose*, but don't memorize it as:

> ❌ *"ALTER TABLE always makes the next ID exactly that number."*

That is too simplistic.

---

## ✂️ Can You Cut a Key Loose?

> *"Can a Primary Key be dropped?"*

Yes:

```sql
ALTER TABLE users
DROP PRIMARY KEY;
```

But this is more consequential than dropping an ordinary UNIQUE constraint, because the Primary Key may be *used by other parts of the database*.

### 🔗 The brief cameo of the Foreign Key

Here is where the instructor briefly mentions Foreign Keys. Two tables:

**`users`**

```text
id | name
---|------
1  | Arun
2  | Ravi
```

**`orders`**

```text
order_id | user_id
---------|--------
101      | 1
102      | 2
```

`users.id` may be referenced by `orders.user_id`. The second table is saying:

> *"This order belongs to the user whose ID is 1."*

That is the basic idea of a **Foreign Key** relationship. So if you casually remove or change the Primary Key, relationships may be affected. The exact behavior depends on the foreign-key definitions and indexes involved, but the general lesson holds:

> **Dropping a Primary Key can have wider consequences than dropping a simple UNIQUE constraint.**

> *"And a UNIQUE constraint? Can that be dropped too?"*

Yes. In MySQL you remove a UNIQUE index/constraint with:

```sql
ALTER TABLE users
DROP INDEX email;
```

The exact command depends on the constraint/index name. After removing it, duplicate emails may become possible.

## 📊 The Two Side by Side

| Feature | Primary Key | UNIQUE |
| --- | --- | --- |
| Duplicate values | ❌ Not allowed | ❌ Not allowed |
| NULL | ❌ Not allowed | ✅ Allowed if the column permits it |
| Number per table | One PK constraint | Multiple allowed |
| Main purpose | Identify each row | Enforce uniqueness |
| Can contain multiple columns? | ✅ Yes | ✅ Yes |
| Can be referenced by a FK? | ✅ Commonly | ✅ A referenced UNIQUE key can also be used, depending on DB rules |
| Optional? | Table can technically exist without one | Optional |
| Can be dropped? | ✅ Yes, but potentially disruptive | ✅ Yes |

## 🧱 The Third Correction: "Every Table Must Have a Primary Key"

> *"Is a Primary Key actually required? The instructor made it sound mandatory."*

The instructor says a Primary Key is ideally required, because otherwise you cannot identify records. As **design advice** for many application tables, that is reasonable. Technically, though:

> ❌ *"Every MySQL table must have a Primary Key."*
> ✅ *"MySQL allows tables without one, although a Primary Key is commonly desirable for application tables."*

This is perfectly valid:

```sql
CREATE TABLE test (
    name VARCHAR(100)
);
```

There is no Primary Key, and the table works. Whether it is a *good idea* is a separate question. For many application tables a proper Primary Key is strongly desirable, because it gives the table a stable row identity and supports relationships and data manipulation more cleanly.

## 🧭 Why Not Make Every Unique Column a Primary Key?

> *"If username, email and phone are all unique, why aren't they all Primary Keys?"*

Because the database is asking two different questions:

* **Primary Key:** *"What is the main identity of this row?"*
* **UNIQUE:** *"What values must not occur more than once?"*

Look at one user:

```text
id = 101
email = abc@gmail.com
username = dharan123
phone = 9876543210
```

All four may be unique. But you generally designate **one** of them as the row's *primary identity*. The others simply carry uniqueness requirements.

A very realistic table therefore looks like this:

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) UNIQUE,
    email VARCHAR(255) UNIQUE,
    phone VARCHAR(20) UNIQUE,
    name VARCHAR(100)
);
```

```text
id
↓
Primary Key
↓
Main identity of the user

username, email, phone
↓
UNIQUE
↓
These values cannot be duplicated
```

This is a very common pattern.

## 🧪 Watching It All Happen, From Start to Finish

Let's build the table the instructor is describing:

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) UNIQUE,
    email VARCHAR(255) UNIQUE,
    name VARCHAR(100),
    salary DECIMAL(10,2)
);
```

First insert:

```sql
INSERT INTO users (username, email, name, salary)
VALUES ('dharan01', 'dharan@gmail.com', 'Dharan', 50000);
```

MySQL generates `id = 1`. Second insert:

```sql
INSERT INTO users (username, email, name, salary)
VALUES ('ravi01', 'ravi@gmail.com', 'Ravi', 50000);
```

MySQL generates `id = 2`.

| id | username | email            | name   | salary |
| -: | -------- | ---------------- | ------ | -----: |
|  1 | dharan01 | dharan@gmail.com | Dharan |  50000 |
|  2 | ravi01   | ravi@gmail.com   | Ravi   |  50000 |

Notice something: **both users have `salary = 50000`**. That is perfectly fine, because salary isn't required to be unique. But `id`, `username` and `email` must be.

### 💥 What if I insert a duplicate Primary Key?

```sql
INSERT INTO users
(id, username, email, name)
VALUES (1, 'abc', 'abc@gmail.com', 'Someone');
```

But `id = 1` already exists. MySQL rejects it:

```text
Existing:
id = 1

New:
id = 1

→ duplicate Primary Key
→ INSERT fails
```

### 💥 What if I insert a duplicate UNIQUE value?

Suppose `email = dharan@gmail.com` already exists:

```sql
INSERT INTO users (username, email, name)
VALUES ('another', 'dharan@gmail.com', 'Another User');
```

This fails too, because `email` has a UNIQUE constraint. Notice the distinction:

```text
id
→ Primary Key
→ row identity

email
→ UNIQUE
→ duplicate prevention
```

Both prevent duplicates. Their **semantic roles** differ.

## 🩹 "My Table Already Exists. Can I Add These Later?"

> *"The lecture only shows creation syntax. What about a table that's already built?"*

Suppose the table exists like this:

```sql
CREATE TABLE users (
    id INT,
    name VARCHAR(100),
    email VARCHAR(255)
);
```

You can add a Primary Key:

```sql
ALTER TABLE users
ADD PRIMARY KEY (id);
```

But this **fails** if existing rows contain `NULL` or duplicate values in `id`. Before adding a Primary Key, the existing data must already satisfy the Primary Key requirements.

And to add AUTO_INCREMENT to an existing column in MySQL, you can modify the column definition:

```sql
ALTER TABLE users
MODIFY id INT NOT NULL AUTO_INCREMENT;
```

provided the existing schema, data and indexing requirements are appropriate. Often the final design is:

```sql
id INT NOT NULL AUTO_INCREMENT PRIMARY KEY
```

## 🧩 Seeing the Whole Machine at Once

> *"Can I see how all of this fits together?"*

```text
                   USERS TABLE
┌────────────────────────────────────────┐
│ id         ← Primary Key               │
│ username   ← UNIQUE                    │
│ email      ← UNIQUE                    │
│ name                                   │
│ salary                                 │
└────────────────────────────────────────┘

id:
  1
  2
  3
  4
  ...

AUTO_INCREMENT
       ↓
automatically generates IDs

PRIMARY KEY
       ↓
ensures each ID is unique and non-NULL

UNIQUE
       ↓
prevents duplicate username/email values
```

And the mental model:

```text
                    PRIMARY KEY
                         │
             ┌───────────┴───────────┐
             │                       │
        UNIQUE values           NOT NULL
             │
             ▼
      uniquely identifies
          each row


                 AUTO_INCREMENT
                       │
                       ▼
          automatically generates
              numeric IDs
```

Now the payoff. Don't memorize this as one magical database spell:

```sql
id INT AUTO_INCREMENT PRIMARY KEY
```

That single line is doing **three different jobs**:

```text
INT
↓
What kind of data is stored?
Integer


AUTO_INCREMENT
↓
How is the value generated?
Automatically by MySQL


PRIMARY KEY
↓
What role does the column play?
Unique identity of the row
```

Read as a sentence:

> *"`id` stores integers, MySQL automatically generates its values for new rows, and `id` is the table's primary identifier."*

Once you see the three jobs, SQL becomes much less like memorizing incantations and much more like understanding a system. 🧠

## 🧪 Sanity Check: Could You Survive the Interview?

Cover the answers and try each question out loud.

**"What is a Primary Key?"**
A constraint that uniquely identifies each row in a table. It cannot contain duplicate or NULL values, and a table can have only one Primary Key constraint.

**"Can a table have multiple Primary Keys?"**
**No.** One table, one Primary Key constraint. But that key can be **composite**, meaning it can contain multiple columns.

**"Can a table have multiple UNIQUE constraints?"**
**Yes.** For example `email`, `username` and `phone` can each be UNIQUE.

**"Difference between Primary Key and UNIQUE?"**

```text
Primary Key → main row identity
UNIQUE      → uniqueness requirement

Primary Key → no NULL
UNIQUE      → NULL can be allowed if the column is nullable

Primary Key → one per table
UNIQUE      → multiple per table
```

**"What is AUTO_INCREMENT?"**
It automatically generates increasing numeric values for a column when new rows are inserted.

**"Is AUTO_INCREMENT the same as Primary Key?"**
**No.**

```text
AUTO_INCREMENT = automatic number generation
PRIMARY KEY    = uniqueness + row identity
```

They are commonly used together.

**"Can a Primary Key be dropped?"**
**Yes**, but it can have broader consequences, particularly when relationships depend on it.

### 🔁 The four myths, corrected

```text
❌ "A table can have only one Primary Key column."
✅ "A table can have only one Primary Key constraint, which may contain multiple columns."

❌ "AUTO_INCREMENT always gives 1,2,3,4,5 with no gaps."
✅ "AUTO_INCREMENT generates increasing values, but gaps can occur."

❌ "Every MySQL table must have a Primary Key."
✅ "MySQL allows tables without one, although a Primary Key is commonly desirable for application tables."

❌ "Unique allows only one NULL."
✅ "In MySQL, a nullable UNIQUE column can generally contain multiple NULL values."
```

## 🔎 Checked Against the Documentation

Some claims in these notes were checked against MySQL documentation. Here is exactly what could and could not be confirmed:

**Confirmed:**

* A UNIQUE index permits multiple NULL values for columns that can contain NULL. Source: [MySQL 8.4 Reference Manual, CREATE INDEX](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)
* `ALTER TABLE ... AUTO_INCREMENT = N` can only change the counter to a value larger than the current maximum (this matches the `= 50` versus max `100` example above). Source: [MySQL 8.0 Reference Manual, AUTO_INCREMENT Handling in InnoDB](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-auto-increment-handling.html)
* Gaps: if a transaction that generated auto-increment values rolls back, those values are lost and not reused, so gaps can appear. The page I retrieved for this was the [MySQL 5.7 version of that InnoDB page](https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/innodb-auto-increment-handling.html); I did not open the 8.4 equivalent.
* Extra nuance not in the lecture: the MySQL 8.4 manual says each InnoDB table has a primary key whether you request one or not, so a table "without a Primary Key" still gets an internal one in InnoDB. Source: [MySQL 8.4 Reference Manual, Optimizing InnoDB Queries](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/optimizing-innodb-queries.html)

**Not confirmed from MySQL manual text in what I retrieved** (these come from the lecture notes above, and general SQL/MariaDB sources state the first two): one Primary Key per table, Primary Key values never NULL, the consequences of `DROP PRIMARY KEY` when foreign keys exist, the exact failure conditions of `ADD PRIMARY KEY`, the `MODIFY ... AUTO_INCREMENT` syntax, and `DROP INDEX email`. Verify these against your own MySQL version before relying on them.
