# 🧺 Making Piles of Rows: `GROUP BY`, `HAVING` & `WITH ROLLUP` in MySQL

> *"`WHERE` filters rows. `GROUP BY` makes piles. `HAVING` filters piles. `ROLLUP` adds up the piles."*

You have a `users` table. Someone asks:

> **"What is the average salary for each gender?"**

Not one overall average. **One answer for Male, and one for Female.**

You could run `AVG(salary)` once per gender and copy the numbers by hand. But the instructor's tool does the sorting and the maths in a single query:

- 🧺 **`GROUP BY`** sorts rows into piles that share a value.
- 🔍 **`HAVING`** keeps only the piles you care about.
- ➕ **`WITH ROLLUP`** adds the subtotal and grand-total rows on the end.

The three questions this chapter answers:

| Question | Short answer |
| -------- | ------------ |
| **What is it?** | A way to collapse rows that share a value into groups, then calculate one result per group |
| **Why does it exist?** | So the database can answer "per gender", "per referrer", "per department" questions in one query |
| **How does it work?** | Filter rows → build groups → calculate aggregates → filter groups (details below) |

## 🧺 Step 1: making piles with `GROUP BY`

`GROUP BY` combines rows that have the **same value in one or more columns** into groups.

```sql
SELECT gender, AVG(salary)
FROM users
GROUP BY gender;
```

Picture what MySQL does:

```text
Users
  │
  ├── Male pile   (13 rows)
  │     ├── 60000
  │     ├── 70000
  │     ├── 59000
  │     └── ...
  │
  └── Female pile (11 rows)
        ├── 65000
        ├── 55000
        └── ...
```

Then `AVG()` runs **inside each pile**. Real output:

| gender | AVG(salary) |
| ------ | ----------: |
| Male   | 63000.0000  |
| Female | 60000.0000  |

Two details worth noticing:

- `AVG()` returns a decimal, so MySQL prints `63000.0000`, not `63000`.
- The order of the rows is not something to rely on. In my runs, a plain `GROUP BY` listed Male first, while the `ROLLUP` queries later listed Female first. If the order matters, add an `ORDER BY`. *(This is my observation from test runs, not a manual quote.)*

The general pattern:

```sql
SELECT group_column, AGGREGATE_FUNCTION(column)
FROM table
GROUP BY group_column;
```

## 🧮 The five aggregate functions

The instructor stresses that `GROUP BY` is typically used with **aggregate functions**. These are the five to know:

```text
COUNT()   SUM()   AVG()   MIN()   MAX()
```

Here they all are at once, per gender:

```sql
SELECT gender,
       COUNT(*)    AS cnt,
       SUM(salary) AS total,
       AVG(salary) AS avg_s,
       MIN(salary) AS mn,
       MAX(salary) AS mx
FROM users
GROUP BY gender;
```

| gender | cnt |  total | avg_s      |    mn |    mx |
| ------ | --: | -----: | ---------- | ----: | ----: |
| Male   |  13 | 819000 | 63000.0000 | 58000 | 70000 |
| Female |  11 | 660000 | 60000.0000 | 55000 | 65000 |

| Function | What it does | Example meaning |
| -------- | ------------ | --------------- |
| `COUNT(*)` | Counts rows in each group | 11 female users, 13 male users |
| `SUM(x)` | Adds the values | Total salary bill per gender |
| `AVG(x)` | Averages the values | Average salary per gender |
| `MIN(x)` | Smallest value | Lowest salary per gender |
| `MAX(x)` | Largest value | Highest salary per gender |

> 🔑 **`GROUP BY` creates the groups. The aggregate functions calculate something about each group.**

## 🏷️ Naming the result columns

The calculated column is called `AVG(salary)` by default, which is ugly. Give it a name with `AS`:

```sql
SELECT gender,
       AVG(salary) AS 'Average Salary'
FROM users
GROUP BY gender;
```

| gender | Average Salary |
| ------ | -------------: |
| Male   |     63000.0000 |
| Female |     60000.0000 |

You can also write `AS avg_salary` (no quotes, no spaces) or alias the group column itself: `gender AS Gender`. The alias only changes **how the result is displayed**. It does not create a new column in the table.

## 🚫 The question that trips everyone: "Why can't I also select `salary`?"

> 💭 **"What's wrong with adding `salary` next to `AVG(salary)`?"**

```sql
SELECT gender, salary, AVG(salary)
FROM users
GROUP BY gender;
```

Real result on a default MySQL 8.0 install:

> ❌ **ERROR 1055: Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'ch.users.salary' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by**

Why? After grouping, MySQL must produce **one row per gender**. But the Male pile contains many salaries:

```text
Male
├── salary = 60000
├── salary = 70000
├── salary = 59000
└── ...      ← which single salary should the Male row show?
```

There is no obvious answer. `AVG(salary)` is fine because it combines the whole pile into one value.

So a grouped query normally contains:

- the column(s) you **group by**, and
- **aggregate calculations** over the other columns.

MySQL's manual adds the background: with the `ONLY_FULL_GROUP_BY` mode (on by default), MySQL rejects queries that mention non-grouped, non-aggregated columns. If that mode is turned off, the server picks *any* value from each group, and the value is nondeterministic, "probably not what you want." If you truly don't care which value you get, `ANY_VALUE()` says so explicitly.

## 🔀 You can group by anything

Gender is only one choice. Rows with the same value in the grouping column land in the same pile:

```sql
GROUP BY referred_by_id     -- one pile per referrer
GROUP BY department          -- (if your table had one)
GROUP BY city
```

Here is the first surprise. Group by `referred_by_id` and count:

```sql
SELECT referred_by_id, COUNT(*) AS total_referred
FROM users
GROUP BY referred_by_id;
```

| referred_by_id | total_referred |
| -------------: | -------------: |
|           NULL |             10 |
|              1 |              8 |
|              5 |              3 |
|              7 |              2 |
|              9 |              1 |

> 💭 **"What is that `NULL` pile of 10?"**

Those are the users nobody referred. `GROUP BY` treats all the `NULL`s as one group. That is exactly why the lecture's referral query adds a `WHERE referred_by_id IS NOT NULL`, coming up shortly.

## ⚔️ `WHERE` vs `HAVING`: the main idea of the lesson

Say you want:

> **"Show only the gender groups whose average salary is greater than ₹61,000."**

The tempting attempt:

```sql
SELECT gender, AVG(salary)
FROM users
WHERE AVG(salary) > 61000
GROUP BY gender;
```

> ❌ **ERROR 1111: Invalid use of group function**

Why? Because of **when** each clause runs:

- `WHERE` filters **individual rows**, *before* any grouping happens.
- `AVG(salary)` is a value that only exists **after** the groups are built.

At the moment `WHERE` runs, the averages do not exist yet.

So for group-level filtering, use **`HAVING`**:

```sql
SELECT gender,
       AVG(salary) AS avg_salary
FROM users
GROUP BY gender
HAVING AVG(salary) > 61000;
```

| gender | avg_salary |
| ------ | ---------: |
| Male   | 63000.0000 |

Female (average 60000) was dropped. The **piles** were filtered, not the rows.

```text
Rows
  ↓
WHERE          ← "Which rows may enter?"
  ↓
Filtered rows
  ↓
GROUP BY       ← "How do we pile them up?"
  ↓
Groups + aggregate values
  ↓
HAVING         ← "Which piles survive?"
  ↓
Filtered groups
```

### The comparison to memorize

| `WHERE` | `HAVING` |
| ------- | -------- |
| Filters **rows** | Filters **groups** |
| Runs **before** grouping | Runs **after** grouping |
| Works on individual row values | Typically works on aggregate values |
| Sits **before** `GROUP BY` | Sits **after** `GROUP BY` |

```sql
-- Row-level filtering
WHERE salary > 60000

-- Group-level filtering
HAVING AVG(salary) > 60000
```

### A practical rule from the manual

MySQL's manual gives this advice: **don't use `HAVING` for things that belong in `WHERE`.** If a condition can be checked on a single row (like `salary > 0`), put it in `WHERE`, so rows are removed *before* the grouping work.

### A convenience (and a gotcha)

MySQL lets `HAVING` refer to a **select alias**, so this also works (I ran it):

```sql
SELECT gender, AVG(salary) AS avg_salary
FROM users
GROUP BY gender
HAVING avg_salary > 61000;
```

The manual describes this as MySQL allowing `GROUP BY` and `HAVING` to refer to select-list values. The `HAVING AVG(salary) > 61000` form is the more portable one, so it is the one to get used to.

## 🤝 Using `WHERE` and `HAVING` together

They are not rivals. One query can use both:

```sql
SELECT gender,
       AVG(salary) AS avg_salary,
       COUNT(*)    AS user_count
FROM users
WHERE id <= 20
GROUP BY gender
HAVING AVG(salary) > 61000;
```

*(The lecture used `id < 5000` on a large table. I scaled it down to `id <= 20` to fit our 24 rows.)*

Follow it step by step:

**Step 1: `WHERE id <= 20`.** Removes users 21 to 24 (all four are male: Nikhil, Varun, Manish, Dev).

**Step 2: `GROUP BY gender`.** Piles: Male (9 rows left) and Female (11 rows).

**Step 3: aggregates.** Without `HAVING`, the output would be:

| gender | avg_salary | user_count |
| ------ | ---------: | ---------: |
| Male   | 62777.7778 |          9 |
| Female | 60000.0000 |         11 |

**Step 4: `HAVING AVG(salary) > 61000`.** Female's 60000 fails.

| gender | avg_salary | user_count |
| ------ | ---------: | ---------: |
| Male   | 62777.7778 |          9 |

## 🧷 `HAVING` with `AND`, `OR`, and `COUNT()`

`HAVING` accepts multiple conditions, and it can filter on **counts**, something `WHERE` cannot do, because a count doesn't exist until after grouping.

```sql
-- Keep groups with more than 12 users
SELECT gender, COUNT(*) AS user_count
FROM users
GROUP BY gender
HAVING COUNT(*) > 12;
```

| gender | user_count |
| ------ | ---------: |
| Male   |         13 |

**`AND`** (both conditions must hold):

```sql
HAVING AVG(salary) > 61000
   AND COUNT(*) < 14
```

Male passes both (63000, 13 users). Female fails the average. Result: **Male only.**

**`OR`** (either condition is enough):

```sql
HAVING AVG(salary) > 61000
    OR COUNT(*) > 10
```

Male passes both; Female fails the average but passes the count (11 > 10). Result: **both groups.**

*(The lecture used thresholds like `COUNT(*) < 4000` for a much larger table. The idea is identical; I scaled the numbers to our data.)*

## 🔗 A practical case: who referred more than one person?

This is the instructor's real-world example. The question:

> **"Which referrers referred more than one user?"**

```sql
SELECT referred_by_id,
       COUNT(*) AS total_referred
FROM users
WHERE referred_by_id IS NOT NULL
GROUP BY referred_by_id
HAVING COUNT(*) > 1;
```

Take it apart:

| Clause | Job |
| ------ | --- |
| `WHERE referred_by_id IS NOT NULL` | Ignore users nobody referred (removes that pile of 10) |
| `GROUP BY referred_by_id` | One pile per referrer |
| `COUNT(*)` | How many users are in each pile |
| `HAVING COUNT(*) > 1` | Keep referrers with more than one referral |

Real output:

| referred_by_id | total_referred |
| -------------: | -------------: |
|              1 |              8 |
|              5 |              3 |
|              7 |              2 |

```text
User 1 → referred 8 users
User 5 → referred 3 users
User 7 → referred 2 users
```

Look at what `HAVING` removed: referrer **9** referred exactly one user, so that pile was dropped. And user 1 is **Aarav**, matching what the instructor found when he looked up `id = 1` in his dataset.

*(Connection to your earlier chapters: `referred_by_id` is the same self-referencing column from the self-join lesson. There you turned IDs into names with a join. Here you count how often each ID appears.)*

## 🗺️ The order things really happen in

This is the most useful thing to remember. The logical flow:

```text
FROM
  ↓
WHERE           ← filter individual rows
  ↓
GROUP BY        ← create groups
  ↓
Aggregates      ← COUNT, SUM, AVG, MIN, MAX
  ↓
HAVING          ← filter groups
  ↓
SELECT
  ↓
ORDER BY
  ↓
LIMIT
```

And the **written** order in your SQL must follow the manual's syntax. The manual states that clauses must appear in exactly the order shown in the `SELECT` syntax; for example, a `HAVING` must come after `GROUP BY` and before `ORDER BY`.

This whole chapter in one query:

```sql
SELECT gender,
       AVG(salary) AS avg_salary,
       COUNT(*)    AS user_count
FROM users
WHERE id <= 20
GROUP BY gender
HAVING AVG(salary) > 61000;
```

> ⚠️ **Small honesty note:** the "`SELECT` comes after `HAVING`" picture is a **mental model**. MySQL bends it slightly: as you saw, it lets `HAVING` use an alias defined in the select list.

## ➕ `WITH ROLLUP`: subtotals and grand totals

The last topic. `WITH ROLLUP` is an extension of `GROUP BY` that adds **summary rows** on the end.

```sql
SELECT gender,
       AVG(salary) AS avg_salary,
       COUNT(*)    AS user_count
FROM users
GROUP BY gender WITH ROLLUP;
```

Real output:

| gender     | avg_salary | user_count |
| ---------- | ---------: | ---------: |
| Female     | 60000.0000 |         11 |
| Male       | 63000.0000 |         13 |
| **NULL**   | **61625.0000** |     **24** |

That last row, with `NULL` in the `gender` column, is the **grand total**. The manual describes it as a "super-aggregate" row. `NULL` here means "all genders."

### The counts and sums simply add up

```text
COUNT:  11 + 13 = 24
SUM:    660000 + 819000 = 1479000
```

Run `SUM(salary)` with `WITH ROLLUP` and the last row is exactly `1479000`.

### ⚠️ But the average is different

The instructor specifically stresses this. The grand-total average is **not** the average of the two group averages.

```text
Wrong:  (60000 + 63000) / 2 = 61500      ← the "average of averages"
Right:  61625                             ← what MySQL returns
```

I ran the wrong calculation as a query to be sure: averaging the two group averages gives `61500`, while the rollup row says `61625`. Why? The groups are different sizes. The correct calculation is a **weighted average**:

```text
(60000 × 11) + (63000 × 13)     660000 + 819000
───────────────────────────  =  ───────────────  =  1479000 / 24  =  61625
          11 + 13                      24
```

Male has 13 people and Female has 11, so Male pulls the overall average up a little more.

### Why "weighted"? An extreme example

```text
Group A:  average 60,000,  100 people
Group B:  average 80,000,    2 people

Simple average of averages:  (60000 + 80000) / 2  =  70,000     ← treats them as equal
Weighted average:  (60000×100 + 80000×2) / 102    ≈  60,392     ← Group A dominates, as it should
```

Group B has only two people, so it barely moves the overall figure.

### What is it for?

The instructor's summary: **subtotals and grand totals.** It is made for reports:

```text
Department       Total Salary
--------------------------------
Engineering        ₹500,000
Marketing          ₹300,000
HR                 ₹200,000
--------------------------------
Grand Total      ₹1,000,000      ← the ROLLUP row
```

### 🚩 How do I tell a real `NULL` from a total row?

> 💭 **"What if some user genuinely has a `NULL` gender? Won't that look like the total?"**

Yes, and the manual warns about exactly this: from the outside, you cannot tell a `NULL` group from a super-aggregate row just by looking. The fix is the `GROUPING()` function, which returns `1` for a rollup row and `0` otherwise:

```sql
SELECT gender,
       AVG(salary) AS avg_salary,
       COUNT(*)    AS user_count,
       GROUPING(gender) AS is_total
FROM users
GROUP BY gender WITH ROLLUP;
```

| gender | avg_salary | user_count | is_total |
| ------ | ---------: | ---------: | -------: |
| Female | 60000.0000 |         11 |        0 |
| Male   | 63000.0000 |         13 |        0 |
| NULL   | 61625.0000 |         24 |        1 |

*(`GROUPING()` is beyond the lecture; it comes from the MySQL manual and I ran it.)*

## 🚧 The syntax trap in the lecture's final example

The notes end with a "complete example" written like this:

```sql
GROUP BY gender
HAVING AVG(salary) > 61000
WITH ROLLUP;          -- ❌ wrong position
```

I ran it:

> ❌ **ERROR 1064: You have an error in your SQL syntax... near 'WITH ROLLUP'**

The manual's `SELECT` syntax shows `WITH ROLLUP` as **part of the `GROUP BY` clause**, so it must come **before** `HAVING`:

```sql
SELECT gender,
       AVG(salary) AS avg_salary,
       COUNT(*)    AS user_count
FROM users
WHERE referred_by_id IS NOT NULL
GROUP BY gender WITH ROLLUP     -- ✅ ROLLUP belongs to GROUP BY
HAVING AVG(salary) > 61000;
```

Real output:

| gender | avg_salary | user_count |
| ------ | ---------: | ---------: |
| Male   | 65200.0000 |          5 |
| NULL   | 61857.1429 |         14 |

Trace it:

```text
users
  │ WHERE referred_by_id IS NOT NULL
  ↓
14 referred users  (9 female, 5 male)
  │ GROUP BY gender WITH ROLLUP
  ↓
Female: 60000 (9)   Male: 65200 (5)   Total: 61857.14 (14)
  │ HAVING AVG(salary) > 61000
  ↓
Female dropped (60000 fails). Male and Total remain.
```

Notice something subtle: the surviving **Total row still counts 14 users**, including the 9 females whose own row `HAVING` hid. The rollup row is calculated from all the filtered rows first; `HAVING` then decides which output rows to show. *(This is what my test run showed. The manual doesn't spell it out in these words, only that `HAVING` can see and test the super-aggregate rows.)*

## 🧠 The three concepts together

### `GROUP BY`: creates groups

```sql
GROUP BY gender
```

> "Put users with the same gender together."

### `HAVING`: filters groups

```sql
HAVING AVG(salary) > 61000
```

> "After creating the groups, keep only those whose average salary exceeds 61,000."

### `WITH ROLLUP`: adds summary rows

```sql
GROUP BY gender WITH ROLLUP
```

> "Give me the individual group results **plus** a higher-level summary."

### The reference table

| Concept | Purpose | Example |
| ------- | ------- | ------- |
| `GROUP BY` | Creates groups | `GROUP BY gender` |
| `COUNT()` | Counts rows | `COUNT(*)` |
| `SUM()` | Adds values | `SUM(salary)` |
| `AVG()` | Calculates the average | `AVG(salary)` |
| `MIN()` | Finds the minimum | `MIN(salary)` |
| `MAX()` | Finds the maximum | `MAX(salary)` |
| `WHERE` | Filters rows | `WHERE id <= 20` |
| `HAVING` | Filters groups | `HAVING COUNT(*) > 1` |
| `WITH ROLLUP` | Adds summary/subtotal rows | `GROUP BY gender WITH ROLLUP` |

### The golden rule

```text
WHERE     → filter ROWS
GROUP BY  → create GROUPS
HAVING    → filter GROUPS
ROLLUP    → add SUMMARY
```

## ✅ Sanity Check: can you predict these?

Use the 24-row table. Answer in your head first.

**1. Why does this fail, and what error do you get?**

```sql
SELECT gender, AVG(salary) FROM users WHERE AVG(salary) > 61000 GROUP BY gender;
```

<details>
<summary>Answer</summary>

`WHERE` runs before grouping, when no averages exist yet. MySQL raises **ERROR 1111: Invalid use of group function**. Use `HAVING AVG(salary) > 61000` instead.

</details>

**2. Why does `SELECT gender, salary, AVG(salary) FROM users GROUP BY gender;` fail on a default MySQL 8.0?**

<details>
<summary>Answer</summary>

**ERROR 1055.** `salary` is neither grouped nor aggregated, and each gender pile holds many salaries. With `ONLY_FULL_GROUP_BY` (on by default), MySQL refuses. Either aggregate it (`MAX(salary)`), add it to `GROUP BY`, or use `ANY_VALUE(salary)` if any value is acceptable.

</details>

**3. What does this return?**

```sql
SELECT gender, AVG(salary), COUNT(*) FROM users
GROUP BY gender
HAVING AVG(salary) > 61000 AND COUNT(*) < 12;
```

<details>
<summary>Answer</summary>

**No rows.** Male passes the average (63000) but fails the count (13 is not < 12). Female passes the count (11 < 12) but fails the average (60000). Neither pile meets both conditions.

</details>

**4. In the referral query, why is referrer 9 missing from the output?**

<details>
<summary>Answer</summary>

Referrer 9 referred exactly **one** user, and `HAVING COUNT(*) > 1` removes piles of size 1.

</details>

**5. If you dropped `WHERE referred_by_id IS NOT NULL` from the referral query (keeping `HAVING COUNT(*) > 1`), what extra row appears?**

<details>
<summary>Answer</summary>

A `NULL` pile with **10** users, the ones nobody referred. `GROUP BY` puts all `NULL`s into one group, and 10 is greater than 1, so it survives `HAVING`. (I confirmed the 10-row `NULL` pile in a run of the ungrouped-by-filter version; the `HAVING` consequence follows directly.)

</details>

**6. The rollup row shows an average of 61625. Why isn't it 61500?**

<details>
<summary>Answer</summary>

61500 is the plain average of the two group averages, which ignores that Male has 13 users and Female has 11. The correct overall average is **weighted**: (60000×11 + 63000×13) / 24 = 61625.

</details>

**7. Where does `WITH ROLLUP` go relative to `HAVING`?**

<details>
<summary>Answer</summary>

**Before it.** `WITH ROLLUP` is part of the `GROUP BY` clause. Putting it after `HAVING` gives ERROR 1064 (a syntax error).

</details>

**8. 🧪 Stretch question (beyond the lecture): how do you hide the grand-total row from a `WITH ROLLUP` result, keeping only the group rows?**

<details>
<summary>Answer</summary>

Filter on `GROUPING()` in `HAVING`:

```sql
SELECT gender, AVG(salary), COUNT(*)
FROM users
GROUP BY gender WITH ROLLUP
HAVING GROUPING(gender) = 0;
```

I ran this: it returns just the Female and Male rows. (The manual documents that `GROUPING()` can be used in the `HAVING` clause.)

</details>

## 💬 Final Takeaway

> **"`WHERE` decides which rows enter the piles, `GROUP BY` builds the piles, `HAVING` decides which piles stay, and `WITH ROLLUP` totals them up. When you total averages, weigh them by how many rows stand behind each one."**
