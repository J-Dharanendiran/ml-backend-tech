> "A database without a table is just an empty room. A table without structure is just a pile of boxes. Structure is what turns a room into something you can actually live in."

You already know how to build the room. You created a database, and you told MySQL which room to stand in:

```sql
USE starter_sql;
```

That single line means exactly what it looks like it means — *"use the `starter_sql` database for whatever I say next."* No ceremony, no hidden behavior. Just a pointer.

But **what do you actually build inside that room?**

That question is where this chapter lives.

---

## 🗣️ "Issue a query" — what does that even mean?

Every time you hear the instruction *"issue a query,"* it's not some mysterious ritual. It collapses into three plain steps:

1. Write the SQL syntax in the query editor.
2. Click execute.
3. MySQL runs it.

That's it. *"Issue a query" = write SQL, then run it.* Everything downstream in this chapter is just different flavors of that same act.

---

## 🏗️ The chain that gets you to data

Before a single row exists, this is the chain you're standing on:

```text
MySQL
  ↓
Database
  ↓
Tables
  ↓
Rows + Columns
  ↓
Data
```

You've already walked the first two steps. Now it's time to build the third: a **table**.

```sql
CREATE TABLE users (
    ...
);
```

Read that literally and it already tells you everything: *"Create a table called `users`, and here's what goes inside it."* The instructor's warning is worth repeating here — this syntax *looks* intimidating the first time you see it, but it isn't. It's a shape you'll recognize instantly within a month of typing it.

---

## 🧩 What does "defining a table" actually mean?

When you create a table, you're not just naming it. You're answering six quiet questions about every single column:

- What columns exist?
- What *type* of data can each one hold?
- What data is **allowed**?
- What data is **forbidden**?
- How long can the data be?
- What extra rules must the data obey?

Here's the shape of the table this chapter builds:

```text
users
│
├── id
├── name
├── email
├── gender
├── date_of_birth
└── created_at
```

And here's the full query, all six columns wired up with data types and rules:

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    gender ENUM('male', 'female', 'other'),
    date_of_birth DATE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

*You might be looking at that and wondering — where do I even start reading this?*

Start with the pattern that repeats six times:

> **column_name → data_type → optional constraints**

Once you see that rhythm, the whole block stops being a wall of syntax and starts being six short sentences.

---

## 🔍 Walking through every column, one promise at a time

### `id` — the column that names itself

```sql
id INT AUTO_INCREMENT PRIMARY KEY
```

- **`INT`** — a whole-number data type. `1`, `2`, `3`, `4`, `5`. Nothing fractional, nothing textual.
- **`AUTO_INCREMENT`** — you never hand-assign this number. Insert a new row, and MySQL quietly bumps the counter for you: `1`, `2`, `3`, `4`, `5`, without you lifting a finger.
- **`PRIMARY KEY`** — the deeper mechanics come later, but for now hold onto this: *`id` is the row's primary identifier.* Every row needs one thing that says "this is unambiguously me."

### `name` — the column that refuses to be empty

```sql
name VARCHAR(100) NOT NULL
```

**`VARCHAR(100)`** stores variable-length text, capped at a maximum of 100 characters. It doesn't reserve 100 characters of space for a name like "Al" — it just won't let a name grow past 100.

**`NOT NULL`** is your first taste of a **constraint** — a rule about the data, not a description of its type. It says: *this value cannot be left blank.* A user without a name isn't a valid user.

### `email` — the column that refuses to repeat

```sql
email VARCHAR(100) UNIQUE NOT NULL
```

Same `VARCHAR(100)` shape, same `NOT NULL` requirement — but now there's a new constraint: **`UNIQUE`**.

*Why does that matter?* Picture an authentication system. If `harry@example.com` is already sitting in one row, `UNIQUE` makes it structurally impossible for a second row to claim that same email. Not "discouraged" — **impossible**. The database itself refuses the duplicate before your application code ever has to check.

### `gender` — the column with a guest list

```sql
gender ENUM('male', 'female', 'other')
```

**`ENUM`** restricts a column to a predefined set of values — here, only `male`, `female`, or `other` get in. Anything else is turned away at the door. The deeper mechanics of `ENUM` are for a later chapter, but the concept to hold onto now is simple: *a column's data type determines what it will and won't accept.*

### `date_of_birth` — the column that speaks in calendar terms

```sql
date_of_birth DATE
```

**`DATE`** is exactly what it says — a data type built for values like `2000-05-15`. No constraint attached here, just a type doing its one job.

### `created_at` — the column that remembers when

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

**`TIMESTAMP`** is a date-and-time type. **`DEFAULT CURRENT_TIMESTAMP`** is a new kind of promise: *if nobody supplies a value, fill it in yourself — with the current moment.* Insert a row and say nothing about `created_at`, and MySQL silently stamps it with "now."

## ⚖️ Data type vs. constraint — the distinction that organizes everything

Here's the split worth carving into memory:

```text
Column
  │
  ├── Data type
  │     └── What kind of data?
  │
  └── Constraints
        └── What rules apply?
```

| Data type (the *what*) | Constraint (the *rule*) |
|---|---|
| `INT`, `VARCHAR(100)`, `DATE`, `TIMESTAMP`, `ENUM(...)` | `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `AUTO_INCREMENT`, `DEFAULT` |

A data type answers *"what shape is this data?"* A constraint answers *"what is this data not allowed to do?"* Every column in `users` is really just one type paired with zero or more rules.

---

## 🧠 Do you need to memorize all of this?

*"Yes and no,"* is the honest answer.

You **should** eventually know, without thinking, that creating a table starts with:

```sql
CREATE TABLE table_name (
    ...
);
```

and that `CREATE TABLE users (...)` reads plainly as *"create a table named `users`."*

But you are **not** supposed to memorize every constraint keyword on day one. Regular use does the memorizing for you — the instructor's honest promise is that after a month or two of writing SQL regularly, these patterns stop needing conscious recall entirely.

> Humans invented computers to store information, and then decided they also needed to memorize the instructions for storing information. Repetition is what quietly fixes that particular design flaw.

## ▶️ Running the query — and reading "0 rows affected" correctly

Before execution:

```text
starter_sql
└── no tables
```

After execution:

```text
starter_sql
└── users
```

And the client reports:

```text
0 rows affected
```

*Wait — did that fail?*

No. Read it literally: it's telling you about **rows**, not tables. `CREATE TABLE` builds structure; it doesn't insert data. Zero rows were touched because zero rows were ever part of the operation. The table exists — the message is just precise about what it *didn't* do.

---

## 🔎 Proving the table exists: `SELECT`

```sql
SELECT * FROM users;
```

Break this into its two halves and it stops being cryptic:

- **`SELECT *`** — the `*` is a wildcard meaning *"all columns."* Nothing excluded.
- **`FROM users`** — *"pull it from the `users` table."*

Together: **"Select all columns from the `users` table."**

Run it right after creation, with zero rows inserted, and you won't see any user data — but you *will* see the column structure itself: `id | name | email | gender | date_of_birth | created_at`. That's your confirmation. The table is real, and it has the shape you asked for.

This exact query — `SELECT * FROM table_name;` — is one you'll type more than almost any other line of SQL you'll ever write. It's worth making it feel like second nature now.

*But what if you don't want every column?*

```sql
SELECT id, email
FROM users;
```

Same sentence structure, narrower request: *"give me only `id` and `email`, not everything."* `SELECT *` says "all of it." `SELECT id, email` says "just these."

## 🧪 Sanity Check

Before moving on, ask yourself:

- Can you explain, out loud, the difference between a **data type** and a **constraint** without looking back?
- Do you know *why* `0 rows affected` isn't an error message?
- Could you write `SELECT` for "everything" and for "just two columns" without hesitating?

If all three land, the chapter did its job.

## ✅ Final Takeaway

> *"You don't design a table to describe the data you have — you design it to refuse the data you shouldn't."*
