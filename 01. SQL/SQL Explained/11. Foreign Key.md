# 🔗 The Promise That Points Somewhere Real: Foreign Keys in MySQL

> *"A pointer is only as trustworthy as the thing it points to. A Foreign Key is the database refusing to let you point at nothing."*

There is one idea underneath this entire chapter. Hold onto it:

> **A Foreign Key creates a relationship between two tables and prevents invalid references between them.**

The name sounds more terrifying than the concept. SQL terminology does enjoy making simple ideas sound like ancient legal documents. 📜

In the last chapter you watched `orders.user_id` quietly point at `users.id`. That pointer had no rules. This chapter is about the rules.

---

## 🏠 The Address That Belonged to Nobody

> *"Why do we even need a Foreign Key?"*

Start with two tables.

**`users`**

| user_id | name   |
| ------: | ------ |
|       1 | Dharan |
|       2 | Arun   |
|       3 | Priya  |

**`addresses`**

| address_id | user_id | city    |
| ---------: | ------: | ------- |
|        101 |       1 | Chennai |
|        102 |       2 | Madurai |

Look at `addresses.user_id`. It answers one question:

> *"Which user does this address belong to?"*

So `addresses.user_id = 1` means "this address belongs to the row where `users.user_id = 1`."

```text
users
  │
  │ user_id
  │
  ▼
addresses
  │
  └── user_id
```

Now give the two tables names for their roles:

```text
users.user_id
      ↑
      │ referenced by
      │
addresses.user_id
```

* 👑 `users` is the **parent table**.
* 👶 `addresses` is the **child table**.
* 🔑 `addresses.user_id` is the **foreign key column**.

The child depends on the parent. Remember that direction. Everything else in this chapter follows from it.

---

## 📜 The Definition, Without the Fear

> *"Okay, but what exactly **is** a Foreign Key?"*

A Foreign Key is a constraint that says:

> **"Values in this column must correspond to valid values in another table's referenced key."**

Here it is in SQL:

```sql
CREATE TABLE addresses (
    address_id INT PRIMARY KEY,
    user_id INT,
    city VARCHAR(50),

    CONSTRAINT fk_user
    FOREIGN KEY (user_id)
    REFERENCES users(user_id)
);
```

This creates a relationship between:

```text
addresses.user_id
        ↓
users.user_id
```

MySQL now understands that these two columns are related, and it will enforce the rules of that relationship.

---

## 👻 The Ghost of User 999

> *"Fine, but what does it actually protect me from?"*

Imagine there is **no** foreign key. The `users` table holds users 1 and 2. Then someone inserts:

```text
address_id = 103
user_id    = 999
city       = Bangalore
```

But user 999 does not exist.

```text
addresses
      │
      └── user_id = 999
                 ❌
               no user
```

This is called an **invalid reference**. The address points at a person who isn't there. A ghost. 👻

With the foreign key in place, MySQL refuses:

```sql
INSERT INTO addresses
VALUES (103, 999, 'Bangalore');
```

This fails, because `users.user_id = 999` does not exist. That protection has a name:

> **Referential integrity.** Every reference must point at something real.

---

## 🧷 The Link, Not the Move

> *"So does the foreign key copy data between the tables or something?"*

No. The instructor describes it as putting a **link** between tables, and that is a good mental model.

Before the foreign key:

```text
users                 addresses

user_id               address_id
name                  user_id
                      city
```

After:

```text
users                 addresses

user_id ◄──────────── user_id
name                  address_id
                      city
```

The foreign key does not physically move any data. It simply tells MySQL:

> *"These columns are related. Enforce the rules that come with that relationship."*

### 🧱 It is one more rule in the family you already know

A foreign key is itself a **constraint**, so it belongs with the ones you've already met:

| Constraint | The rule it places on your data |
| --- | --- |
| **PRIMARY KEY** | Every row must have a unique identifier |
| **UNIQUE** | Duplicate values are not allowed |
| **NOT NULL** | A value must be provided |
| **CHECK** | The value must pass a condition |
| **FOREIGN KEY** | This value must correspond to a valid value in another table |

---

## 🔬 Reading the Syntax Slowly

> *"What does each word in that FOREIGN KEY line actually mean?"*

```sql
FOREIGN KEY (user_id)
REFERENCES users(user_id)
```

Take it apart one piece at a time:

* **`FOREIGN KEY`** says: *"I'm defining a foreign key."*
* **`(user_id)`** is the column in the **current** (child) table, here `addresses.user_id`.
* **`REFERENCES`** says: *"This points at another table."*
* **`users(user_id)`** is the parent table and its referenced column.

Read as one sentence:

```text
addresses.user_id
        ↓
references
        ↓
users.user_id
```

### 🧐 "Does the column need to exist in both tables?"

> *"Why does the column need to exist in both tables?"*

The lecture's framing here is loose, so let's tighten it. The purpose is to establish a relationship, so there must be a column on each side. But the two columns are **two different columns in two different tables**. They are connected only by the constraint:

```text
Parent table                Child table

users.user_id  ◄────────── addresses.user_id
```

And here is the precise part: **the names do not have to match.** The MySQL manual's own example links `child.parent_id` to `parent.id`. What *does* have to match is the **data type**: the columns need similar types, and for integers the size and sign must be the same. (See the docs-check section at the end.)

---

## 🏷️ Three Things That Look Like One

Here is where the video is easiest to misread. In this line there are **three different things**:

```sql
CONSTRAINT fk_user
FOREIGN KEY (user_id)
REFERENCES users(user_id)
```

| Term | What it is |
| --- | --- |
| `user_id` | The **column** |
| `FOREIGN KEY` | The **type of constraint** |
| `fk_user` | The **name** of the constraint |

```text
fk_user
  ↓
constraint name

FOREIGN KEY
  ↓
type of constraint

(user_id)
  ↓
child column

users(user_id)
  ↓
referenced parent column
```

### 🤔 Why give a constraint a name at all?

> *"If the constraint doesn't create a new row or anything visible in the table, why does it need a name?"*

Because you may need to **modify or remove that specific constraint later**. A name is a handle:

```sql
ALTER TABLE addresses
DROP FOREIGN KEY fk_user;
```

The name isn't there to display something in the table. It's there so you can manage the constraint.

### 🎲 "What if I don't name it?"

> *"What happens if I skip the name?"*

MySQL generates one for you:

```sql
FOREIGN KEY (user_id)
REFERENCES users(user_id);
```

The instructor's advice is simple: **name your foreign keys yourself.** `fk_user` is much easier to work with than an ugly generated name you'd have to go and look up.

### 🕵️ And if it was already generated?

> *"Then how do I find the name to drop it?"*

Ask MySQL to show you the table definition:

```sql
SHOW CREATE TABLE addresses;
```

Somewhere in the output you'll see the constraint and its name:

```text
CONSTRAINT `fk_user`
FOREIGN KEY (`user_id`)
REFERENCES `users` (`user_id`)
```

Now you know what to drop:

```sql
ALTER TABLE addresses
DROP FOREIGN KEY fk_user;
```

For an unnamed constraint, the MySQL manual's example shows a generated name of the form `child_ibfk_1`, so the name you find won't be pretty. That is exactly why naming your own is the better habit.

## ⚰️ The Question Every Foreign Key Must Answer: What If the Parent Dies?

> *"What happens to the address if I delete the user?"*

This is the most important part of the chapter. Take these tables:

**`users`**

| user_id | name   |
| ------: | ------ |
|       1 | Dharan |
|       2 | Arun   |

**`addresses`**

| address_id | user_id | city    |
| ---------: | ------: | ------- |
|        101 |       1 | Chennai |
|        102 |       2 | Madurai |

Now:

```sql
DELETE FROM users
WHERE user_id = 1;
```

What becomes of address 101, which points at user 1?

The answer depends on the foreign key's **`ON DELETE` action**. MySQL gives you several. The lecture covers two, and you brought a third. Let's meet all three.

---

### 🕳️ Option 1: `ON DELETE SET NULL`

```sql
CREATE TABLE addresses (
    address_id INT PRIMARY KEY,
    user_id INT,
    city VARCHAR(100),

    CONSTRAINT fk_user
    FOREIGN KEY (user_id)
    REFERENCES users(user_id)
    ON DELETE SET NULL
);
```

Run the same delete. User 1 disappears, and because of `SET NULL`, the child's reference becomes `NULL`:

**`users`**

| user_id | name |
| ------: | ---- |
|       2 | Arun |

**`addresses`**

| address_id | user_id | city    |
| ---------: | ------: | ------- |
|        101 |    NULL | Chennai |
|        102 |       2 | Madurai |

The address row **survives**. Only its link to the deleted user is cut.

> *"Why would I want that?"*

Because sometimes the child record is still useful even when the parent is gone. You're saying: *"The address exists, but it is no longer associated with a user."*

There is one hard requirement, and it follows directly from what the words mean:

> ⚠️ **The foreign key column must allow NULL.**

```sql
user_id INT            -- allows NULL ✅
user_id INT NOT NULL   -- conflicts with ON DELETE SET NULL ❌
```

MySQL cannot set a `NOT NULL` column to `NULL`.

---

### 🛑 Option 2: `ON DELETE RESTRICT`

```sql
CONSTRAINT fk_user
FOREIGN KEY (user_id)
REFERENCES users(user_id)
ON DELETE RESTRICT
```

This means:

> **Don't allow the parent row to be deleted while child rows still reference it.**

With address 101 still pointing at user 1:

```sql
DELETE FROM users
WHERE user_id = 1;
```

MySQL rejects it:

```text
user 1
  ↑
  │ referenced by
  │
address 101

→ ❌ deletion rejected
```

> *"Why is that useful?"*

It prevents **orphaned references**. Without it you could end up with `addresses.user_id = 1` while `users.user_id = 1` no longer exists, which makes the relationship meaningless. `RESTRICT` says:

> *"You're not deleting this parent until you deal with the children."*

Human civilization has discovered that relationships have consequences. SQL apparently decided to enforce the lesson. 😌

---

### 🧹 Option 3: `ON DELETE CASCADE`

Here is where your own question enters the story. You wrote this constraint and asked what it would do:

```sql
CONSTRAINT fk_user
FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE CASCADE
```

> *"What would CASCADE do?"*

> **`ON DELETE CASCADE`: if a parent row is deleted, MySQL automatically deletes the child rows that reference it.**

Think of it as *"delete the dependent records too."* 🧹

Set up a slightly bigger example. Notice user 1 now has **two** addresses:

**`users`**

|  id | name   |
| --: | ------ |
|   1 | Dharan |
|   2 | Arun   |

**`addresses`**

| address_id | user_id | city       |
| ---------: | ------: | ---------- |
|        101 |       1 | Chennai    |
|        102 |       1 | Madurai    |
|        103 |       2 | Coimbatore |

Now delete user 1:

```sql
DELETE FROM users
WHERE id = 1;
```

MySQL follows the links from the parent:

```text
users
id = 1
   │
   ├──────────────┐
   ▼              ▼
address 101    address 102
user_id = 1    user_id = 1
```

Both children go with it. What remains:

**`users`**

|  id | name |
| --: | ---- |
|   2 | Arun |

**`addresses`**

| address_id | user_id | city       |
| ---------: | ------: | ---------- |
|        103 |       2 | Coimbatore |

The two addresses belonging to user 1 are gone, automatically.

Notice something about your constraint, too: the child column is `user_id` but the parent column is `id`. **The names differ and it works perfectly.** The link is made by `REFERENCES users(id)`, not by matching names.

---

### ⚖️ The Three Side by Side

Same parent deletion, three different fates for the child:

| `ON DELETE` | Parent deleted? | What happens to the child rows |
| --- | --- | --- |
| **CASCADE** | ✅ Allowed | Deleted |
| **SET NULL** | ✅ Allowed | `user_id` becomes `NULL` |
| **RESTRICT** | ❌ Prevented | Stay unchanged |

```text
CASCADE
Parent deleted
      ↓
Child deleted

SET NULL
Parent deleted
      ↓
Child reference → NULL

RESTRICT
Parent deletion
      ↓
❌ STOP
```

### ⚠️ A warning about CASCADE

`CASCADE` can delete a **lot** of data automatically. If one user has 50 addresses, deleting that user deletes all 50. And if other tables cascade from *those* addresses, the effect propagates further down the chain.

So `CASCADE` isn't "better" than `SET NULL` or `RESTRICT`. It depends on what the data **means**:

* For **Order → OrderItems**, cascading deletion can make sense, because the items only exist as part of the order.
* For **User → Address**, whether you want the address deleted along with the user depends on your application's data-retention requirements.

Those two examples are design judgment, not MySQL rules. Your application decides.

### 📌 One correction worth keeping

The lecture presents `RESTRICT` as something you choose to get protection. In MySQL it is closer to the **baseline**. When you write no `ON DELETE` clause at all, the default action is `NO ACTION`, which InnoDB treats the same as `RESTRICT`. So a plain foreign key already refuses to delete a parent that still has children. `SET NULL` and `CASCADE` are the behaviors you opt into.

And one more thing the lecture doesn't mention: everything above has an `ON UPDATE` twin. You can choose what happens to children when a parent's key value is *changed*, using the same set of actions.

## ➕ "My Table Already Exists. Can I Add the Foreign Key Later?"

> *"Do I have to create the foreign key at the same moment as the table?"*

No. The instructor points this out explicitly. First the table:

```sql
CREATE TABLE addresses (
    address_id INT PRIMARY KEY,
    user_id INT,
    city VARCHAR(100)
);
```

Then, later:

```sql
ALTER TABLE addresses
ADD CONSTRAINT fk_user
FOREIGN KEY (user_id)
REFERENCES users(user_id);
```

The workflow can be:

```text
Create table
     ↓
Add columns
     ↓
Insert/modify data
     ↓
Add foreign key later
```

### 🧟 The catch: existing data

The lecture's note here is that if existing rows already contain invalid references, adding the constraint can fail, because MySQL has to enforce the relationship on data that's already there:

```text
addresses.user_id = 999
users.user_id     = (no 999)
```

That row would violate the new rule. This is a sensible expectation, but the manual page I read does not spell this failure out in so many words, so treat it as something to **test on your own MySQL version** before relying on it. (More in the docs-check section.)

---

## ✂️ "Can I Remove a Foreign Key Later?"

> *"And if I want it gone?"*

Yes:

```sql
ALTER TABLE addresses
DROP FOREIGN KEY fk_user;
```

### 🪢 Dropping the constraint is not dropping the column

> *"Does that delete my `user_id` column too?"*

No, and this distinction saves people from panic. Before:

```text
addresses

address_id
user_id      ← foreign key
city
```

After `DROP FOREIGN KEY fk_user`:

```text
addresses

address_id
user_id      ← still here, now a plain column
city
```

You removed **the constraint**, not the column. To remove the column you'd need something different:

```sql
ALTER TABLE addresses
DROP COLUMN user_id;
```

```text
DROP FOREIGN KEY
        ≠
DROP COLUMN
```

## ⏱️ When Does the Foreign Key Actually Do Something?

> *"If it doesn't add a row or a visible column, when is it even doing anything?"*

You're right that it's invisible. Creating one does not add another row or another data column. The database stores the constraint as **metadata** and consults it whenever you modify data. It springs into action on three operations:

### 1️⃣ INSERT

```sql
INSERT INTO addresses
VALUES (101, 999, 'Chennai');
```

If `users.user_id = 999` doesn't exist: ❌ rejected.

### 2️⃣ UPDATE

```sql
UPDATE addresses
SET user_id = 999
WHERE address_id = 101;
```

If user 999 doesn't exist: ❌ rejected.

### 3️⃣ DELETE (on the parent)

```sql
DELETE FROM users
WHERE user_id = 1;
```

Here the `ON DELETE` rule decides: `RESTRICT` prevents it, `SET NULL` nulls the child, `CASCADE` deletes the child.

The full picture:

```text
                FOREIGN KEY
                     │
                     ▼
         Connects two tables
                     │
                     ▼
       Enforces valid references
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
   INSERT / UPDATE            DELETE
          │                     │
          ▼                     ▼
   Invalid references      ON DELETE rule
       rejected             determines what
                            happens
```

---

## 🔧 What MySQL Does Behind the Curtain

> *"How does it actually check all this without slowing everything down?"*

Two internal details from the MySQL manual make the "invisible" constraint feel less magical:

1. **Indexes.** MySQL requires an index on the foreign key columns (and on the referenced columns) so that foreign key checks are fast and don't need a full table scan. If you create a foreign key and no suitable index exists on the child column, MySQL **creates one for you**. So a foreign key doesn't add a row or a visible column, but it can add an index.
2. **Cascades.** InnoDB performs cascading operations using a depth-first search on the records of the index that belongs to the foreign key.

This is also why the earlier "add the foreign key later" advice comes with a footnote: when you add one using `ALTER TABLE`, the manual says to make sure the **referenced** columns already have an index. A primary key already has one, which is one more reason foreign keys usually point at primary keys.

## 🧪 The Whole Example, End to End

Put everything together. The **parent** table:

```sql
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    name VARCHAR(100)
);

INSERT INTO users VALUES
(1, 'Dharan'),
(2, 'Arun'),
(3, 'Priya');
```

The **child** table:

```sql
CREATE TABLE addresses (
    address_id INT PRIMARY KEY,
    user_id INT,
    city VARCHAR(100),

    CONSTRAINT fk_user
    FOREIGN KEY (user_id)
    REFERENCES users(user_id)
    ON DELETE SET NULL
);
```

```text
users.user_id
      ↑
      │
      │ FK relationship
      │
addresses.user_id
```

**✅ A valid insert:**

```sql
INSERT INTO addresses
VALUES (101, 1, 'Chennai');
```

Works, because `users.user_id = 1` exists.

**❌ An invalid insert:**

```sql
INSERT INTO addresses
VALUES (102, 999, 'Bangalore');
```

Foreign key violation, because user 999 doesn't exist.

**🗑️ Delete the parent:**

```sql
DELETE FROM users
WHERE user_id = 1;
```

Because of `ON DELETE SET NULL`:

| address_id | user_id | city    |
| ---------: | ------: | ------- |
|        101 |    NULL | Chennai |

## 🧩 Seeing the Whole Machine at Once

Don't memorize this as one giant SQL spell:

```sql
CONSTRAINT fk_user
FOREIGN KEY (user_id)
REFERENCES users(user_id)
ON DELETE SET NULL;
```

It is **four pieces**, each doing one job:

```text
fk_user
   │
   └── constraint name

user_id
   │
   └── child FK column

users(user_id)
   │
   └── parent reference

ON DELETE SET NULL
   │
   └── deletion behavior
```

Once those four pieces stop looking like one incomprehensible SQL sentence, foreign keys become much less mysterious.

## 🛂 One Mental Model to Keep

Imagine a passport. You have two tables:

```text
PERSON
person_id
name

PASSPORT
passport_id
person_id
country
```

`PASSPORT.person_id` should point to a real `PERSON.person_id`:

```text
PERSON
person_id = 101
      ▲
      │
      │
PASSPORT
person_id = 101
```

That connection is the foreign key. It is the database saying:

> *"Don't give me a reference to a parent that doesn't exist."* 🔗

## 🧪 Sanity Check: Could You Survive the Interview?

Cover the answers and try each question out loud.

**"What is a Foreign Key?"**
A constraint on a child table's column(s) saying every value must correspond to a valid value in the referenced key of a parent table. It prevents invalid references.

**"Which table is the parent and which is the child?"**
The parent holds the referenced values (`users`). The child holds the foreign key column and depends on the parent (`addresses`). The constraint is defined on the **child**.

**"What happens if you insert a child row pointing at a parent that doesn't exist?"**
MySQL rejects the INSERT (and an UPDATE that would do the same).

**"What are `RESTRICT`, `SET NULL` and `CASCADE`?"**

| `ON DELETE` | Parent deleted | Child rows |
| --- | --- | --- |
| RESTRICT | ❌ Prevented | Unchanged |
| SET NULL | ✅ Allowed | FK becomes NULL |
| CASCADE | ✅ Allowed | Deleted too |

**"What does `SET NULL` require?"**
The foreign key column must be nullable, not `NOT NULL`.

**"What is the default if I write no `ON DELETE`?"**
`NO ACTION`, which InnoDB treats as `RESTRICT`.

**"Does dropping a foreign key drop the column?"**
No. `DROP FOREIGN KEY` removes the constraint; `DROP COLUMN` removes the column.

**"How do you find an unnamed constraint's name?"**
`SHOW CREATE TABLE table_name;`

**"Can you add a foreign key after the table exists?"**
Yes, with `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ...`.

### 🔁 The four myths, corrected

```text
❌ "The two columns need the same name."
✅ "The names can differ (child.parent_id → parent.id). The data types must be similar."

❌ "RESTRICT is an extra protection you have to switch on."
✅ "Omitting ON DELETE gives NO ACTION, which InnoDB treats the same as RESTRICT."

❌ "A foreign key adds nothing to the table."
✅ "It adds no rows or data columns, but MySQL creates an index on the FK column if none exists."

❌ "CASCADE is the tidy option."
✅ "CASCADE can delete a lot automatically. Choose it only when children have no meaning without the parent."
```

## 🔎 Checked Against the Documentation

Several claims in the lecture and these notes were checked against the MySQL manual. Here is exactly what could and could not be confirmed.

**Confirmed, from the full text of [MySQL 8.4 Reference Manual, FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html), which I opened in full:**

* The constraint is defined on the **child** table; the parent holds the values being referenced.
* MySQL rejects an `INSERT` or `UPDATE` that would create a child foreign key value with no matching parent key.
* The available referential actions are `CASCADE`, `SET NULL`, `RESTRICT`, `NO ACTION`, and `SET DEFAULT`. `SET DEFAULT` is parsed but rejected by InnoDB and NDB.
* If `ON DELETE`/`ON UPDATE` is not specified, the default is always `NO ACTION`. For InnoDB it is equivalent to `RESTRICT`, and specifying `RESTRICT` is the same as omitting the clause.
* With `SET NULL`, the child columns must not be declared `NOT NULL`.
* With `CASCADE`, matching child rows are deleted or updated automatically, and cascaded foreign key actions do **not** activate triggers.
* If you give no `CONSTRAINT` symbol, a name is generated automatically. A named symbol must be unique within the database. The manual's example shows a generated name of `child_ibfk_1`, and it says to use `SHOW CREATE TABLE` to find the name and `ALTER TABLE ... DROP FOREIGN KEY` to drop it.
* MySQL requires indexes on foreign keys and referenced keys. If the child table has no suitable index, one is created automatically. When adding a foreign key with `ALTER TABLE`, create an index on the referenced columns first.
* Corresponding columns need **similar data types**. For `INTEGER` and `DECIMAL`, size and sign must be the same; string lengths need not match. The manual's own example links `child.parent_id` to `parent.id`, so column names need not match.
* Parent and child tables must use the same storage engine and cannot be temporary tables.
* InnoDB performs cascading operations using a depth-first search on the index that corresponds to the foreign key.
* Rows added while `foreign_key_checks` is disabled are **not** re-checked when it is re-enabled.
* Referencing a non-unique key is a deprecated InnoDB extension that must be enabled with `restrict_fk_on_non_standard_key`. This supports pointing foreign keys at primary or unique keys.

**Confirmed only from search-result excerpts, not from a page I opened in full** (the [MySQL Restrictions and Limitations excerpt, FOREIGN KEY Constraint Differences](https://dev.mysql.com/doc/mysql-reslimits-excerpt/8.0/en/ansi-diff-foreign-keys.html), an 8.0 page):

* Cascading operations may not be nested more than 15 levels deep.
* A self-referential `ON DELETE CASCADE` or `ON DELETE SET NULL` is possible.
* For storage engines without foreign key support, such as MyISAM, MySQL parses and ignores foreign key specifications.

**Not confirmed from the manual text I retrieved:**

* That `ALTER TABLE ... ADD FOREIGN KEY` **fails** when the table already contains orphan rows. The lecture says so and it is plausible, but the "Adding Foreign Key Constraints" section I read does not state it. Test it on your own MySQL version.
* The design advice (Order → OrderItems suits `CASCADE`; User → Address depends on retention needs) is judgment, not a documented rule. The passport picture is a teaching analogy.
* I read the 8.4 manual; the page's version selector also lists 9.7 as current. Behavior on your installed version may differ, so check the matching manual.

## ✅ Final Takeaway

> **"A Foreign Key is a promise that every pointer lands on something real. The `ON DELETE` rule decides what happens when the thing being pointed at goes away: `RESTRICT` says *stop*, `SET NULL` says *let go*, `CASCADE` says *follow it down*. Learn the four pieces separately (name, column, reference, action) and the one long line stops being a spell."**
