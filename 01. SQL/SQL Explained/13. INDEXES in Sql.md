# 📖 The Index at the Back of the Book: MySQL Indexes, Explained

> *"An index is a lookup structure the database keeps on the side, so it can jump to your data instead of reading everything."*

Picture a book with 1,000 pages. You want **Chapter 13**.

You could start at page 1 and check every page:

```text
Page 1   → Chapter 1
Page 2   → Chapter 1
Page 3   → Chapter 1
...
Page 400 → Chapter 13   (finally!)
```

That is painfully slow. 🐌

But the book has an **index** at the back:

```text
Chapter 1  → Page 1
Chapter 2  → Page 37
Chapter 13 → Page 400
```

You look up "Chapter 13", see "Page 400", and flip straight there. ⚡

The instructor builds the whole lesson on this one analogy. A database index works on the same basic idea:

```text
Column value  →  location/reference of the matching rows
```

So the three questions this chapter answers are:

| Question | Short answer |
| -------- | ------------ |
| **What is it?** | A separate data structure that helps MySQL find rows faster |
| **Why does it exist?** | So searches, filters, and joins don't have to read the whole table |
| **How does it work inside?** | It keeps column values in a searchable, sorted structure that points to the rows (details below) |

---

## 🐌 The problem: a million rows and one email

Imagine a `users` table:

| id | name | email | gender |
| --: | ---- | ----- | ------ |
| 1 | A | a@gmail.com | Male |
| 2 | B | b@gmail.com | Female |
| 3 | C | c@gmail.com | Male |
| ... | ... | ... | ... |
| 1,000,000 | Z | z@gmail.com | Female |

And your app keeps running this:

```sql
SELECT *
FROM users
WHERE email = 'ishan@example.com';
```

Without a suitable index, MySQL may have to **examine many rows** to find the match. The bigger the table, the more that costs.

With an index on `email`, MySQL has a structure designed for exactly this lookup:

```text
Index on email
──────────────
a@gmail.com        → row 1
b@gmail.com        → row 2
...
ishan@example.com  → the matching row
...
```

The instructor's point: if you **repeatedly** retrieve users by email, an index on `email` can make those retrievals faster.

---

## 🤔 "So the index just hides somewhere and helps indirectly?"

Here is a question that came up right after the lesson, in your own words:

> 💭 **"So the index is something that hides within the database/table and it indirectly helps to access the data quicker?"**

That is a very good beginner mental model. Two small sharpenings:

1. An index is a **separate data structure** associated with a table. It is not an extra visible column, and not a second set of rows you normally query.
2. **You don't call it.** You write the same SQL as always, and MySQL decides whether an index would help.

```text
You
 ↓
SQL query
 ↓
MySQL optimizer  →  "Would an index help here?"
 ↓
Index (if useful)
 ↓
Relevant rows
```

One sentence to keep:

> **Table = the actual data. Index = a lookup structure that helps MySQL find that data faster.** 🧠

## ⚙️ Under the hood: what the index actually is

The lecture stays at the analogy level. Here is the layer beneath it, taken from MySQL's manual (sources in the Docs Check):

- Most MySQL indexes (`PRIMARY KEY`, `UNIQUE`, `INDEX`, `FULLTEXT`) are stored in **B-trees**, a sorted tree structure that lets MySQL find a position without scanning everything.
- Without an index, MySQL must start at the first row and read through the entire table. With one, it can work out where to seek in the data file without looking at all the data.
- In **InnoDB** (MySQL's default engine), the primary key is special: it is the **clustered index**, which stores the row data itself.
- Every *other* index is a **secondary index**. Each entry in it stores the indexed columns **plus the primary key value** of the row. To fetch the full row, InnoDB takes that primary key value and looks it up in the clustered index.

So the "location/reference" from the book analogy is, for a secondary index in InnoDB, **the primary key of the row**.

```text
Secondary index on email            Clustered index (the table itself)
────────────────────────            ──────────────────────────────────
arun@gmail.com     → id 2  ───┐     id 1 │ Dharan │ dharan@gmail.com
dharan@gmail.com   → id 1     ├───► id 2 │ Arun   │ arun@gmail.com
ravi@gmail.com     → id 3  ───┘     id 3 │ Ravi   │ ravi@gmail.com
```

*(This is a simplified picture: the real structures are trees, not flat lists.)*

## 🔑 The primary key already comes with an index

This is one of the important things the instructor teaches:

> When you create a `PRIMARY KEY`, MySQL **automatically creates an index** for it.

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);
```

Now `id` is both a primary key **and** indexed. So this is efficient:

```sql
SELECT * FROM users WHERE id = 500;
```

> 💭 **"So a primary key and an index are the same thing?"**

No. Keep them apart:

| | Primary key | Index |
| --- | ----------- | ----- |
| **What it is** | A **constraint** that identifies each row uniquely | A **structure** that speeds up access to data |
| **Relationship** | In MySQL, defining one automatically creates the other | Can exist without any primary key |

*(In InnoDB, the primary key index is the clustered index that stores the rows themselves, which is one reason primary-key lookups are so direct.)*

## 👀 Step 1 of the lifecycle: seeing what exists

Before creating anything, look at what is already there:

```sql
SHOW INDEXES FROM users;
```

You will see something like this (conceptually):

| Table | Key_name  | Column |
| ----- | --------- | ------ |
| users | PRIMARY   | id     |
| users | idx_email | email  |

Meaning: `id` is indexed (via the primary key), and `email` is indexed (via an index named `idx_email`). The real output has many more columns, but these are the ones to read first.

Why check first? So you inspect what's there instead of blindly creating more and hoping the database appreciates your enthusiasm. 😅

---

## 🛠️ Step 2: creating an index

The syntax:

```sql
CREATE INDEX index_name
ON table_name(column_name);
```

For example:

```sql
CREATE INDEX idx_email
ON users(email);
```

Now `email` has an index named `idx_email`. Verify it:

```sql
SHOW INDEXES FROM users;
```

This is a **single-column index**: one column indexed.

```text
users
│
├── id
├── name
├── email   ← indexed
└── gender
```

It shines when your app keeps searching by that column:

```sql
SELECT * FROM users WHERE email = 'abc@gmail.com';
```

The instructor's principle:

> **Create an index when a particular column is frequently used for retrieval.**

---

## 🏛️ Don't build an index museum

> 💭 **"If indexes make things faster, why not index every column?"**

Because indexes are not free. The instructor warns that indexes:

- 💾 consume **additional disk space**
- 🐢 can slow down **`INSERT`**
- 🐢 can slow down **`UPDATE`**
- 🐢 can slow down **`DELETE`**

Why? Because when the table changes, **the index has to change too.**

### Why `INSERT` gets slower

```sql
CREATE INDEX idx_email ON users(email);

INSERT INTO users (id, name, email)
VALUES (101, 'Dharan', 'dharan@gmail.com');
```

The database doesn't just add the row. It must also update the email index:

```text
INSERT without index          INSERT with index
────────────────────          ─────────────────
table modification            table modification
                                    +
                              index modification
```

More work.

### Why `UPDATE` gets slower

```sql
UPDATE users
SET email = 'new@gmail.com'
WHERE id = 10;
```

If `email` is indexed, the index entry must move too:

```text
Before:  abc@gmail.com → row 10
                ↓ UPDATE
After:   new@gmail.com → row 10
```

### Why `DELETE` gets slower

Same principle. If a row appears in an index, deleting the row means fixing the index.

### The trade-off, in one picture

```text
                  INDEX
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
     Faster reads        Extra write cost
          │                   │
       SELECT              INSERT
       WHERE               UPDATE
       JOIN                DELETE
```

So indexes are **not** simply "make the database faster." The accurate model:

> **Indexes can make certain data-retrieval operations faster, at the cost of extra storage and extra maintenance work when data changes.**

---

## 🎯 When to use one

The instructor's rule: base it on **actual query usage**, not on "this is a column, therefore it deserves an index."

Good candidates are columns that show up repeatedly in conditions such as:

```sql
WHERE email = ...
WHERE gender = ...
```

or in combinations of columns. Use indexes **when needed**. Be more careful when a table takes lots of writes.

---

## 🧱 Multi-column indexes

Now the more interesting part. Suppose you often run:

```sql
SELECT *
FROM users
WHERE email = 'abc@gmail.com'
  AND gender = 'Male';
```

You are filtering on **two columns**. For that, you can index both together:

```sql
CREATE INDEX idx_email_gender
ON users(email, gender);
```

Notice the **two columns** inside the parentheses. Compare that with the single-column version:

```sql
CREATE INDEX idx_email ON users(email);      -- one column
CREATE INDEX idx_email_gender
ON users(email, gender);                     -- two columns
```

The instructor demonstrates multi-column indexes using columns such as `gender` and `salary`.

---

## ⚠️ Column order matters (the most important advanced point)

Say you create:

```sql
CREATE INDEX idx_gender_salary
ON users(gender, salary);
```

The order is **1. gender, 2. salary**. That order is baked into the index.

Think of a sorted filing cabinet:

```text
gender
  ├── Male
  │     └── salary (sorted within Male)
  └── Female
        └── salary (sorted within Female)
```

It is organized **first by gender, then by salary**.

### Two queries, two outcomes

**Query 1: uses both columns, in index order** ✅

```sql
SELECT * FROM users
WHERE gender = 'Male' AND salary = 50000;
```

Matches the structure: `gender → salary`.

**Query 2: uses only the second column** ❌

```sql
SELECT * FROM users
WHERE salary = 50000;
```

You are searching by `salary`, but the index begins with `gender`. The instructor says the index may not be used efficiently here.

This is the **leftmost-prefix principle**. For `(gender, salary)`, the useful prefixes are:

```text
✅ gender
✅ gender + salary
❌ salary alone
```

### 📞 The phone book picture

A phone book is sorted **Last Name → First Name**.

- Find **"Smith, John"**: easy. Locate Smith, then John.
- Find **every "John"**: painful. The book isn't organized by first name.

```text
INDEX(last_name, first_name)

✅ WHERE last_name = ...
✅ WHERE last_name = ... AND first_name = ...
❌ WHERE first_name = ...            (not built for this)
```

> 🔑 **The first column in a multi-column index is the one that matters most.**

## ⏱️ Don't trust; measure

The instructor gives you a practical task. Follow these steps:

**Step 1.** Insert a **large** amount of data into the table.

**Step 2.** Run a query and note the time:

```sql
SELECT * FROM users WHERE ...;
```

**Step 3.** Create an index:

```sql
CREATE INDEX idx_gender ON users(gender);
```

**Step 4.** Run the same query again and **compare the times**.

The lesson:

> **Don't blindly assume an index helps. Measure query performance.**

---

## 🗑️ Step 3 of the lifecycle: dropping an index

If an index isn't earning its keep, remove it:

```sql
DROP INDEX index_name
ON table_name;
```

For example:

```sql
DROP INDEX idx_email
ON users;
```

The instructor shows checking the indexes **before and after** to confirm it disappeared:

```sql
SHOW INDEXES FROM users;   -- before
DROP INDEX idx_email ON users;
SHOW INDEXES FROM users;   -- after: idx_email is gone
```

### The whole practical toolkit

```text
            INDEX
              │
     ┌────────┼────────┐
     ↓        ↓        ↓
   SHOW    CREATE     DROP
```

| Action | Command |
| ------ | ------- |
| See indexes | `SHOW INDEXES FROM users;` |
| Create index | `CREATE INDEX idx_email ON users(email);` |
| Drop index | `DROP INDEX idx_email ON users;` |

## 🗺️ The big picture, on one table

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100),
    gender VARCHAR(20),
    salary INT
);
```

Suppose you also create indexes on `email`, `gender`, and `(gender, salary)`.

| Query | Index that can help |
| ----- | ------------------- |
| `WHERE id = 10` | The primary-key index |
| `WHERE email = 'abc@gmail.com'` | `idx_email` |
| `WHERE gender = 'Male' AND salary = 50000` | `idx_gender_salary` |

But every additional index has a cost. 💸

```text
Without index                       With suitable index
─────────────                       ───────────────────
Potentially examine many rows       Use the index to locate rows
          ↓                                   ↓
          🐌                                  ⚡
```

The instructor's closing advice: use indexes when query performance on large tables is a real concern, and avoid unnecessary ones when the table sees lots of updates.

## ✅ Sanity Check: can you answer these?

Try each before opening the answer.

**1. You create `INDEX(gender, salary)`. Which of these queries can use it for lookups?**

- (a) `WHERE gender = 'Male'`
- (b) `WHERE gender = 'Male' AND salary = 50000`
- (c) `WHERE salary = 50000`
- (d) `WHERE salary = 50000 AND gender = 'Male'`

<details>
<summary>Answer</summary>

**(a), (b), and (d) can; (c) cannot.** (a) uses the leftmost prefix. (b) and (d) test *all* the index's columns; the order you write the conditions in doesn't change that (my reasoning; the manual says a multi-column index can serve queries that test all its columns). (c) tests only `salary`, which is not a leftmost prefix.

</details>

**2. Does adding an index make `INSERT` faster, slower, or the same?**

<details>
<summary>Answer</summary>

**Slower (more work).** The database updates the table *and* every index that covers the new row. The same maintenance idea applies to `UPDATE` and `DELETE`.

</details>

**3. What index do you get for free when you declare `id INT PRIMARY KEY`?**

<details>
<summary>Answer</summary>

An index on `id`. In `SHOW INDEXES` output, a primary key's index is always named `PRIMARY`.

</details>

**4. Write the command to remove an index called `idx_email` from `users`.**

<details>
<summary>Answer</summary>

```sql
DROP INDEX idx_email ON users;
```

</details>

**5. Can you write a query that reads the index directly, like a table?**

<details>
<summary>Answer</summary>

Not in normal use. You write ordinary SQL, and MySQL's optimizer decides whether an index helps.

</details>

**6. 🧪 Stretch question (beyond the lecture): you index only `gender`, which has two values across a million rows. Will that index be very helpful?**

<details>
<summary>Answer</summary>

Probably **not very**. An index on a column with few distinct values narrows the search very little, since each value still matches a huge share of the rows. MySQL's manual says that when several indexes are possible, it normally prefers the most selective one, meaning the one that finds the fewest rows. `SHOW INDEXES` even reports a **Cardinality** estimate (number of unique values in the index). This is my reasoning from those facts, not a claim from the lecture. It is also why the "measure before and after" exercise matters: try it and see.

</details>

## 💬 Final Takeaway

> **"An index is a shortcut MySQL keeps beside your table. It makes the lookups you repeat much faster, but it charges rent on every write, so index the columns your queries actually use, put the most-used column first, and measure before you believe it."**
