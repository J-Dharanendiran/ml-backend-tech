# The Undo Button MySQL Doesn't Always Give You

Every database eventually asks you a question you'd rather not answer under pressure: *when exactly does a change become permanent?* Not when you type it. Not when it runs. Somewhere in between there's a moment where the change could still be taken back — and the whole lesson of **auto-commit** is about finding, and controlling, that moment. Because one wrong `DELETE` is apparently all it takes to turn a peaceful afternoon into archaeology. 😄

## The Setting That Runs the Show

MySQL ships with a quiet default sitting in the background:

```sql
autocommit = 1
```

— also written as `autocommit = ON`. It means every SQL statement is treated as its own tiny transaction, finished and sealed the instant it runs. So when you type:

```sql
DELETE FROM users
WHERE id = 5;
```

MySQL doesn't pause to ask if you're sure. It reasons:

> "You executed it, so I assume you meant it."

The deletion is committed automatically — no waiting, no safety net. And that's the trap worth noticing before it bites: once it's committed, `ROLLBACK` can't reach back and undo it.

## The Scenario Everyone Dreads

Picture a small table:

| id | name     |
|----|----------|
| 1  | Sneha    |
| 2  | Raj      |
| 3  | Priyanka |
| 4  | Farhan   |

The plan is to delete Farhan:

```sql
DELETE FROM users
WHERE id = 4;
```

But the fingers slip, and what actually runs is:

```sql
DELETE FROM users
WHERE id = 3;
```

Priyanka is gone. With auto-commit ON, that deletion is *already* permanent by the time the mistake registers. There's no reaching backward — the door closed the moment the statement ran.

*Is there a way to buy yourself a second look before that door closes?* Yes — and that's the entire reason auto-commit can be turned off.

## Switching Off the Autopilot

```sql
SET autocommit = 0;
```

— sometimes written as `SET autocommit = OFF`. This one line changes everything about how risky operations feel. Changes still happen, but they no longer seal themselves shut on arrival. There's a pause built in, and inside that pause sits a choice:

```text
Database before
       ↓
   DELETE
       ↓
Temporary transaction state
       ↓
   ┌───────────────┐
   │ COMMIT        │ → Make permanent
   │ ROLLBACK      │ → Undo
   └───────────────┘
```

That pause — that window between *"it ran"* and *"it's permanent"* — is the whole idea this lesson is built around.

## What a Transaction Actually Is

A **transaction** is a group of operations MySQL treats as a single unit — a bundle that either all happens, or none of it does.

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

Those two statements aren't really two separate actions. They're one transfer, split into halves:

```text
Transfer ₹100
     │
     ├── Remove ₹100 from A
     │
     └── Add ₹100 to B
```

You never want only *half* of that to become permanent — money vanishing from one account without arriving in the other is exactly the kind of disaster a transaction exists to prevent.

## COMMIT: "Make It Permanent"

```sql
SET autocommit = 0;

DELETE FROM users
WHERE id = 5;

COMMIT;
```

```text
DELETE
  ↓
Change exists in current transaction
  ↓
COMMIT
  ↓
Change becomes permanent
```

`COMMIT` is the word that finally locks the door. Everything since the last safe point gets saved for good.

## ROLLBACK: "Undo Since the Last Safe Point"

```sql
SET autocommit = 0;

DELETE FROM users
WHERE id = 5;

ROLLBACK;
```

As long as that deletion was never committed, `ROLLBACK` erases it as if it never happened — returning the database to its last safe, committed state.

## The Idea That Makes Everything Click: "Since the Last COMMIT"

Here's where the lesson earns its keep. Suppose:

```sql
SET autocommit = 0;

UPDATE users SET name = 'Dharan' WHERE id = 1;
DELETE FROM users WHERE id = 2;

ROLLBACK;
```

*Both* changes vanish — not just the last one. Why? Because neither one happened after a `COMMIT`. `ROLLBACK` doesn't count statements; it counts distance from the last safe point:

```text
                    Last COMMIT
                         ↓
Database ────────────────●───────────────
                         │
                         │
                    UPDATE
                         │
                    DELETE
                         │
                    ROLLBACK
                         │
                         ↓
              Back to last COMMIT
```

*Does `ROLLBACK` work like Ctrl+Z, undoing your last action?* Not quite — and this distinction matters. It's closer to:

> **"Return to the previous committed state,"**

not *"undo the previous statement."* Once a `COMMIT` runs, it plants a new permanent flag in the ground. A later `ROLLBACK` can't walk past that flag — it only erases what happened *after* it.

## Walking Through the Whole Rescue

**Step 1 — disable the autopilot:**

```sql
SET autocommit = 0;
```

**Step 2 — plant a safe point:**

```sql
COMMIT;
```

```text
Database State A
       ↑
   LAST COMMIT
```

**Step 3 — the mistake happens:**

```sql
DELETE FROM users
WHERE id = 3;
```

```text
Database State A
       ↓
     DELETE
       ↓
Database State B
```

*"Oops. That wasn't the user I wanted."* Humanity survives another SQL query.

**Step 4 — walk it back:**

```sql
ROLLBACK;
```

```text
Database State A
       ↑
       │
   ROLLBACK
       │
Database State B
```

The mistake dissolves. The database sits exactly where it did at the last commit — as though the wrong deletion never ran.

**Step 5 — do it correctly, this time:**

```sql
DELETE FROM users
WHERE id = 5;
```

Verify it. Only then:

```sql
COMMIT;
```

```text
DELETE
  ↓
Verify
  ↓
COMMIT
  ↓
Permanent
```

Check first, commit second — never the other way around.

## Auto-Commit ON vs. OFF, Side by Side

| Auto-Commit ON | Auto-Commit OFF |
|---|---|
| Changes commit automatically | Changes wait for an explicit `COMMIT` |
| No `COMMIT` needed per statement | You commit deliberately |
| `ROLLBACK` can't undo an already-committed statement | `ROLLBACK` can discard anything uncommitted |
| Convenient | More control |
| Fine for ordinary work | Better for careful, multi-step changes |

The recommendation is straightforward: leave auto-commit **on** for everyday work, and switch it **off** only when you're about to do something you'd want a chance to reconsider.

## Three Commands, Three Jobs

**`SET autocommit`** — the switch itself:

```sql
SET autocommit = 1;   -- AUTO-COMMIT ON
SET autocommit = 0;   -- AUTO-COMMIT OFF
```

**`COMMIT`** — *"Save these changes."*

```sql
COMMIT;
```

**`ROLLBACK`** — *"Undo what I've done since the last commit."*

```sql
ROLLBACK;
```

## The One Diagram Worth Keeping

```text
                 AUTOCOMMIT = 1
                       │
                       ↓
              SQL statement runs
                       │
                       ↓
                 AUTO COMMIT
                       │
                       ↓
                  PERMANENT
```

versus:

```text
                 AUTOCOMMIT = 0
                       │
                       ↓
              SQL statement runs
                       │
                       ↓
              NOT YET PERMANENT
                   /        \
                  /          \
             COMMIT        ROLLBACK
                ↓              ↓
           PERMANENT         UNDO
```

That single contrast holds the entire lesson.

## Why Not Just Leave Auto-Commit Off All the Time?

*If off is safer, why not stay there permanently?* Because most work isn't risky. A `SELECT` doesn't touch data at all, and ordinary single-row changes don't need a manual safety ritual attached to every one of them:

```text
Query
 ↓
Automatically committed
 ↓
Done
```

Constantly managing transactions by hand for routine work adds friction without adding safety. The discipline is worth reserving for the moments that actually call for it:

```text
Disable auto-commit
        ↓
Perform changes
        ↓
Check the result
        ↓
       ┌───────┐
       ↓       ↓
    COMMIT  ROLLBACK
       ↓       ↓
    Save     Undo
```

## A Realistic Workflow, Start to Finish

```sql
SET autocommit = 0;

-- perform the risky change
DELETE FROM users
WHERE id = 5;

-- inspect the result before trusting it
SELECT *
FROM users;

-- if it's correct:
COMMIT;

-- if it's wrong:
-- ROLLBACK;

-- return to normal behavior when finished
SET autocommit = 1;
```

That last line matters as much as the first — leaving auto-commit off indefinitely just recreates the friction the default setting was designed to avoid.

## Three Words That Look Similar but Aren't

**Auto-commit** — a *setting* that controls whether commits happen automatically.

```sql
SET autocommit = 0;
```

**`COMMIT`** — a *command* that explicitly finalizes the current transaction.

```sql
COMMIT;
```

**`ROLLBACK`** — a *command* that discards whatever hasn't been committed yet.

```sql
ROLLBACK;
```

```text
AUTOCOMMIT
    │ controls
    ↓
When transactions are automatically committed

COMMIT
    ↓
Explicitly finalize changes

ROLLBACK
    ↓
Discard uncommitted changes
```

## The Practical Habit Worth Keeping

**Normal work:**

```sql
SET autocommit = 1;
```

**Before a risky or critical operation:**

```sql
SET autocommit = 0;
-- perform it, check it
COMMIT;    -- if right
-- ROLLBACK;  -- if wrong
SET autocommit = 1;   -- return to normal
```

That's the entire discipline, boiled down to a habit rather than a theory.

---

> **The takeaway:** *"Auto-commit ON means MySQL saves everything the moment it happens; auto-commit OFF means you get to check your work before the database agrees to remember it — and that pause, however brief, is the only real undo button SQL ever gives you."*
