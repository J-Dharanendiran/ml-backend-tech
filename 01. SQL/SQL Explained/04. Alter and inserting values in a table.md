# 🪑 The Room That Learned to Rearrange Itself

> "You built the room. Then reality showed up with a requirement you didn't have yesterday. This is the chapter about not having to demolish the house every time that happens."

Last time, you built `users` and locked its structure in with `CREATE TABLE`. But structure isn't a one-time decision — it's a living thing that gets renovated the moment a real requirement shows up. And requirements almost never show up on schedule.

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100),
    gender VARCHAR(10),
    date_of_birth DATE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

That's the room as it stands. **What happens when the room isn't enough anymore?**

---

## 🔧 ALTER TABLE — renovating, not rebuilding

Here's the one-sentence definition worth carving in:

> **`ALTER TABLE` changes the *structure* of an existing table. It does not touch the data inside the rows — not primarily, anyway.**

Add a column, remove a column, redefine a column, reposition a column, adjust a constraint. That's the whole job description. Think of it the way you'd think about renovating a house you already live in — you're not tearing it down and starting over, you're changing what's already standing.

---

## ➕ Adding a column

Suppose it's day 40 of the project and someone finally asks: *"wait — how do we know if a user is even active?"*

*Because apparently that requirement surfaces only after the table already exists.* A classic tradition of software, and not one you invented.

```sql
ALTER TABLE users
ADD COLUMN is_active BOOLEAN DEFAULT TRUE;
```

Read it in four pieces:

- **`ALTER TABLE users`** → "I'm modifying the structure of `users`."
- **`ADD COLUMN`** → "specifically, I'm creating a new column."
- **`is_active BOOLEAN`** → "it's called `is_active`, and it stores true/false values."
- **`DEFAULT TRUE`** → "if a new row doesn't say otherwise, assume the user is active."

```text
Before:  id | name | email | gender | date_of_birth | created_at
After:   id | name | email | gender | date_of_birth | created_at | is_active
```

---

## 🤔 What DEFAULT actually promises

This deserves its own beat, because it's easy to misread.

```sql
INSERT INTO users (name, email)
VALUES ('Harry', 'harry@example.com');
```

You said nothing about `is_active`. So the database reaches for the default:

```text
name    email                  is_active
------------------------------------------
Harry   harry@example.com      TRUE
```

**`DEFAULT` means: "the value automatically used when nothing else is supplied."** It does *not* mean the value is locked in forever. You can still override it explicitly:

```sql
is_active = FALSE
```

The default is a fallback, not a cage.

---

## 🔒 Adding a column *with* a constraint

Constraints attach to new columns exactly the way they attached to columns at creation time:

```sql
ALTER TABLE users
ADD COLUMN phone VARCHAR(15) NOT NULL;
```

```text
phone
 ↓
VARCHAR(15)
 ↓
NOT NULL
```

The general shape is always:

```sql
ALTER TABLE table_name
ADD COLUMN column_name data_type constraints;
```

Nothing new to learn here — just the same vocabulary from table creation, reused mid-renovation.

---

## ➖ Dropping a column

Now imagine the opposite decision: *"we don't actually need `is_active` anymore."*

```sql
ALTER TABLE users
DROP COLUMN is_active;
```

*But here's the part that deserves a pause before you run it:*

Dropping a column doesn't just remove a label — it removes **the column and every value stored in it**, permanently.

```text
Before:
id | name | email | is_active
------------------------------
1  | A    | a@x   | TRUE
2  | B    | b@x   | FALSE

After DROP COLUMN is_active:
id | name | email
-----------------
1  | A    | a@x
2  | B    | b@x
```

That data isn't hiding somewhere. It's gone. SQL is extremely obedient and has zero emotional attachment to what you're deleting — which means the caution has to come from you, not from the tool.

---

## 🖊️ Modifying a column's definition

Suppose `name VARCHAR(100)` turns out to be too short for someone's actual name.

```sql
ALTER TABLE users
MODIFY COLUMN name VARCHAR(150);
```

```sql
ALTER TABLE table_name
MODIFY COLUMN column_name new_definition;
```

Same column, same position — just a wider definition.

---

## 🔀 Repositioning a column

*Can you move where a column sits in the table, not just what it holds?* Yes — and this is where `MODIFY COLUMN` does something you might not expect.

```sql
ALTER TABLE users
MODIFY COLUMN email VARCHAR(100) AFTER id;
```

`AFTER id` means exactly what it says: *"put `email` immediately after `id`."*

You can also send a column all the way to the front:

```sql
ALTER TABLE users
MODIFY COLUMN date_of_birth DATE FIRST;
```

```text
date_of_birth
id
email
name
gender
created_at
```

**One easy-to-miss detail:** even when you're only repositioning a column, `MODIFY COLUMN` still wants the full definition restated — `VARCHAR(100)`, `DATE`, whatever it is. You're not just writing `MODIFY COLUMN email AFTER id`. The type comes along for the ride every time.

---

## 🗺️ The ALTER TABLE map

```text
ALTER TABLE
│
├── ADD COLUMN     → add a new column
├── DROP COLUMN    → remove a column (and its data)
└── MODIFY COLUMN  → redefine, re-constrain, or reposition
                       ├── AFTER column
                       └── FIRST
```

Structure is a living surface. This is the toolkit for reshaping it without starting over.

---

## 📥 INSERT — from structure to data

Everything above changed the *shape* of the room. Now you're finally moving furniture in.

`INSERT` sits inside a bigger idea you'll keep running into — **CRUD**:

```text
C → Create   (INSERT)
R → Read     (SELECT)
U → Update   (UPDATE)
D → Delete   (DELETE)
```

Basic shape:

```sql
INSERT INTO table_name
VALUES (...);
```

---

## ⚠️ The risky way: positional inserts

```sql
INSERT INTO users
VALUES (
    '2013-07-13',
    1,
    'alice@example.com',
    'Alice',
    'Female',
    DEFAULT
);
```

This only works if you know the table's exact column order by heart — and that's exactly the problem. *What happens the moment someone reorders a column with `MODIFY COLUMN ... FIRST`?* Every positional `INSERT` written against the old order silently starts inserting the wrong value into the wrong column. Nothing crashes. It just quietly lies.

---

## ✅ The better way: name your columns

```sql
INSERT INTO users
(name, email, gender, date_of_birth)
VALUES
('Harry', 'harry@example.com', 'Male', '2012-12-01');
```

Now there's no ambiguity:

```text
name          → Harry
email         → harry@example.com
gender        → Male
date_of_birth → 2012-12-01
```

And notice what's absent from that column list: `id` and `created_at`. You don't have to mention every column — only the ones you're actually supplying.

---

## 🕳️ What happens to the columns you leave out?

This is the part worth sitting with, because it's not "nothing happens" — it's two very different automatic behaviors depending on the column:

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO users
(name, email)
VALUES
('Harry', 'harry@example.com');
```

- **`id`** is missing from the list, but it has `AUTO_INCREMENT` — so MySQL mints the next number itself.
- **`created_at`** is missing too, but it has `DEFAULT CURRENT_TIMESTAMP` — so MySQL stamps the current moment on its own.

```text
id | name  | email              | created_at
----------------------------------------------
1  | Harry | harry@example.com  | current time
```

You left two columns unnamed, and the table filled both in without you — for two completely different reasons.

---

## 🔢 AUTO_INCREMENT, watched over several inserts

```sql
INSERT INTO users (name, email) VALUES ('Alice', 'alice@example.com');
```

No `id` supplied, none needed:

```text
INSERT #1 → id = 1
INSERT #2 → id = 2
INSERT #3 → id = 3
```

Every insert, the counter just moves forward on its own.

---

## 📦 Inserting many rows at once

Writing this three separate times works, but it's not how you'd actually do it:

```sql
INSERT INTO users (name, email, gender) VALUES ('Harry', 'harry@example.com', 'Male');
INSERT INTO users (name, email, gender) VALUES ('Alice', 'alice@example.com', 'Female');
INSERT INTO users (name, email, gender) VALUES ('John', 'john@example.com', 'Male');
```

One statement can carry all three:

```sql
INSERT INTO users
(name, email, gender)
VALUES
('Harry', 'harry@example.com', 'Male'),
('Alice', 'alice@example.com', 'Female'),
('John', 'john@example.com', 'Male');
```

The comma between parentheses is doing all the work — it's the difference between three round-trips to the database and one.

*Does that mean cramming everything into a single giant INSERT is always the right move?* Not quite. The real performance gain depends on the database engine, transaction settings, network latency, indexes, triggers, and batch size. "Multiple rows can be more efficient" isn't the same claim as "every insert should contain 900,000 rows." Databases, like humans, have limits.

---

## 🎯 INSERT + DEFAULT, explicitly

You can lean on a default silently:

```sql
INSERT INTO users
(name, email, gender)
VALUES
('Harry', 'harry@example.com', 'Male');
```

Or you can say so out loud:

```sql
INSERT INTO users
(name, email, gender, created_at)
VALUES
('Harry', 'harry@example.com', 'Male', DEFAULT);
```

Both land in the same place. One just makes the intent visible in the query itself.

---

## 🆚 ALTER TABLE vs. INSERT — the line that must never blur

```text
ALTER TABLE
     ↓
"What should my table look like?"

INSERT
     ↓
"What records should be inside my table?"
```

One reshapes the container. The other fills it. Confusing the two is the fastest way to reach for the wrong command under pressure.

Zooming out one more level, here's where every command you've met so far actually lives:

| SQL command | What it changes |
|---|---|
| `CREATE TABLE` | Creates a new table |
| `ALTER TABLE` | Changes table structure |
| `INSERT` | Adds rows |
| `SELECT` | Reads rows |
| `UPDATE` | Changes existing row data |
| `DELETE` | Removes rows |
| `DROP TABLE` | Removes the entire table |

```text
DATABASE
   │
   └── TABLE
        │
        ├── STRUCTURE
        │      └── ALTER TABLE
        │
        └── DATA
               ├── INSERT
               ├── SELECT
               ├── UPDATE
               └── DELETE
```

## 💬 A quiet tool: comments

```sql
-- This is a comment
```

MySQL skips that line entirely when executing. That makes comments useful for two things: leaving yourself notes, and temporarily disabling a query without deleting it.

```sql
-- Add active status
ALTER TABLE users
ADD COLUMN is_active BOOLEAN DEFAULT TRUE;
```

Only the `ALTER TABLE` line runs. The comment is invisible to MySQL — visible only to the next person reading the script, which is often you, six months from now, wondering what you were thinking.
