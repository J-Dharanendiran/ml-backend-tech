# ⚠️ The Two Commands That Don't Ask Twice

> "SELECT only ever shows you things. UPDATE and DELETE actually touch them. The moment a command can change what's real, the rules of carelessness change with it."

Every command so far has been reversible in spirit. Add a column, you can drop it. Insert a row, you can remove it. But now you're meeting the two commands that reach directly into data that already exists — and neither one checks with you twice before acting.

```text
UPDATE  → changes existing values
DELETE  → removes existing rows
```

Both are syntactically simple. That's exactly what makes them dangerous.

---

## ✏️ UPDATE — changing what's already there

Here's the table:

| id | name  | gender | salary | email |
|---:|-------|--------|-------:|-------|
| 1  | Aarav | Male   | 65000  | aarav@example.com |
| 2  | Aisha | Female | 55000  | aisha@example.com |
| 3  | Raj   | Male   | 60000  | raj@example.com |
| 4  | Sneha | Female | 50000  | sneha@example.com |

Aarav's salary needs to drop from `65000` to `45000`:

```sql
UPDATE users
SET salary = 45000
WHERE id = 1;
```

Three moving parts, each answering its own question:

```text
UPDATE users     → which table?
SET salary=45000 → what should change?
WHERE id = 1      → which row?
```

`UPDATE` names the table. `SET` names the new value. `WHERE` names the target. Miss any one of those and the sentence stops meaning what you think it means.

---

## 🚨 Why WHERE is the whole safety mechanism

Watch what happens when you drop the last clause:

```sql
UPDATE users
SET salary = 45000;
```

No `WHERE`. So the instruction reads: *"change the salary of every row in `users`."* Not just Aarav's. Everyone's. If this table held 10,000 employees, all 10,000 would now earn the same salary — and MySQL will not pause to ask if that was intentional. It just does what you told it, precisely and without judgment.

```sql
UPDATE users
SET salary = 45000
WHERE id = 1;
```

The `WHERE` clause is the *only* thing standing between "change one row" and "change every row." It's not a formality — it's the entire difference.

---

## 🔧 Updating other columns, and more than one at once

Nothing restricts `UPDATE` to numbers:

```sql
UPDATE users
SET name = 'Aisha Khan'
WHERE email = 'aisha@example.com';
```

*"Find the user with this email, change their name."* You can also change several columns in the same statement:

```sql
UPDATE users
SET
    name = 'Aarav Kumar',
    salary = 70000,
    gender = 'Male'
WHERE id = 1;
```

```text
Row id = 1
┌────────────────────────────┐
│ name   → Aarav Kumar       │
│ salary → 70000             │
│ gender → Male              │
└────────────────────────────┘
```

One `WHERE`, three changes, one row.

---

## 👥 Updating more than one row

`WHERE` was never limited to "exactly one row." It targets *every* row satisfying a condition:

```sql
UPDATE users
SET salary = 70000
WHERE gender = 'Female';
```

Every female user gets updated — could be one row, could be a thousand. Same with:

```sql
UPDATE users
SET salary = 70000
WHERE salary < 60000;
```

Anyone earning under 60000 gets swept up.

---

## 🔁 Updating relative to the existing value

*Can you say "add 10,000 to whatever's already there" instead of setting a fixed number?* Yes — and this pattern comes up constantly:

```sql
UPDATE users
SET salary = salary + 10000
WHERE salary < 60000;
```

Look closely at `salary = salary + 10000` — the right side reads the *current* value before the left side overwrites it.

```text
50000 → 50000 + 10000 = 60000
55000 → 55000 + 10000 = 65000
```

Each row's new value depends on that same row's old value. MySQL computes it per row, not once for the whole table.

---

## 🎯 Every WHERE trick you already know still works here

Nothing new to learn — everything from querying transfers directly:

```sql
WHERE id = 5;
WHERE gender != 'Male';
WHERE salary > 60000;
WHERE salary < 60000;
WHERE salary >= 60000;
WHERE salary <= 60000;
WHERE id IN (1, 2, 3, 4, 5);
WHERE gender = 'Female' AND salary > 60000;
WHERE gender = 'Female' OR salary > 60000;
```

`WHERE` doesn't care whether it's sitting inside a `SELECT`, an `UPDATE`, or — as you'll see next — a `DELETE`. It's the same filtering logic wearing three different jobs.

```sql
UPDATE users
SET salary = 70000
WHERE id IN (1, 3, 5);
```

Only those three rows move.

---

## 🔢 Reading "rows affected"

After an `UPDATE`, MySQL Workbench reports something like:

```text
10 rows affected
```

That's a direct count: 10 rows matched your `WHERE` condition and were changed. If instead you run:

```sql
UPDATE users
SET salary = 100000
WHERE id = 9999;
```

and no user has that ID, you get:

```text
0 rows affected
```

Not an error — just an honest report that nothing matched.

---

## 🛑 Safe Update Mode and Error 1175

This is where a MySQL Workbench quirk becomes relevant. Workbench ships with **Safe Update Mode**, which can reject an `UPDATE` if the `WHERE` clause doesn't reference a key column:

```sql
UPDATE users
SET salary = 70000
WHERE salary < 60000;
```

Depending on your settings, this can throw:

```text
Error Code: 1175
```

because `salary` isn't a key column. Here's the distinction worth holding onto:

```text
SQL validity  ≠  Workbench safety restrictions
```

The SQL itself is perfectly valid. Workbench is just refusing to run it because it can't confirm you meant to touch potentially many rows. The error isn't SQL protecting you — it's the *client* protecting you from yourself.

---

## 👀 The habit that prevents disasters

Before running:

```sql
UPDATE users
SET salary = salary + 10000
WHERE salary < 60000;
```

run this first:

```sql
SELECT *
FROM users
WHERE salary < 60000;
```

Now you can actually *see* which rows are about to change, before you commit to changing them. Same `WHERE` clause, zero risk, full visibility.

---

## 🗑️ DELETE — removing rows entirely

```sql
DELETE FROM table_name
WHERE condition;
```

```sql
DELETE FROM users
WHERE id = 3;
```

*"Delete the row where id equals 3."* One row, gone.

You can delete by condition instead of by ID:

```sql
DELETE FROM users
WHERE salary < 65000;
```

Every row where salary is under 65000 is removed — however many that turns out to be.

---

## 📋 DELETE with a list, or multiple conditions

Exactly the same tools as before:

```sql
DELETE FROM users
WHERE id IN (1, 2, 3, 4, 5);
```

```sql
DELETE FROM users
WHERE gender = 'Female'
AND salary < 50000;
```

```sql
DELETE FROM users
WHERE gender = 'Female'
OR salary < 50000;
```

`AND` requires both conditions. `OR` only needs one. Nothing new — just `DELETE` borrowing the filtering vocabulary you already own.

---

## 💥 The danger that deserves its own warning

```sql
DELETE FROM users;
```

No `WHERE`. Read literally, this says: *delete every row in `users`.* The table still exists afterward — but it's completely empty. Every row you've inserted, updated, and carefully filtered throughout this whole series would simply be gone.

> **Never run `UPDATE` or `DELETE` without deliberately checking whether the `WHERE` clause is doing what you think it's doing.**

That's not a stylistic suggestion. It's the single rule that separates "I made a controlled change" from "I accidentally erased a table."

---

## 🆚 DELETE vs. DROP TABLE — a distinction that must never blur

```text
DELETE FROM users WHERE id = 3;
    → removes one row, table still exists

DELETE FROM users;
    → removes every row, table still exists (now empty)

DROP TABLE users;
    → removes the table itself — structure, columns, and data, all of it
```

```text
DELETE
└── Removes rows

DROP TABLE
└── Removes the table
    ├── structure
    ├── columns
    └── data
```

These are not degrees of the same action. `DELETE` empties a container. `DROP TABLE` destroys the container.

| Command | Removes table? | Removes rows? | Changes values? |
|---|---:|---:|---:|
| `UPDATE` | ❌ | ❌ | ✅ |
| `DELETE` (with WHERE) | ❌ | ✅ | ❌ |
| `DELETE FROM table` (no WHERE) | ❌ | ✅ All | ❌ |
| `DROP TABLE` | ✅ | ✅ | ❌ |

## 🧠 The spreadsheet mental model

```text
┌────┬────────┬────────┐
│ ID │ Name   │ Salary │
├────┼────────┼────────┤
│ 1  │ Aarav  │ 65000  │
│ 2  │ Aisha  │ 55000  │
│ 3  │ Raj    │ 60000  │
└────┴────────┴────────┘
```

`UPDATE users SET salary = 70000 WHERE id = 1;` → Aarav's row stays, one cell changes: `65000 → 70000`.

`DELETE FROM users WHERE id = 1;` → Aarav's entire row disappears. Everyone else stays exactly as they were.

`DROP TABLE users;` → the whole table, rows and structure alike, ceases to exist.

```text
DATABASE
   │
   └── TABLE
        │
        ├── ROW
        │    ├── column values
        │    └── column values
        └── ROW
```

`UPDATE` touches values inside rows. `DELETE` removes rows. `DROP TABLE` removes the table.

## 🧭 The professional workflow

Say you want to delete every user earning under `50000`. Don't reach straight for `DELETE`.

```text
Step 1 — write the condition:      salary < 50000
Step 2 — test it with SELECT:      SELECT * FROM users WHERE salary < 50000;
Step 3 — inspect the results
Step 4 — only then convert:        DELETE FROM users WHERE salary < 50000;
```

The same shape applies to `UPDATE`:

```text
SELECT  → "who will be affected?"
Inspect → confirm it's the right set
UPDATE  → "now change them"
```

`SELECT` with the exact same `WHERE` clause is a dry run. It costs nothing and shows you precisely who's about to be touched, before anything irreversible happens.

For real, production-grade work, this workflow usually sits behind one more layer — backing up the data before the destructive operation runs at all:

```text
Before dangerous operation
        ↓
Backup
        ↓
SELECT with WHERE
        ↓
Verify affected records
        ↓
UPDATE / DELETE
```

On a five-row practice table, that's overkill. As a habit to build now, before the stakes are real, it's exactly the right size.

---

## 🧩 WHERE, the same word, three different jobs

```text
SELECT → WHERE → "retrieve these rows"
UPDATE → WHERE → "modify these rows"
DELETE → WHERE → "remove these rows"
```

One clause, one piece of logic, reused across three completely different consequences. That's the thread tying this entire chapter — and the last two — together: `WHERE` is always the targeting mechanism. What changes is only what happens *after* the target is identified.

## 📚 Core syntax reference

**UPDATE**

```sql
-- one column
UPDATE users SET salary = 70000 WHERE id = 5;

-- multiple columns
UPDATE users SET name = 'Aarav Kumar', salary = 70000 WHERE id = 5;

-- multiple rows
UPDATE users SET salary = 70000 WHERE id IN (1, 2, 3);

-- relative to existing value
UPDATE users SET salary = salary + 10000 WHERE salary < 60000;
```

**DELETE**

```sql
-- one row
DELETE FROM users WHERE id = 5;

-- multiple rows
DELETE FROM users WHERE id IN (1, 2, 3);

-- conditional
DELETE FROM users WHERE salary < 50000;

-- multiple conditions
DELETE FROM users WHERE gender = 'Female' AND salary < 50000;
```

**Dangerous — never accidental**

```sql
UPDATE users SET salary = 50000;   -- every row
DELETE FROM users;                  -- every row
DROP TABLE users;                   -- the table itself
```
