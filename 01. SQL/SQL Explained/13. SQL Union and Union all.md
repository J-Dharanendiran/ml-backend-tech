# 🧱 The Rows That Stacked Themselves: `UNION` & `UNION ALL` in MySQL

> *"`JOIN` reaches sideways. `UNION` stacks upward."*

You have just finished `JOIN`s. You know how to take a `users` table and an `addresses` table and glue them **side by side** into one wider result.

Now the instructor changes the problem completely. 🎬

Two tables. Nearly identical in shape. And this time, **nothing links them together.**

---

## 📋 Two tables, one list

Meet the first table:

### `users`

| id | name  | email           |
| -: | ----- | --------------- |
|  1 | Rahul | rahul@gmail.com |
|  2 | Priya | priya@gmail.com |
|  3 | Anil  | anil@gmail.com  |

And its close cousin:

### `admin_users`

|  id | name  | email           |
| --: | ----- | --------------- |
| 101 | Anil  | anil@gmail.com  |
| 102 | Pooja | pooja@gmail.com |

Someone walks up to you and says: *"Give me one list of everyone. I don't care whether they are a regular user or an admin."*

You want this:

```text
Rahul
Priya
Anil
Pooja
```

Your first instinct, fresh from the last lesson:

> 💭 **"I just learned `JOIN`. Isn't this a `JOIN` problem?"**

Look at what a `JOIN` actually does. It needs a **relationship**: a matching column that says *this row over here belongs with that row over there.* A user and their address share a `user_id`, so they can be placed side by side.

But Rahul and Pooja? They have no relationship. They simply live in **two tables that look alike**, and you want the rows of one to continue where the rows of the other stop.

The instructor describes it exactly that way: **extending one result set with another result set.** Not widening. **Lengthening.** 📏

That is `UNION`.

---

## 🏗️ The shape of a `UNION`

> 💭 **"Okay, so how do I actually write it?"**

```sql
SELECT column1, column2
FROM table1

UNION

SELECT column1, column2
FROM table2;
```

Applied to our two tables:

```sql
SELECT name
FROM users

UNION

SELECT name
FROM admin_users;
```

Picture what happens:

```text
users                    admin_users
------                   ------------
Rahul                    Anil
Priya                    Pooja
Anil
       \                  /
        \                /
             UNION
               ↓
        Combined result
        --------------
        Rahul
        Priya
        Anil
        Pooja
```

Two separate `SELECT` statements ran. `UNION` took their outputs and **placed one underneath the other.**

Notice what did **not** happen: no tables were connected. `UNION` never touches the tables. It touches the **results**.

---

## 🧠 The one mental model to keep

Say it slowly, because it will save you from a lot of confusion later:

- **`JOIN`** combines related data **side by side** ↔️
- **`UNION`** combines compatible results **top to bottom** ↕️

```text
JOIN                             UNION
----                             -----
Table A      Table B             Result 1
A1  A2       B1  B2                 A
 |   |        |   |                 B
 └───┴────────┴───┘                 C
   (wider rows)                  Result 2
                                    D
                                    E
                                    F
                                 (more rows, same columns)
```

So do not think:

> ~~"`UNION` connects tables."~~

Think:

> **"`UNION` combines the results of `SELECT` statements vertically."**

| Question you are asking | Tool |
| ----------------------- | ---- |
| "These rows are *related*; show them together in one row" | `JOIN` |
| "These rows are *similar*; show them in one list" | `UNION` |

---

## 👯 The moment Anil shows up twice

Look back at the tables. **Anil exists in both `users` and `admin_users`.** He is a regular user *and* an admin.

You run your query:

```sql
SELECT name, email
FROM users

UNION

SELECT name, email
FROM admin_users;
```

And you get:

| name  | email           |
| ----- | --------------- |
| Rahul | rahul@gmail.com |
| Priya | priya@gmail.com |
| Anil  | anil@gmail.com  |
| Pooja | pooja@gmail.com |

> 💭 **"Wait. Where did the second Anil go? Did I lose a row?"**

You did not lose him by accident. It is the **default behavior**:

> **`UNION` removes duplicate rows.**

If the same row appears in both result sets, `UNION` returns it **only once.** The instructor demonstrates exactly this: the same person in both places comes back a single time.

### 🔁 But what if you *want* both Anils?

Then you say so out loud:

```sql
SELECT name, email
FROM users

UNION ALL

SELECT name, email
FROM admin_users;
```

| name  | email           |
| ----- | --------------- |
| Rahul | rahul@gmail.com |
| Priya | priya@gmail.com |
| Anil  | anil@gmail.com  |
| Anil  | anil@gmail.com  |
| Pooja | pooja@gmail.com |

The duplicate stays.

The whole difference fits in two lines:

```text
UNION      →  Combine  +  Remove duplicates
UNION ALL  →  Combine  +  Keep duplicates
```

| Feature            | `UNION` | `UNION ALL` |
| ------------------ | :-----: | :---------: |
| Combines results   |    ✅    |      ✅      |
| Removes duplicates |    ✅    |      ❌      |
| Keeps duplicates   |    ❌    |      ✅      |

And a small bonus from the MySQL manual: the default has a name. Writing `UNION DISTINCT` means the same thing as plain `UNION`; it just makes the intent explicit. (Sources are in the Docs Check at the end.)

## 🤔 The mystery of the missing `id`

Now look closely at the query above. You selected `name` and `email`. You did **not** select `id`.

> 💭 **"Why not just add `id` too? It's right there in both tables."**

Try it and see what happens. Anil's `id` is `3` in `users` and `101` in `admin_users`:

```sql
SELECT id, name, email FROM users
UNION
SELECT id, name, email FROM admin_users;
```

Now the two Anil rows are:

```text
3    Anil  anil@gmail.com
101  Anil  anil@gmail.com
```

Those are **different rows**. `UNION` compares the *whole row*, not just the name. So the duplicate you wanted removed is no longer a duplicate, and both Anils survive. 😅

> 🔑 **Duplicate removal only works on rows that are identical in every selected column.** Choose your columns with that in mind.

*(This consequence is my own reasoning from the "duplicate rows are removed" rule, not a line from the lecture. Test it yourself in a MySQL shell and it is easy to confirm.)*

## 🧩 The columns must line up

You are allowed to select more than one column; you saw that already. But there is a rule, and it is the one that trips people up.

> 💭 **"What if my two `SELECT`s don't return the same columns?"**

Think of stacking two spreadsheets on top of each other. The columns have to sit above one another:

```text
SELECT A, B, C
       ↓  ↓  ↓
       A  B  C

UNION

SELECT X, Y, Z
       ↓  ↓  ↓
       X  Y  Z
```

Position **1** stacks on position **1**. Position **2** on position **2**. And so on.

So this works ✅:

```sql
SELECT name, email FROM users
UNION
SELECT name, email FROM admin_users;
```

And this does not ❌:

```sql
SELECT name, email FROM users      -- 2 columns
UNION
SELECT name FROM admin_users;      -- 1 column
```

The rule from the lecture:

> **The number of columns must match across every `SELECT`, and the corresponding columns should have compatible data types.**

SQL will not invent a third column out of sheer compassion. 😌

Two more things worth knowing, both from the MySQL manual:

1. **Position matters, names do not.** The column names in the final result come from the **first** `SELECT`. The names in later `SELECT`s are ignored for naming.
2. **"Compatible" is looser than "identical."** MySQL is willing to reconcile different types rather than refuse. Still, aim for matching types in matching positions, since mismatches make the result harder to reason about.

## 🏷️ Teaching every row where it came from

Here is where `UNION` stops being a party trick and becomes a real-world tool.

After stacking users and admins, you look at the list and think:

> 💭 **"Okay, I have one big list. But which of these people are admins?"**

The information is gone. Once rows are stacked, nothing says which table each came from.

The fix, which the instructor demonstrates, is beautifully simple: **add a constant column** to each `SELECT`.

```sql
SELECT name, email, 'USER' AS role
FROM users

UNION

SELECT name, email, 'ADMIN' AS role
FROM admin_users;
```

| name  | email           | role  |
| ----- | --------------- | ----- |
| Rahul | rahul@gmail.com | USER  |
| Priya | priya@gmail.com | USER  |
| Anil  | anil@gmail.com  | USER  |
| Anil  | anil@gmail.com  | ADMIN |
| Pooja | pooja@gmail.com | ADMIN |

Read that carefully:

- `'USER'` and `'ADMIN'` are **constants**. They are not stored in any table; you invented them inside the query.
- `AS role` gives that invented column a name.
- You are no longer just combining data. You are **preserving where it came from.**

And did you notice the twist? **Anil appears twice again**, even though we used plain `UNION`. His `role` differs (`USER` vs `ADMIN`), so the rows are no longer identical. It is the same lesson as the `id` mystery, arriving from a different direction. 🎯

## 📊 The three-ad-platform problem

Now zoom out. Imagine you work in marketing analytics and your data lives in three tables:

```text
facebook_ads
google_ads
microsoft_ads
```

Each has similar metrics: `campaign`, `impressions`, `clicks`, `conversions`, `cost`. You need **one consolidated report.**

```sql
SELECT campaign, impressions, clicks, conversions,
       'Facebook' AS source
FROM facebook_ads

UNION ALL

SELECT campaign, impressions, clicks, conversions,
       'Google' AS source
FROM google_ads

UNION ALL

SELECT campaign, impressions, clicks, conversions,
       'Microsoft' AS source
FROM microsoft_ads;
```

| campaign   | impressions | clicks | conversions | source    |
| ---------- | ----------: | -----: | ----------: | --------- |
| Campaign A |       10000 |    500 |          50 | Facebook  |
| Campaign B |       12000 |    700 |          70 | Google    |
| Campaign C |        9000 |    450 |          40 | Microsoft |

The instructor calls this **cross-category reporting**: similar datasets from different sources, consolidated, with a column identifying the source.

> 💭 **"Why `UNION ALL` here and not `UNION`?"**

Because the `source` column already makes every row distinct, and because two campaigns with identical numbers on two platforms are *genuinely separate facts*, not duplicates to be erased. You do not want the database quietly merging real data. That is the moment to choose `UNION ALL`: **duplicates are legitimate, keep them.**

There is a second, practical reason. Deduplication takes work. Several tutorials note that `UNION ALL` avoids that work and is faster when you know duplicates are impossible or wanted. (These are secondary sources; see the Docs Check.)

## 🔃 Sorting the stacked result

You have your combined list. Now you want it sorted, say by date of birth:

```sql
SELECT name, date_of_birth
FROM users

UNION

SELECT name, date_of_birth
FROM admin_users

ORDER BY date_of_birth;
```

> 💭 **"Where does `ORDER BY` go? After each `SELECT`?"**

The instructor's rule: **at the very end**, once, after the last `SELECT`.

Think of it as a pipeline:

```text
SELECT 1
    ↓
SELECT 2
    ↓
  UNION
    ↓
combined result
    ↓
 ORDER BY
    ↓
sorted final result
```

You sort the **finished stack**, not the individual pieces.

One honest footnote: MySQL *does* allow ordering an individual `SELECT` inside a `UNION`, but only if you wrap that `SELECT` in parentheses, and it is mainly useful for things like `LIMIT` on one branch. For sorting the whole combined result, the rule above is the one you need.

---

## 🧭 When should you reach for `UNION`?

The instructor names three situations.

**1. Similar tables.**
`users` and `admin_users`: same structure, and you want their rows together.

**2. Combining filtered results.**
Two queries against the same table, each with its own `WHERE`, whose results share the same column structure. For instance (with a hypothetical `city` column):

```sql
SELECT name, email FROM users WHERE city = 'Chennai'
UNION
SELECT name, email FROM users WHERE city = 'Mumbai';
```

**3. Cross-category reporting.**
Facebook, Google, Microsoft: similar data from different sources, with a source column.

---

## 🔁 `JOIN` vs `UNION`, one last time

Since you just learned joins, this is the connection to lock in.

| | `JOIN` | `UNION` |
| --- | --- | --- |
| Direction | ↔️ Side by side | ↕️ One underneath another |
| Needs | A relationship between rows | Same number of columns, compatible types |
| Result shape | Wider (more columns) | Longer (more rows) |
| Example | `users` + `addresses` → `name, email, city, country` | `users` + `admin_users` → `name, email` |

> 📝 **`JOIN` = side by side. `UNION` = one underneath another.**

## 🎯 Everything, on one map

```text
                    SQL UNION
                       │
          Stacks SELECT results vertically
                       │
          ┌────────────┴────────────┐
          │                         │
        UNION                   UNION ALL
   (removes duplicates)      (keeps duplicates)
          │                         │
          └────────────┬────────────┘
                       │
        Every SELECT must line up:
   ┌───────────────────┴───────────────────┐
   │                                       │
 Same number of columns          Compatible data types
   │                                       │
   └───────────────────┬───────────────────┘
                       │
       Names come from the FIRST SELECT
                       │
    Add 'CONSTANT' AS label to track the source
                       │
              ORDER BY once, at the end
```

The three things to carry into your SQL and API preparation:

1. 🧱 **`UNION` stacks `SELECT` results vertically.**
2. 👯 **`UNION` removes duplicate rows; `UNION ALL` keeps them.** Duplicates are judged on the *entire* row.
3. 🧩 **Every `SELECT` must return the same number of columns, in compatible types, in matching positions.**

---

## 💬 Final Takeaway

> **"`JOIN` asks *who belongs together*. `UNION` asks *who belongs in the same list*. When you stack rows, choose your columns carefully, because a duplicate is only a duplicate if every column agrees."**
