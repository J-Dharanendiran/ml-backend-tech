# 🔍 The Question the Table Was Waiting For

> "A table full of rows is just a pile of facts until someone asks it a specific question. Querying is the moment the pile becomes an answer."

You've built the room, renovated it, and moved data in. Now comes the part that actually justifies all of that setup: **asking the table something and getting exactly what you asked for back.**

```text
Database
   ↓
Ask a question
   ↓
SQL query
   ↓
Database finds matching data
   ↓
Result
```

Every technique in this chapter is a different way of sharpening that question.

---

## 🗂️ SELECT * — asking for everything

Say the table looks like this:

| id | name  | email             | gender | date_of_birth | salary |
|---:|-------|-------------------|--------|----------------|-------:|
| 1  | Alice | alice@gmail.com   | Female | 1998-05-12     | 60000  |
| 2  | Harry | harry@gmail.com   | Male   | 1995-08-20     | 75000  |
| 3  | John  | john@gmail.com    | Male   | 2001-03-15     | 50000  |
| 4  | Emma  | emma@gmail.com    | Female | 1999-11-10     | 80000  |

```sql
SELECT *
FROM users;
```

The `*` says one thing: *"give me every column, no exceptions."* You already met this line building the table in the first place — here, it's doing the same job on real data.

---

## 🎯 SELECT specific columns

*Do you always need everything the table has?* Rarely. Suppose all you want is `name` and `gender`:

```sql
SELECT name, gender
FROM users;
```

| name  | gender |
|-------|--------|
| Alice | Female |
| Harry | Male   |
| John  | Male   |
| Emma  | Female |

Notice what `SELECT name, gender` is actually controlling: **which columns show up.** It says nothing about which *rows* qualify — that's a different job, coming up next.

You can even reorder columns just by reordering the list:

```sql
SELECT gender, name
FROM users;
```

The database doesn't care which order you prefer — it just mirrors back whatever order you ask for.

---

## 🚪 WHERE — the gatekeeper for rows

This is where querying stops being cosmetic and starts being useful.

```sql
SELECT *
FROM users
WHERE gender = 'Female';
```

Read it as one sentence: *"Give me every column, from `users`, but only where gender is Female."*

| id | name  | gender |
|---:|-------|--------|
| 1  | Alice | Female |
| 4  | Emma  | Female |

---

## ⚖️ SELECT vs. WHERE — the split worth memorizing

```sql
SELECT name, email
FROM users
WHERE gender = 'Female';
```

Two separate jobs are happening in that one query:

```text
SELECT → which columns?
WHERE  → which rows?
```

`SELECT` never filters rows. `WHERE` never chooses columns. Keep those two questions apart and most of SQL's filtering logic stops feeling tangled.

---

## 🔢 Comparison operators

`WHERE` becomes genuinely powerful once you can *compare* values, not just match them exactly:

| Operator | Meaning |
|---|---|
| `=` | Equal to |
| `!=` or `<>` | Not equal to |
| `>` | Greater than |
| `<` | Less than |
| `>=` | Greater than or equal to |
| `<=` | Less than or equal to |

A few in motion:

```sql
WHERE gender = 'Female';       -- exactly Female
WHERE gender != 'Male';        -- anything but Male (<> works too)
WHERE id > 10;                 -- 11, 12, 13... not 10 itself
WHERE salary < 50000;          -- strictly under 50000
WHERE salary >= 70000;         -- 70000 counts
WHERE id <= 10;                -- 10 counts
```

The `>` / `>=` distinction is small on paper but decides whether a boundary value like `70000` makes it into your results or gets left out.

## ❓ NULL — the value that isn't really a value

Suppose Harry never gave a date of birth:

| id | name  | date_of_birth |
|---:|-------|---------------|
| 1  | Alice | 1998-05-12    |
| 2  | Harry | NULL          |
| 3  | John  | 2001-03-15    |

**`NULL` means "there is no value" — missing or unknown.** It is *not* the same as `0`, `''`, the text `'NULL'`, or `FALSE`. Those are all real values. `NULL` is the absence of one.

### Finding it

```sql
SELECT *
FROM users
WHERE date_of_birth IS NULL;
```

### Finding its opposite

```sql
SELECT *
FROM users
WHERE date_of_birth IS NOT NULL;
```

*Why not just write `WHERE date_of_birth = NULL`?* Because it silently fails to work — `NULL` isn't a value you can be "equal to," it's the absence of one, so ordinary `=` comparisons can't reach it. `IS NULL` and `IS NOT NULL` exist specifically because `=` and `!=` were never built to handle "nothing."

---

## 📏 BETWEEN — asking for a range

```sql
SELECT *
FROM users
WHERE date_of_birth BETWEEN '1990-01-01' AND '1999-12-31';
```

Works identically on numbers:

```sql
SELECT *
FROM users
WHERE salary BETWEEN 50000 AND 80000;
```

```text
50000 → ✅
60000 → ✅
80000 → ✅
90000 → ❌
```

**One detail worth locking in: `BETWEEN` is inclusive in MySQL.** Both endpoints — `50000` and `80000` — are included, not just the values strictly in between.

---

## 📋 IN — asking for a list of acceptable values

Instead of stacking `OR` five times:

```sql
WHERE id = 1
   OR id = 2
   OR id = 3
   OR id = 4
   OR id = 5
```

write it once:

```sql
SELECT *
FROM users
WHERE id IN (1, 2, 3, 4, 5);
```

Same idea with text:

```sql
SELECT *
FROM users
WHERE gender IN ('Male', 'Female');
```

```text
Male    → ✅
Female  → ✅
Other   → ❌
```

`IN` is really just a shorthand for a chain of `OR`s pointed at the same column — cleaner to write, and unmistakably clearer to read.

---

## 🧩 AND — both must be true

```sql
SELECT *
FROM users
WHERE gender = 'Female'
AND salary > 70000;
```

| gender | salary | Result |
|--------|-------:|--------|
| Female | 80000  | ✅ |
| Female | 60000  | ❌ |
| Male   | 80000  | ❌ |
| Male   | 60000  | ❌ |

```text
Condition A AND Condition B → BOTH must be TRUE
```

Notice Female-with-60000 still fails. `AND` doesn't reward partial credit.

---

## 🔀 OR — at least one is enough

```sql
SELECT *
FROM users
WHERE gender = 'Male'
OR salary > 65000;
```

Walk through why each row lands where it does:

**Row: Male, 50000** → `Male = TRUE`, `salary > 65000 = FALSE` → `TRUE OR FALSE = TRUE` → returned.

**Row: Female, 70000** → `Male = FALSE`, `salary > 65000 = TRUE` → `FALSE OR TRUE = TRUE` → returned.

**Row: Female, 50000** → `Male = FALSE`, `salary > 65000 = FALSE` → `FALSE OR FALSE = FALSE` → excluded.

`OR` only needs one side to hold. `AND` needs both.

---

## 🎛️ Grouping with parentheses

Once `AND` and `OR` start mixing, parentheses stop being optional:

```sql
SELECT *
FROM users
WHERE (gender = 'Male' OR gender = 'Female')
AND salary > 60000;
```

Read it as: *"gender must be Male or Female — and, separately, salary must exceed 60000."* Without the parentheses, it's genuinely ambiguous which condition binds to which, and that ambiguity is exactly where incorrect results quietly slip in.

---

## 📶 ORDER BY — sorting the result

```sql
SELECT *
FROM users
ORDER BY date_of_birth;
```

### ASC — ascending (the default)

```sql
SELECT *
FROM users
ORDER BY salary ASC;
```

```text
40000 → 50000 → 60000 → 70000 → 80000
```

### DESC — descending

```sql
SELECT *
FROM users
ORDER BY salary DESC;
```

```text
80000 → 70000 → 60000 → 50000 → 40000
```

`ORDER BY salary` and `ORDER BY salary ASC` mean the same thing — ascending is the silent default. Writing `ASC` explicitly costs nothing and removes any doubt about what the query intends.

---

## ✂️ LIMIT — capping how many rows come back

```sql
SELECT *
FROM users
LIMIT 5;
```

*Returns at most 5 rows* — but *which* 5, exactly? On its own, `LIMIT` makes no promises about which rows you get.

### LIMIT + ORDER BY — where it actually gets useful

```sql
SELECT *
FROM users
ORDER BY salary DESC
LIMIT 5;
```

```text
1. Get users
2. Sort by salary
3. Highest salary first
4. Keep only 5 rows
```

*Why does the order of these two clauses matter so much?* Because `LIMIT` without `ORDER BY` is really saying "give me some 5 rows — surprise me." That's rarely what "top 5" actually means. Sorting first, then limiting, is what turns "some rows" into "the *right* rows."

---

## 🧵 Putting it all together

The request: *"Female users earning more than ₹70,000, sorted by salary from highest to lowest, only the first five."*

```sql
SELECT *
FROM users
WHERE gender = 'Female'
AND salary > 70000
ORDER BY salary DESC
LIMIT 5;
```

Read top to bottom, each clause answers one question:

```text
SELECT *              → which columns? all of them
FROM users             → from where?
WHERE ... AND ...      → which rows qualify?
ORDER BY salary DESC   → in what order?
LIMIT 5                → how many, at most?
```

## 🧠 The query as a pipeline

```text
              USERS TABLE
                   │
                   ↓
             ┌───────────┐
             │   WHERE   │  → filter
             └─────┬─────┘
                   ↓
             Matching rows
                   │
                   ↓
             ┌───────────┐
             │ ORDER BY  │  → sort
             └─────┬─────┘
                   ↓
               Sorted rows
                   │
                   ↓
             ┌───────────┐
             │  LIMIT    │  → restrict
             └─────┬─────┘
                   ↓
              Final rows
```

`SELECT` sits alongside this whole pipeline, deciding which *columns* of the final rows you actually get to see.

## 📚 The full reference

| SQL | Purpose | Example |
|---|---|---|
| `SELECT *` | Select all columns | `SELECT * FROM users;` |
| `SELECT col1` | Select specific columns | `SELECT name FROM users;` |
| `WHERE` | Filter rows | `WHERE gender = 'Female'` |
| `=` | Equal | `id = 5` |
| `!=` / `<>` | Not equal | `gender != 'Male'` |
| `>` | Greater than | `salary > 50000` |
| `<` | Less than | `salary < 50000` |
| `>=` | Greater/equal | `salary >= 50000` |
| `<=` | Less/equal | `salary <= 50000` |
| `IS NULL` | Find NULL | `date_of_birth IS NULL` |
| `IS NOT NULL` | Find non-NULL | `date_of_birth IS NOT NULL` |
| `BETWEEN` | Range (inclusive) | `salary BETWEEN 50000 AND 80000` |
| `IN` | Match a list | `id IN (1,2,3)` |
| `AND` | All conditions must match | `gender='Female' AND salary>70000` |
| `OR` | At least one condition | `gender='Male' OR salary>70000` |
| `ORDER BY` | Sort results | `ORDER BY salary` |
| `ASC` | Ascending (default) | `ORDER BY salary ASC` |
| `DESC` | Descending | `ORDER BY salary DESC` |
| `LIMIT` | Restrict number of rows | `LIMIT 5` |

## 🗺️ Where this sits in the bigger picture

```text
                SQL
                 │
       ┌─────────┴──────────┐
       │                    │
   STRUCTURE              DATA
       │                    │
 ALTER TABLE          ┌─────┴──────────┐
                      │                │
                   MODIFY            QUERY
                   DATA              DATA
                      │                │
                  INSERT             SELECT
                  UPDATE              WHERE
                  DELETE              ORDER BY
                                       LIMIT
```

> `ALTER TABLE` changes what the table looks like.
> `INSERT` adds data.
> `SELECT` retrieves data.
> `WHERE` decides which rows qualify.
> `ORDER BY` decides their order.
> `LIMIT` decides how many rows you receive.

That's the backbone. Joins, aggregation, grouping, subqueries, and window functions are all just this same pipeline getting more clauses stapled onto it.

## ✅ Final Takeaway

> *"`WHERE` decides who's in the room. `ORDER BY` decides who stands where. `LIMIT` decides how many you actually let through the door."*
