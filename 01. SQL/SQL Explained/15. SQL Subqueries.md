# 🪆 The Query Inside the Query: Subqueries in MySQL

> *"A subquery is simply a query whose result is being used by another query."*

Here is a question that sounds easy:

> **"Find all users whose salary is greater than the average salary."**

Try to write it in one line, and you hit a wall. 🧱

To compare each salary to the average, you need to **know the average first**. But you have not calculated it yet. It lives in the same table you are querying.

The instructor's answer is a tool that looks like ancient wizardry at first glance, but is really just this: **ask SQL one question so you can ask it another.**

The three questions this chapter answers:

| Question | Short answer |
| -------- | ------------ |
| **What is it?** | A query written inside another query |
| **Why does it exist?** | To break a complex problem into smaller pieces (divide and conquer) |
| **How does it work?** | The inner query produces a result; the outer query uses it (details below) |

---

## 📋 Our data for this chapter

Every example below runs against this `users` table. (It reuses the names from the self-join chapter, and I chose the salaries so the average matches the `61625` in the lecture notes.)

| id | name   | salary | referred_by_id |
| -: | ------ | -----: | -------------: |
|  1 | Aarav  |  80000 |           NULL |
|  2 | Ananya |  45000 |              1 |
|  3 | Sneha  |  70000 |              2 |
|  4 | Yash   |  40000 |           NULL |
|  5 | Imran  |  63000 |              1 |
|  6 | Farhan |  55000 |              3 |
|  7 | Aisha  |  90000 |              5 |
|  8 | Kabir  |  50000 |              2 |

The average, by hand: 80000 + 45000 + 70000 + 40000 + 63000 + 55000 + 90000 + 50000 = **493000**, and 493000 ÷ 8 = **61625**. ✅

## 🧩 The problem, in three small steps

The instructor's main point: **subqueries help break a complex problem into smaller problems.**

Instead of one giant mental leap, do this.

**Step 1.** Find the average salary:

```sql
SELECT AVG(salary)
FROM users;
```

```text
61625
```

**Step 2.** Find users earning more than that number. You could type it in by hand:

```sql
SELECT *
FROM users
WHERE salary > 61625;
```

That works, but you had to run Step 1 yourself and copy the number. If a salary changes tomorrow, your hard-coded `61625` is wrong.

**Step 3.** Let SQL do both steps together:

```sql
SELECT *
FROM users
WHERE salary > (
    SELECT AVG(salary)
    FROM users
);
```

That is a **subquery**.

```text
SELECT *                          ← OUTER query
FROM users
WHERE salary > (
    SELECT AVG(salary)            ← SUBQUERY (inner query)
    FROM users
);
```

Result:

| id | name  | salary | referred_by_id |
| -: | ----- | -----: | -------------: |
|  1 | Aarav |  80000 |           NULL |
|  3 | Sneha |  70000 |              2 |
|  5 | Imran |  63000 |              1 |
|  7 | Aisha |  90000 |              5 |

Four users earn above 61625. 🎯

---

## ⚙️ How SQL "sees" it

> 💭 **"What order does this run in? Does the inner query go first?"**

A good way to think about it:

```text
1. Inner query runs   →  SELECT AVG(salary) FROM users   →  61625
2. Outer query becomes →  SELECT * FROM users WHERE salary > 61625
3. Outer query returns the matching users
```

The subquery provides a **value**, and the outer query uses it.

> ⚠️ **This is a mental model, not a literal description.** MySQL's optimizer is free to execute the query differently. The manual describes cases where it rewrites subqueries into other forms (see the Docs Check). Your results stay the same; only the internal route may differ.

## ↔️ It isn't only `>`

The instructor shows you are not stuck with one operator. Swap `>` for `<`:

```sql
SELECT *
FROM users
WHERE salary < (
    SELECT AVG(salary)
    FROM users
);
```

| id | name   | salary |
| -: | ------ | -----: |
|  2 | Ananya |  45000 |
|  4 | Yash   |  40000 |
|  6 | Farhan |  55000 |
|  8 | Kabir  |  50000 |

Four users earn below the average. Above (4) plus below (4) equals all 8, since nobody earns exactly 61625.

The general shape, for a subquery in `WHERE`:

```sql
SELECT columns
FROM table
WHERE column operator (
    subquery
);
```

```text
             OUTER QUERY
                  ↓
        WHERE salary > [value]
                         ↑
                     SUBQUERY
                         ↓
               SELECT AVG(salary)
```

The manual adds one small syntax rule: **a subquery must always appear within parentheses.**

## 🔢 One value, or many? (the distinction that saves you)

This is the most important idea in the chapter, so slow down.

### The `AVG()` subquery returns **one value**

```text
61625
```

That is a **scalar** result (a single value), so a plain comparison works:

```sql
WHERE salary > (SELECT AVG(salary) FROM users)
```

### Other subqueries return **many values**

```sql
SELECT id
FROM users
WHERE salary > 50000;
```

```text
1
3
5
6
7
```

Five rows. (Kabir earns exactly 50000, so `>` leaves him out.)

Now watch what goes wrong if you treat this like a single value:

```sql
SELECT id, name, referred_by_id
FROM users
WHERE referred_by_id = (
    SELECT id
    FROM users
    WHERE salary > 50000
);
```

> ❌ **ERROR 1242: Subquery returns more than 1 row**

`=` compares against **one** value, and you handed it five. The fix is `IN`, which checks **membership in a set**:

```sql
SELECT id, name, referred_by_id
FROM users
WHERE referred_by_id IN (
    SELECT id
    FROM users
    WHERE salary > 50000
);
```

| id | name   | referred_by_id |
| -: | ------ | -------------: |
|  2 | Ananya |              1 |
|  5 | Imran  |              1 |
|  6 | Farhan |              3 |
|  7 | Aisha  |              5 |

Read it in plain English: *"Show users whose referrer is one of the people earning over 50000."*

```text
Subquery
   ↓
[1, 3, 5, 6, 7]
   ↓
IN
   ↓
each user's referred_by_id
```

The manual describes four kinds of subquery result: a **scalar** (one value), a **column** (one column, many rows), a **row**, and a **table**. Which kind you produce decides where you can use it.

| Subquery returns | Example | Use with |
| ---------------- | ------- | -------- |
| One value (scalar) | `SELECT AVG(salary) ...` | `>`, `<`, `=` |
| Many values (one column) | `SELECT id ... WHERE salary > 50000` | `IN` |

## 🪆 Queries inside queries inside queries

The instructor briefly shows that subqueries can be **nested**: a query inside a query inside another query.

```text
Outer query
    ↓
    Subquery
        ↓
        Another subquery
```

The manual confirms you can nest "to a considerable depth." Just because you *can* doesn't mean every query should look like a puzzle. 😄

Now use it for something real. Suppose the threshold isn't a fixed 50000, but **the average salary itself**:

> **"Find users referred by people who earn more than the average."**

```sql
SELECT id, name, referred_by_id
FROM users
WHERE referred_by_id IN (
    SELECT id
    FROM users
    WHERE salary > (
        SELECT AVG(salary)
        FROM users
    )
);
```

Peel it from the inside out:

| Layer | Query | Returns |
| ----- | ----- | ------- |
| 🟢 **Deepest** | `SELECT AVG(salary) FROM users` | `61625` |
| 🟡 **Middle** | `SELECT id FROM users WHERE salary > 61625` | IDs `1, 3, 5, 7` (Aarav, Sneha, Imran, Aisha) |
| 🔵 **Outer** | `... WHERE referred_by_id IN (1, 3, 5, 7)` | Ananya, Imran, Farhan, Aisha |

Final result:

| id | name   | referred_by_id |
| -: | ------ | -------------: |
|  2 | Ananya |              1 |
|  5 | Imran  |              1 |
|  6 | Farhan |              3 |
|  7 | Aisha  |              5 |

```text
Outer query
     ↓  finds referred users
    IN
     ↓
Middle subquery
     ↓  finds IDs of above-average earners
     >
     ↓
Inner subquery
     ↓  calculates the average salary
```

The same two-level idea with a fixed number, "referred by people earning above ₹75,000":

```sql
SELECT id, name, referred_by_id
FROM users
WHERE referred_by_id IN (
    SELECT id
    FROM users
    WHERE salary > 75000
);
```

Only Aarav (80000, id 1) and Aisha (90000, id 7) qualify as referrers. Aarav referred Ananya and Imran; Aisha referred nobody. So the result is **Ananya and Imran**.

---

## 🔗 A side note: this looks like your self join

You just learned self joins, and this query might ring a bell. Both use `referred_by_id` to point back into the same table.

The manual notes that subqueries "provide alternative ways to perform operations that would otherwise require complex joins." Here is the "referred by someone earning over 50000" question as a self join:

```sql
SELECT a.id, a.name, a.referred_by_id
FROM users AS a
JOIN users AS b
    ON a.referred_by_id = b.id
WHERE b.salary > 50000;
```

It should return the same four rows (Ananya, Imran, Farhan, Aisha). *(This equivalence is my own observation, not from the lecture. Run both in a MySQL shell to confirm on your data.)*

Neither form is "the right one." Subqueries read like a sequence of questions; joins read like a wiring diagram. Pick what you can read back a month from now.

## 📍 Where can a subquery live?

The instructor names **three places**: `WHERE`, `SELECT`, and `FROM`. You've seen `WHERE`. Now the other two.

### 1️⃣ In `SELECT`: a subquery as a column

Suppose you want each user's salary **and** the average, side by side:

```sql
SELECT
    name,
    salary,
    (
        SELECT AVG(salary)
        FROM users
    ) AS average_salary
FROM users;
```

| name   | salary | average_salary |
| ------ | -----: | -------------: |
| Aarav  |  80000 |          61625 |
| Ananya |  45000 |          61625 |
| Sneha  |  70000 |          61625 |
| Yash   |  40000 |          61625 |
| Imran  |  63000 |          61625 |
| Farhan |  55000 |          61625 |
| Aisha  |  90000 |          61625 |
| Kabir  |  50000 |          61625 |

The subquery calculates **one value** (61625), and it shows up as an extra column on every row.

> 💭 **"Why did the average repeat on every row?"**

Because the subquery has no connection to any particular row. It returns the same single value, and SQL attaches it to each row.

In this position, the manual says the subquery must be a **scalar operand** (one value). Returning several columns is only allowed for row comparisons.

### 🏷️ Naming the result with `AS`

```sql
) AS average_salary
```

`AS` names the calculated column. You could equally write `AS avg_salary` or `AS average_employee_salary`. The alias is simply the name you want displayed.

### 2️⃣ In `FROM`: a subquery as a temporary table

```sql
SELECT *
FROM (
    SELECT id, name, salary
    FROM users
    WHERE salary > 50000
) AS high_salary_users;
```

The inner query produces a result. The outer query treats that result **like a table**. This is called a **derived table**.

| id | name   | salary |
| -: | ------ | -----: |
|  1 | Aarav  |  80000 |
|  3 | Sneha  |  70000 |
|  5 | Imran  |  63000 |
|  6 | Farhan |  55000 |
|  7 | Aisha  |  90000 |

> ⚠️ **The alias is mandatory here.** The manual says the `[AS] tbl_name` clause is required "because every table in a `FROM` clause must have a name." Drop `AS high_salary_users` and MySQL refuses the query.

```sql
SELECT ...
FROM (
    SELECT ...
    FROM ...
) AS alias;
```

### The three places, side by side

| Where | Role of the subquery | Example |
| ----- | -------------------- | ------- |
| **`WHERE`** | Supplies a value or set for filtering | `WHERE salary > (SELECT AVG(salary) ...)` |
| **`SELECT`** | Becomes an extra column | `(SELECT AVG(salary) ...) AS average_salary` |
| **`FROM`** | Acts as a temporary table (derived table) | `FROM (SELECT ...) AS high_salary_users` |

## 🧠 The mental model to keep

Don't think:

> ~~"Subqueries are some complicated SQL feature."~~

Think:

> **"I need a result from one query, and I want to use that result inside another query."**

The progression of the lesson, as a ladder:

```text
Simple query
    ↓
Query using a calculated value
    ↓
Subquery
    ↓
Subquery returning multiple rows + IN
    ↓
Nested subqueries
    ↓
Subqueries in SELECT / WHERE / FROM
```

Once that clicks, a subquery is just **SQL asking SQL another question before answering the original one.** 🗃️

## ✅ Sanity Check: can you predict these?

Use the 8-row table above. Answer in your head first.

**1. How many users does `salary > (SELECT AVG(salary) FROM users)` return? And with `<`?**

<details>
<summary>Answer</summary>

**4 and 4.** Above: Aarav, Sneha, Imran, Aisha. Below: Ananya, Yash, Farhan, Kabir.

</details>

**2. What happens here?**

```sql
SELECT * FROM users
WHERE referred_by_id = (SELECT id FROM users WHERE salary > 50000);
```

<details>
<summary>Answer</summary>

**An error (1242, "Subquery returns more than 1 row").** The subquery returns five ids, and `=` expects one value. Use `IN`.

</details>

**3. Why is Kabir missing from `SELECT id FROM users WHERE salary > 50000`?**

<details>
<summary>Answer</summary>

His salary is **exactly** 50000, and `>` means strictly greater. Use `>=` to include him.

</details>

**4. How many rows does the `SELECT name, salary, (SELECT AVG(salary) FROM users) AS average_salary FROM users` query return, and what is in the last column?**

<details>
<summary>Answer</summary>

**8 rows** (one per user), and the last column is `61625` on every row.

</details>

**5. What is wrong with this?**

```sql
SELECT * FROM (SELECT id, name FROM users WHERE salary > 50000);
```

<details>
<summary>Answer</summary>

The derived table has **no alias**. Add one, e.g. `... ) AS high_earners;`.

</details>

**6. Users referred by people earning above ₹75,000: which rows?**

<details>
<summary>Answer</summary>

**Ananya and Imran.** Referrers over 75000 are Aarav (id 1) and Aisha (id 7). Aarav referred Ananya and Imran; Aisha referred no one.

</details>

**7. 🧪 Stretch question (beyond the lecture): what does this return?**

```sql
SELECT name FROM users
WHERE id NOT IN (SELECT referred_by_id FROM users);
```

*(Goal: "who has never referred anyone?")*

<details>
<summary>Answer</summary>

**Zero rows, surprisingly.** The subquery's list includes `NULL` (Aarav and Yash have no referrer), and when `NOT IN` meets a `NULL` in the list, no row can be confirmed as "not in it." The usual fix is to exclude nulls inside the subquery:

```sql
SELECT name FROM users
WHERE id NOT IN (
    SELECT referred_by_id FROM users
    WHERE referred_by_id IS NOT NULL
);
```

By hand: the people who appear as a referrer are ids 1, 2, 3, and 5 (Aarav, Ananya, Sneha, Imran). Everyone else has never referred anyone, so **the fixed query returns Yash, Farhan, Aisha, and Kabir.**

*(This behavior follows standard SQL null logic and I'm confident in it, but I did not verify it against the MySQL manual in this pass. Test it in a shell.)*

</details>

## 💬 Final Takeaway

> **"When one query needs an answer that another query can give, put the second inside the first. Ask whether the inner query hands back one value or many, and choose `>` or `IN` to match."**
