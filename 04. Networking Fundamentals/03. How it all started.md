# 🌐 The Network That Needed a Language: How the Internet Started

> *"Wires can connect two computers. Only rules can make them understand each other."*

You are about to follow one idea across roughly sixty years: **how the Internet started, why it was created, how the World Wide Web appeared on top of it, and why none of it works without protocols.**

You are learning networking so you can later follow a request from a browser all the way to a cloud server running an ML model. So we will not memorize a list of names and dates. We will watch each problem appear, and watch the next invention answer it.

## 🚀 It begins with a satellite

It is **1957**. The Soviet Union launches **Sputnik 1**, the first artificial satellite. In the United States the reaction is alarm: the feeling of having fallen behind in science and technology.

The US government responds. In **February 1958**, President Eisenhower's administration creates **ARPA**, the **Advanced Research Projects Agency**, widely described as a response to Sputnik, with the job of preventing "technological surprise" **[S1][S2]**.

Notice something: ARPA was **not** created to build a network. It was created to keep the US ahead in research. The network came later, as a side road that turned out to be the main highway.

> 💭 *"So why was the Internet created? Where does a network come into this?"*

Picture three research institutions:

* 🏛️ **MIT** in Massachusetts
* 🌴 **Stanford** in California
* 🌴 **UCLA** in California

Researchers at each had powerful computers. But those computers could not talk to each other. A researcher in one place who needed another place's machine or data had no easy way to reach it.

**The problem:** *How can computers at institutions far apart communicate with each other?*

The answer was **ARPANET**.

### ⚠️ Three corrections to the usual story

The lesson you are working from simplified a few things. Here is what the sources say:

1. **Stanford was really SRI.** The first four ARPANET nodes were **UCLA, the Stanford Research Institute (SRI), UC Santa Barbara, and the University of Utah**. "Stanford" in the video's list is a simplification **[S3][S4][S5]**.
2. **The date is 1969, not 1957.** The first host-to-host message was sent at **10:30 pm on 29 October 1969**, from UCLA to SRI. It was meant to be "login", but the system crashed after two letters, so the first message was **"lo"**. The full "login" went through about an hour later **[S3][S5]**.
3. **ARPANET was not built to survive a nuclear war.** That story is very popular, but Vint Cerf wrote that **Larry Roberts was clear ARPANET was intended for resource sharing**. The nuclear-survival idea came from Paul Baran's earlier work. Cerf adds that resilience came back on the table later, when he and Bob Kahn worked on the Internet **[S6][S7]**.

So the honest origin is not "war machine". It is *researchers who wanted to share computers and information.*

## 🔌 ARPANET: the first handshake

ARPANET (**Advanced Research Projects Agency Network**) was an early computer network that connected research institutions so they could exchange information.

Imagine MIT has a computer holding a research paper. Another institute wants it. Without a network, someone has to move it by physical media or some other slow route. With a network, the computers exchange data electronically:

```text
Computer A (MIT)
       |
       |  Network
       |
Computer B (Another Research Institute)
```

That is the basic idea of computer networking.

But connecting computers is only the beginning, and this is where the story turns.

**The computers must also agree on *how* to communicate.**

---

## 🗣️ The language problem

> 💭 *"What exactly is a network protocol?"*

A **network protocol is a set of rules that governs communication between devices.**

Imagine two people. Person A speaks only English. Person B understands only Tamil. They can hear each other perfectly, but they cannot communicate until they find a language they both understand.

Computers have the same problem. One application expects data in one format, another expects a different format. They need **agreed-upon rules** for sending and interpreting information. Those rules are protocols.

### Three real situations

**✉️ Example 1: Sending an email to your professor.**
Your email app talks to mail servers using protocols, each handling a different part of the job:

* **SMTP**: sends email between clients and mail servers, or between mail servers.
* **IMAP**: lets an email client access and synchronize messages stored on a mail server.
* **POP3**: lets an email client retrieve messages from a mail server.

**📹 Example 2: A video call with a friend.**
Audio and video must cross the network. Here, *delay hurts more than losing an occasional packet.*

> 💭 *"Why would losing data be acceptable?"*

Imagine a video frame gets delayed. By the time it arrives, your screen is already showing a newer frame. Waiting for the old one would make the conversation lag. So depending on the application and protocol, some lost packets are tolerated instead of resent.

**📁 Example 3: Sending a project file.**
Now you want **every byte** to arrive correctly. One missing or corrupted piece can make the file unusable. Protocols such as **TCP** provide reliable, ordered delivery of a byte stream and can retransmit missing data.

### The key takeaway from these three

Different applications need different things:

| Application | Main requirement |
| --- | --- |
| Email | Correctly send and receive messages |
| File transfer | Reliable, complete data delivery |
| Video calling | Low latency, timely audio/video delivery |
| Web browsing | Retrieve web resources and display content |

The requirement shapes which protocols an application uses.

> **Important distinction:** A protocol does not belong to just one application. The same protocol can support many different applications.

## 📬 IP, TCP, UDP: the three words you will hear everywhere

You do not need every technical detail yet. Start with each one's **role**.

### 📍 IP: the addressing system

**IP (Internet Protocol)** handles addressing and forwarding packets across interconnected networks.

Think of addressing a parcel. A postal system needs a destination. IP packets carry a **source** and a **destination** address:

```text
Source IP:      192.168.1.10
Destination IP: 142.250.x.x
```

These are illustrative addresses, not a real connection. IP helps **routers** forward packets toward their destination.

> **Remember:** IP gives addressing and packet delivery across networks, but it does **not** guarantee every packet arrives.

### 🔒 TCP: the careful courier

**TCP (Transmission Control Protocol)** provides a **reliable, ordered byte stream** between two endpoints, using mechanisms such as acknowledgments and retransmissions to recover from loss.

Imagine sending this text:

```text
THE INTERNET CONNECTS COMPUTERS
```

It may travel in several segments. TCP helps make sure the receiving application gets the bytes **in the correct order**, and that missing data is retransmitted when needed.

TCP is not magic, though: if the network itself becomes unavailable, a connection can still fail.

### ⚡ UDP: the quick messenger

**UDP (User Datagram Protocol)** sends individual datagrams **without TCP's built-in reliable, ordered delivery**. It has less protocol overhead and does not set up a connection the way TCP does.

Applications use UDP when they want to handle reliability themselves, or when avoiding retransmission delay matters. Many real-time communication systems use it.

### Side by side

| Feature | IP | TCP | UDP |
| --- | --- | --- | --- |
| Primary role | Packet addressing and forwarding | Reliable, ordered byte stream | Datagram delivery |
| Reliability | No delivery guarantee | Retransmission and ordered delivery | No built-in retransmission guarantee |
| Data unit | IP packet | TCP segment | UDP datagram |
| Typical purpose | Moving packets between networks | Applications needing reliable delivery | Applications using datagrams |

Notice: **TCP and UDP operate above IP. They do not replace IP.**

```text
        Application
             |
        TCP or UDP
             |
             IP
             |
       Network hardware
```

This is a simplified view of the protocol stack. We study the full layers later.

## 🌍 From one network to a network of networks

> 💭 *"How did the Internet grow beyond ARPANET?"*

ARPANET began by connecting research institutions. Over time, more networks and computers joined. The crucial step was adopting the **TCP/IP protocol suite**, so different networks could speak a common language.

There is a precise moment for this. On **1 January 1983**, ARPANET performed a coordinated, one-day cutover from its older host protocol (NCP) to TCP/IP. This kind of all-at-once changeover is called a **flag day** **[S8]**. At that time only around 400 hosts had to switch, which is why a single deadline was possible. At today's scale a flag day like that would be impractical **[S9]**.

Now picture two separate networks connected by routers:

```text
University Network
        |
      Router
        |
     Internet
        |
      Router
        |
Company Network
```

The university and the company do not need to share one physical network. Routers forward packets between them using IP.

So the Internet is not one giant computer network built in one place:

> **It is a global system of interconnected networks.** That is why people call it a *network of networks*.

## 🕸️ A different invention: the World Wide Web

Now the story takes a turn that confuses almost everyone.

> 💭 *"Is the Internet the same thing as the Web?"*

No. The Web came **later** and solved a **different** problem.

Imagine you are researching machine learning. You find a document on linear regression. Inside it, a reference to *gradient descent*. You want to jump straight to that explanation, without hunting through a pile of documents. A system of interconnected documents with **clickable links** makes this easy.

That is the idea behind the **World Wide Web (WWW)**: a system of interlinked resources accessed over the Internet using web technologies.

It was invented by **Tim Berners-Lee** while working at **CERN**. He wrote his first proposal in **March 1989**. By the end of 1990 he had the first web server and browser running at CERN **[S10]**, and the first website was made public on **6 August 1991** at `info.cern.ch` **[S10][S11]**.

The Web uses three core technologies. Let's see each.

### 🧱 HTML: the structure of a page

```html
<h1>Introduction to Machine Learning</h1>

<p>Machine learning allows systems to learn patterns from data.</p>

<a href="https://example.com">Read more</a>
```

A heading, a paragraph, and a hyperlink.

### 🏷️ URL: the address of a resource

```text
https://example.com/articles/ml
```

* `https`: the scheme
* `example.com`: the host
* `/articles/ml`: the path

The browser uses this to request the resource.

### 🤝 HTTP: the conversation

HTTP defines how a web client and server exchange requests and responses:

```text
Your Browser
     |
     | HTTP Request
     v
Web Server
     |
     | HTTP Response
     v
Your Browser
```

The response might be HTML, an image, JSON, or something else, depending on the request.

### Putting them together

You open a machine learning website:

1. You enter the URL in your browser.
2. The browser works out how to reach the server, typically using **DNS** to resolve the hostname.
3. The browser establishes the necessary network connection.
4. It sends an **HTTP request**.
5. The server returns an **HTTP response**.
6. The browser processes the response and displays the page.

This is simplified. Modern connections can involve HTTPS, TLS, TCP, QUIC and more.

> **The Internet provides the connectivity. The Web is a service that runs over it.**

## ⚖️ Internet vs. World Wide Web

| Internet | World Wide Web |
| --- | --- |
| A global system of interconnected networks | A system of interlinked web resources |
| Uses IP and other networking protocols | Uses technologies such as HTTP, HTML and URLs |
| Supports many services | One service that operates over the Internet |
| Supports email, web browsing, online gaming and more | Supports websites and web applications |

* Open a website in your browser → you are using the **Web**.
* Send email through a mail app → an Internet service that does not necessarily involve the Web.
* Play an online game → Internet connectivity, without the Web being the main channel.

> **The Web depends on the Internet, but the Internet is not limited to the Web.**

## 🗄️ Where does a website actually live?

> 💭 *"If websites are published by web servers, what is actually on the server?"*

Suppose you build an ML application and deploy it. It has a web page, backend code, and a trained model:

```text
       User's Browser
              |
              | HTTP Request
              v
         Web Server
              |
              v
        Backend API
              |
              v
       Machine Learning
            Model
              |
              v
        Prediction
              |
              v
         HTTP Response
              |
              v
       User's Browser
```

But a web server does not necessarily hold everything:

* HTML, CSS and JavaScript may be served as **static resources**.
* **Backend code** runs in an application environment.
* **Data** may live in a database.
* A **trained ML model** may be a file, or loaded into application memory.

These can sit on one machine or be spread across several. This is exactly where networking starts connecting to **APIs, Docker, cloud computing and ML deployment**.

## 🔎 The problem of finding things

The Web grows. Thousands of documents. You can reach a page by typing its URL or following a link. But:

> 💭 *"What if I want a topic and I don't know any URL?"*

That is a **discovery problem**. Early on, websites linked to each other and directories organized resources by hand. As the Web expanded, that stopped scaling. **Search engines** let you find resources by submitting a query.

A simplified search engine:

1. **Crawling**: software discovers web pages.
2. **Indexing**: information about those pages is processed and organized for retrieval.
3. **Query processing**: the engine interprets your search.
4. **Ranking**: relevant results are ordered.
5. **Results**: you receive a list of pages to explore.

> 💭 *"Was Yahoo the first search engine?"*

The video suggests so. That needs qualification:

* **Archie**, built by McGill student Alan Emtage, went live in **September 1990**, before the Web was public and before Yahoo. It indexed file names on FTP sites **[S12][S13]**.
* **Yahoo** began in **1994** as a directory of websites created by Jerry Yang and David Filo, which became a popular web directory **[S12]**.

So the idea to keep is not "who was first". It is that **search engines solved the problem of finding information across an expanding Web.**

## 📜 Who writes the rules?

Now the deepest question of the chapter.

> 💭 *"If developers around the world build different applications, how can those applications ever communicate?"*

Imagine two developers.

Developer A's app sends:

```text
USER: Dharan
MESSAGE: Hello
```

Developer B's app expects:

```json
{
  "username": "Dharan",
  "message": "Hello"
}
```

Without a compatible format and process, the two apps cannot reliably exchange information. **Protocols provide the common rules.** But who creates those protocols?

### 📝 RFC: Request for Comments

An **RFC** is a document in a long-running series used to record Internet technical specifications, and the series covers both standards documents and general contributions from the research and engineering community **[S14]**.

> **Not every RFC is an Internet standard.** IETF documents are a large part of the RFC series, but not all of it **[S14]**.

### 🏛️ The organizations

The video credited the Internet Society. That is an oversimplification. Several bodies share the work:

| Organization | General role | Source |
| --- | --- | --- |
| **Internet Society (ISOC)** | An international organization concerned with the growth and evolution of the Internet; the IETF operates under the ISOC umbrella | [S15][S16] |
| **IETF** | Develops many Internet protocol standards through an open process; produced, for example, HTTP/3 (RFC 9114) | [S15][S17] |
| **IANA** | Maintains registries of protocol parameters for IETF standards | [S15][S16] |
| **W3C** | Develops Web standards; founded by Tim Berners-Lee in 1994 at MIT | [S10] |

> **The important idea:** the Internet has no single central authority that invents and controls every technical rule. Different organizations and communities coordinate standards, registries and specifications.

## 🤖 One click, every layer: the whole chapter in motion

Let's connect everything with an example from your own world.

You built an **image classification app** and deployed it to a cloud server. You open it in a browser and upload an image. What happens?

1. **🕸️ The Web.** You enter a URL. It identifies the resource.
2. **📖 DNS.** The browser needs a network address for the hostname. DNS helps resolve it to an IP address.
3. **📍 IP.** Your computer sends packets toward the server's IP address. Routers forward them across networks.
4. **🚚 Transport.** Depending on the connection: **TCP** or **QUIC**. HTTP/1.1 and HTTP/2 are commonly used over TCP, while **HTTP/3 uses QUIC, which is built on UDP** **[S17]**.
5. **🤝 HTTP.** Your browser sends an HTTP request. With an upload, the request can carry the image data.
6. **⚙️ Backend API.** The server passes the image to application code.
7. **🧠 ML model.** The app preprocesses the image and runs it through the trained model, which produces a prediction.
8. **📨 Response.** The backend returns the prediction in an HTTP response, perhaps as JSON. Your browser displays it.

```text
             YOU
              |
              v
       Web Browser
              |
              v
          DNS Lookup
              |
              v
       IP Connectivity
              |
              v
     TCP or QUIC Transport
              |
              v
         HTTP Request
              |
              v
        Cloud Server
              |
              v
          Backend API
              |
              v
       ML Model Inference
              |
              v
        Prediction Result
              |
              v
        HTTP Response
              |
              v
       Web Browser
              |
              v
             YOU
```

Real implementations are more complex, but this is a useful mental model.

## 🔗 ML Bridge

Look at that flow again. **Your trained model is only one box inside it.** Everything else is the networking story of this chapter.

| Networking idea | Where it shows up in ML work |
| --- | --- |
| **Protocol** (agreed format) | A model API expects a specific JSON shape. If the client sends a different shape, the request fails, just like Developer A and Developer B |
| **HTTP request/response** | Calling a prediction endpoint is an HTTP request; the prediction comes back as a response |
| **URL** | The endpoint address of your deployed model |
| **DNS and IP** | How a client finds your server in the cloud |
| **Web server and backend** | The layer that receives the request and hands the image or features to your model |
| **Internet vs Web** | A model service can be reached through the Web (a page) or called directly by another program; both ride on the same Internet |

When you later learn **FastAPI, Docker and cloud deployment**, you will be building the "Cloud Server → Backend API → ML Model" part of that diagram. The rest is already provided by the Internet.

## 🌀 Deepest Realization

Go back to where we started. ARPA built a network so computers could share resources. That was a **wiring** problem.

The moment computers were wired together, a harder problem appeared: **agreement**. Format, order, addressing, reliability, discovery, who decides. Every later invention in this story, whether TCP/IP, HTTP, the Web, search engines or RFCs, is an answer to a question of the form:

> **"We can already connect. How do we agree?"**

That is why the story is mostly about protocols, not about cables. And it is why a model that works perfectly on your laptop still needs an agreed interface before anyone else can use it.

## 🧠 The 80/20: what to keep

You do not need to memorize every date. Keep these eight ideas first:

| Concept | What you should understand |
| --- | --- |
| ARPANET | An early network connecting research institutions |
| Internet | A global system of interconnected networks |
| Protocol | Rules governing communication between systems |
| IP | Addressing and packet forwarding |
| TCP | Reliable, ordered byte-stream delivery |
| UDP | Datagram delivery without TCP's built-in reliability |
| World Wide Web | A system of interlinked web resources accessible over the Internet |
| HTTP | A protocol for web requests and responses |

And three supporting ideas:

* **URL**: identifies a resource and how to access it.
* **DNS**: helps resolve domain names to IP addresses.
* **Web server**: receives requests and serves web resources or application responses.

### Your mental model

* The **Internet** is the infrastructure connecting computers and networks.
* **IP** is the addressing and packet-forwarding system.
* **TCP and UDP** are transport protocols with different delivery characteristics.
* The **Web** is a system of linked resources that uses the Internet.
* **HTTP** lets web clients and servers exchange requests and responses.
* **Protocols** in general are the agreed rules that let independently built systems communicate.
