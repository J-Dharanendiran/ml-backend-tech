# 🗣️ The Language the Browser Speaks: HTTP and Its Four Verbs

> *"You typed a web address and pressed Enter. A page appeared. Somewhere between those two moments, two machines that have never met agreed on how to talk to each other. That agreement has a name: HTTP."*

---

## 🌍 You Already Own Most of the Pieces

By now you have collected a lot of networking vocabulary:

- **client-server architecture** (who asks, who answers)
- **IP addresses** (where a machine lives)
- **ports** (which door on that machine)
- **routers** (who forwards traffic between networks)
- **TCP/IP and the OSI model** (how data is carried, layer by layer)

But every one of those pieces answers a question about *delivery*. None of them says what the message *means*. If the network is the postal system, we still need the language written on the letter.

That language, for the web, is **HTTP**.

---

## 🧭 So What Exactly Is HTTP?

You open Google Chrome and type:

`https://www.google.com`

Chrome now needs resources from a server in order to show you a page.

> 💭 *"But how does my browser communicate its request to the server? How does the server know what my browser wants? And how does my browser understand the answer?"*

All three questions have the same answer. **HTTP defines the rules for this conversation.**

HTTP stands for **Hypertext Transfer Protocol**. It is an **application-layer protocol** that defines how a client requests resources from a server and how the server responds.

Think of it as a common language. If the browser spoke French and the server spoke Tamil, delivery would still work (the parcel arrives), but nobody would understand the letter. HTTP is the agreed language.

Here are the words you need before going further:

| Term | Meaning | Example |
| --- | --- | --- |
| **Client** | The software that initiates a request | Google Chrome |
| **Server** | The software that receives the request and sends a response | Google's web server |
| **HTTP** | The protocol that defines how requests and responses work | Asking the server for a web page |
| **HTTP request** | A message sent by the client | *"Give me the search page."* |
| **HTTP response** | A message sent by the server | The requested page, or an error message |

This is the client-server model you already learned, now with a *language* attached to it.

## 🚶 The Journey of One Request

Let's follow a single request from the moment you press Enter.

### 1️⃣ You enter a URL

You type:

`https://example.com/products`

Your browser reads this as: *"Get me a resource from the server behind example.com."*

| Component | Meaning |
| --- | --- |
| `https` | The scheme: secure HTTP communication |
| `example.com` | The domain name identifying the server you want |
| `/products` | The path identifying the resource you want |

> 💭 *"What is the difference between the domain and the path?"*

The **domain** tells the world *which server* to talk to. The **path** tells that server *which thing* you want. Domain = the building. Path = the room inside it.

### 2️⃣ Your browser finds the server

Your computer cannot send traffic to the name `example.com` the way it sends traffic to an IP address. It first needs the address. Your browser and operating system use mechanisms such as **DNS** to turn the domain name into an IP address.

Imagine the name resolves to `203.0.113.10`. (This is an illustrative address, not the real one for example.com.)

Now your router, your internet service provider, and the rest of the networking infrastructure carry the traffic toward that address.

> ⚠️ **Notice something important:** DNS and routing are *not* HTTP. They are the surrounding machinery that lets HTTP happen. HTTP has not even spoken yet.

### 3️⃣ A communication path is established

Before HTTP messages can flow, the client needs a transport path to the server. Which one depends on the HTTP version:

| HTTP version | Common transport |
| --- | --- |
| HTTP/1.1 | TCP |
| HTTP/2 | TCP |
| HTTP/3 | QUIC, which uses UDP underneath |

- For HTTP/1.1 and HTTP/2, **TCP** provides reliable transport. For HTTPS over TCP, **TLS** adds encryption and integrity checks.
- HTTP/3 replaces TCP with **QUIC**, which provides reliable streams and security while running over UDP.

> 📝 So the classic statement "HTTP runs on top of TCP" is true for the traditional versions, and needs this qualification for HTTP/3.

### 4️⃣ The browser sends an HTTP request

Now the browser finally speaks. Conceptually it says:

> *"Please provide the resource located at `/products`."*

It can also add extra information: what content types it accepts, who it is, and authentication details. We will open up this message in a moment.

### 5️⃣ The server processes the request

The server receives the request and decides how to handle it. For `GET /products`, it might pull product information from a database and assemble a reply.

The browser has no idea *how* the server got that information. It only needs both sides to follow the same protocol. That is the power of an agreed language.

### 6️⃣ The server sends an HTTP response

A successful response carries:

- a **status code** that reports the outcome,
- **headers** describing the response,
- the requested **content**, when applicable.

### 7️⃣ The browser displays the website

> 💭 *"Is a website just one file that gets downloaded?"*

No. A page usually needs an HTML document, CSS files, JavaScript files, images, fonts, and more. After the first response, the browser makes **additional requests** for each of them:

```text
Browser
   |
   | HTTP request for the HTML document
   v
Web server
   |
   | HTTP response containing HTML
   v
Browser
   |
   | HTTP request for a CSS file
   v
Web server
   |
   | HTTP response containing CSS
   v
Browser
   |
   | HTTP request for an image
   v
Web server
   |
   | HTTP response containing the image
   v
Browser renders the page
```

That is why loading one page can involve dozens of requests.

> 🎯 **The central idea:** HTTP defines the request-response conversation. It does **not** replace DNS, IP, TCP, UDP, or routers.

## 📦 HTTP vs TCP vs IP: Who Does What?

> 💭 *"I keep mixing these up. What is the difference between HTTP, TCP, and IP?"*

Picture sending a parcel to someone. Several parties share the job:

| Technology | Main responsibility | Analogy |
| --- | --- | --- |
| **HTTP** | Defines what the client requests and how the server responds | The contents and instructions of your message |
| **TCP** | Provides reliable, ordered transport of data | A delivery service that tracks the parcel and handles missing pieces |
| **IP** | Handles addressing and forwarding packets across networks | The destination address used to route the parcel |
| **DNS** | Resolves a domain name to an IP address | Looking up an address from a person's name |

*These analogies are illustrations, not exact technical equivalents.*

Now watch them cooperate on this message:

```http
GET /products HTTP/1.1
Host: example.com
```

- **HTTP** gives the message its meaning.
- **TCP** (for a TCP connection) carries the bytes reliably and in order.
- **IP** addresses and forwards the packets.
- **Routers** pass the packets between networks toward the destination.
- The **server's HTTP software** finally interprets the request.

> **HTTP does not tell a router which page to return. HTTP tells the *server* what resource the client is asking for.**

## ✉️ What Does an HTTP Request Actually Look Like?

An **HTTP request is a message sent by a client to a server asking it to perform an operation on a resource.**

When you open a product page, your browser could send this simplified HTTP/1.1 request:

```http
GET /products HTTP/1.1
Host: example.com
Accept: text/html
```

Let's read it piece by piece, like reading a letter.

### 🔤 The method: `GET`

The method says **what kind of operation** the client wants. `GET` means *"retrieve this resource."*

### 📍 The path: `/products`

This identifies the resource on the server. Different paths can point to different resources or endpoints:

```text
/products
/products/42
/users
/users/15
```

The server's software decides how each path is handled.

### 🔢 The version: `HTTP/1.1`

This names the HTTP version of the illustrative request. HTTP/1.1 is a readable, text-based format, which makes it ideal for learning. HTTP/2 and HTTP/3 use different wire formats, but the meanings of methods, status codes, and headers stay consistent.

### 🏷️ The headers

```http
Host: example.com
Accept: text/html
```

Headers are extra information about the request.

- **`Host: example.com`** names the hostname the request targets.
- **`Accept: text/html`** says the client can accept an HTML representation.

### The four parts of an HTTP/1.1 request

| Part | Purpose |
| --- | --- |
| **Request line** | Identifies the method, target, and HTTP version |
| **Headers** | Carry metadata about the request |
| **Blank line** | Separates the headers from the body |
| **Body** | Carries request content when needed (optional) |

A `GET` normally needs no body. A `POST` usually does:

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json

{"name":"Alice","age":21}
```

- **Request line:** the client is submitting information to the `/users` endpoint.
- **Headers:** they name the host, describe the submitted content, and state the response format the client accepts.
- **Blank line:** the end of the headers.
- **Body:** the data being submitted.

What the server does with that data is up to its software. It might validate it, create a user, and save it to a database.

## 🔨 The Four Verbs: GET, POST, PUT, DELETE

> 💭 *"What are GET, POST, PUT, and DELETE?"*

The **HTTP method tells the server what kind of operation the client intends**. To make the four verbs concrete, imagine a product-management application that holds this product:

```json
{
  "id": 42,
  "name": "Keyboard",
  "price": 1500
}
```

### 📖 GET: *"Show me."*

You want to see product 42:

```http
GET /products/42 HTTP/1.1
Host: example.com
Accept: application/json
```

The server might reply:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 42,
  "name": "Keyboard",
  "price": 1500
}
```

> **GET means retrieve a resource.** It should not be used to request a change to the server's state.

### ➕ POST: *"Here, handle this."*

You want to add a new product:

```http
POST /products HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "name": "Mouse",
  "price": 800
}
```

The application might validate and save it, then answer:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 43,
  "name": "Mouse",
  "price": 800
}
```

`201 Created` says a resource was created.

> **POST means submit data for processing by the target resource.** It is not limited to registration forms. Its exact effect depends on how the server implements it, and APIs use it for many kinds of operations.

### ♻️ PUT: *"Replace it with this."*

You want to change product 42:

```http
PUT /products/42 HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "name": "Mechanical Keyboard",
  "price": 2500
}
```

If the server supports this successfully, the product becomes:

```json
{
  "id": 42,
  "name": "Mechanical Keyboard",
  "price": 2500
}
```

The key word is **replacement**, not merely "sending some data." How fields like the ID are treated depends on the API's implementation.

> **PUT requests replacement of the target resource's representation.**

### 🗑️ DELETE: *"Remove it."*

```http
DELETE /products/42 HTTP/1.1
Host: example.com
```

If appropriate, the server deletes the resource and may answer:

```http
HTTP/1.1 204 No Content
```

`204 No Content` means success, with no response body.

> **DELETE requests removal of the specified resource.**

### The four verbs side by side

| Method | Intended operation | Example |
| --- | --- | --- |
| **GET** | Retrieve a resource | View product 42 |
| **POST** | Submit data for processing | Add a product |
| **PUT** | Replace a resource's representation | Replace product 42's details |
| **DELETE** | Delete a resource | Delete product 42 |

One more useful detail: PUT and DELETE are defined as **idempotent**. Repeating an identical request has the same intended effect on server state as sending it once. Delete product 42 twice and the end state is the same: it is gone. **POST has no such general guarantee**: send "add a Mouse" twice and you may get two Mice. As always, real behavior depends on how the server implements the endpoint.

## 📬 What Happens When the Server Replies?

Sending a request is only half of the conversation. The server must communicate the outcome. Take this request:

```http
GET /products/42 HTTP/1.1
Host: example.com
Accept: application/json
```

If product 42 exists, the server might respond:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 47

{
  "id": 42,
  "name": "Keyboard",
  "price": 1500
}
```

*(The Content-Length number here is illustrative, not an exact byte count for the displayed body.)*

A response has three parts:

1. **The status line**: `HTTP/1.1 200 OK` names the version and reports the result. `200` means the request succeeded.
2. **The response headers**: `Content-Type` names the media type of the body, and `Content-Length` gives the body's length in bytes when applicable.
3. **The response body**: the actual product information the client will display or use.

### 🚦 Status codes worth recognizing

| Status code | Meaning | Example |
| --- | --- | --- |
| `200 OK` | The request succeeded | Product information retrieved |
| `201 Created` | A resource was created | A new product was added |
| `301 Moved Permanently` | The resource has a permanent redirect | A page redirects to a new URL |
| `400 Bad Request` | The server cannot process the request because it is invalid | Malformed request data |
| `401 Unauthorized` | Authentication is required or has failed | The request lacks valid authentication |
| `403 Forbidden` | The server refuses the requested operation | The user lacks permission |
| `404 Not Found` | The requested resource was not found | Product ID does not exist |
| `500 Internal Server Error` | The server hit an unexpected problem | An unhandled server-side error |

The status code reports the *outcome*. The body can carry the details. For example, a `404` response might include a JSON body explaining that the product does not exist.

## 🏷️ The Headers: Why Are There So Many?

When you inspect a real request in Chrome, you will see headers such as `Accept`, `Accept-Encoding`, `Accept-Language`, `Cookie`, and `Connection`.

> 💭 *"Why does my browser send so many headers? What are they all for?"*

Because every request needs context. A typical request from Chrome might look like this (illustrative; real headers vary by browser, site, and HTTP version):

```http
GET /products HTTP/1.1
Host: example.com
Accept: text/html, application/xhtml+xml
Accept-Encoding: gzip, br
Accept-Language: en-IN
Cookie: session_id=example123
```

| Header | Purpose |
| --- | --- |
| `Host` | Identifies the target hostname in HTTP/1.1 |
| `Accept` | Says which response media types the client can accept |
| `Accept-Encoding` | Says which content encodings (such as compression formats) are supported |
| `Accept-Language` | Says what language the client prefers |
| `Cookie` | Sends applicable cookies to the server |

Three of them deserve a closer look:

- **`Accept: text/html`** means *"I can handle HTML."* An API client might send `Accept: application/json` instead, and the server may use that to choose a suitable response format.
- **`Accept-Language: en-IN`** states a language preference. A site with multiple language versions may use it to choose one.
- **`Cookie: session_id=example123`** sends a cookie tied to the request's domain and path. Cookies help a site recognize a session across requests, for example to remember who is logged in.

That last one opens a puzzle.

## 🧠 Why Is HTTP Called "Stateless"?

> 💭 *"If HTTP is stateless, how does a website remember that I'm logged in?"*

First, what does *stateless* mean? Suppose you visit a shopping site and send:

```http
GET /products HTTP/1.1
Host: example.com
```

Later you send:

```http
GET /cart HTTP/1.1
Host: example.com
```

At the protocol level, the second request does **not** inherently carry the history of the first. **Each request is treated as independent**, not automatically inheriting application state from earlier ones.

But a shopping site that forgot you between every click would be useless. You log in, add an item to your cart, and expect the site to remember.

> 💭 *"So how do websites solve this?"*

They build memory **on top of** HTTP, using **cookies and session identifiers**. After you authenticate, the server might reply:

```http
HTTP/1.1 200 OK
Set-Cookie: session_id=example123; HttpOnly; Secure
```

The browser may then attach that cookie to later requests that apply:

```http
GET /cart HTTP/1.1
Host: example.com
Cookie: session_id=example123
```

The application uses the session identifier to connect this request to an existing session, and now the cart is yours.

> 🔑 **The distinction that matters: HTTP stays stateless even when applications build stateful sessions on top of it.** The protocol forgets. The application remembers, using a token the browser keeps handing back.

## ❓ The Question Mark in the URL

You have surely seen URLs like this:

```text
https://example.com/search?q=python
```

> 💭 *"What does the `?` mean, and where does `q=python` go?"*

| Component | Meaning |
| --- | --- |
| `https` | URL scheme |
| `example.com` | Hostname |
| `/search` | Path |
| `?` | Begins the query string |
| `q=python` | A query parameter |

The server receives the path and the query as part of the **request target** and can use them to decide what to return. Here is a URL with two parameters:

```text
https://example.com/products?category=books&sort=price
```

```text
category=books
sort=price
```

The application might read this as *"books, sorted by price."* But the parameters do not perform that operation on their own. **The server's application has to implement the behavior.**

### How it looks inside the request

In HTTP/1.1:

```http
GET /products?category=books&sort=price HTTP/1.1
Host: example.com
Accept: application/json
```

The parameters live in the **request target**, right after the path. A POST carries its data differently, in the **body**:

**GET with a query parameter:**

```http
GET /products?category=books HTTP/1.1
Host: example.com
```

**POST with a body:**

```http
POST /products HTTP/1.1
Host: example.com
Content-Type: application/json

{"category":"books"}
```

Both deliver information to the server. They just use different compartments of the message.

> ⚠️ **A practical warning:** HTTPS encrypts the request and response in transit, but that does not make it safe to put secrets in a URL. Query parameters can show up in browser history, server logs, and other places. Never put passwords or secret tokens in URLs.

## 🔍 Watch It Happen: The Chrome Network Tab

Reading about requests is useful. Seeing real ones is better.

> 💭 *"How can I see real HTTP requests in Google Chrome?"*

1. **Open a website**, for example `https://example.com`.
2. **Open Developer Tools**: right-click the page and choose **Inspect**, or press `Ctrl + Shift + I`.
3. **Select the Network tab** at the top of Developer Tools.
4. **Reload the page** with `Ctrl + R`. Entries start appearing: HTML documents, JavaScript, CSS, images, and other resources.
5. **Click one entry** to see its details.

Depending on the request and your Chrome version, you can inspect:

| Section | What you can examine |
| --- | --- |
| **General** | Request URL, request method, and status code |
| **Request Headers** | Headers sent by the client |
| **Payload** | Submitted request data, when present |
| **Response Headers** | Headers returned by the server |
| **Preview** | A formatted view of supported response content |
| **Response** | The response content |

Click an API request and you might see:

```text
Request URL: https://example.com/products/42
Request Method: GET
Status Code: 200 OK
```

and, in the response:

```json
{
  "id": 42,
  "name": "Keyboard",
  "price": 1500
}
```

Now the abstractions become observable. You can see what the client asked for, how the server answered, and how the exchange fits the larger page-loading process. That beats memorizing header names without ever looking at a real one.

## 🤖 ML Bridge: Where HTTP Meets Your Models

HTTP matters even more once you start building APIs.

A frontend talks to a backend over HTTP. The backend can expose **endpoints that return data** instead of full HTML pages. Suppose you build a spam classifier and expose:

```text
POST /predict
```

A frontend (or any other app) sends the email text:

```http
POST /predict HTTP/1.1
Host: localhost:8000
Content-Type: application/json

{
  "text": "Congratulations! You have won a prize."
}
```

Your FastAPI application receives it and might:

1. **Validate** the incoming data.
2. **Pass** the text to a trained machine learning model.
3. **Get** the model's prediction.
4. **Return** it to the client.

The response might be:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "prediction": "spam",
  "confidence": 0.97
}
```

*(The JSON is illustrative, and the confidence value is not the output of a real model.)*

The whole flow in one line:

```text
Client → HTTP request → FastAPI backend → ML model → HTTP response → Client
```

FastAPI gives you the tools to define endpoints and process requests. HTTP supplies the conventions both sides rely on. The same pattern works for an image-classification API or any other ML application you build.

And notice how the four verbs map onto a model service:

| Verb | What it could mean for your ML app |
| --- | --- |
| `GET` | Fetch a stored result or a model's metadata |
| `POST` | Send data in and ask the model to predict |
| `PUT` | Replace a stored record or configuration |
| `DELETE` | Remove a stored record |

## 🧩 Putting the Whole Picture Together

You open a browser and request a product page. Here is who does what:

| Layer or component | What it contributes |
| --- | --- |
| **Application** | The browser requests a web resource |
| **HTTP** | Defines the request method, target, headers, and response semantics |
| **TLS** (when used) | Protects HTTP communication in transit |
| **TCP or QUIC** | Provides the transport mechanism, depending on the HTTP version |
| **IP** | Supports addressing and packet forwarding |
| **Routers and network infrastructure** | Carry traffic toward the destination |
| **Web server and application** | Process the request and generate a response |
| **Browser** | Interprets the response and renders the content |

And the concepts, each as the question it answers:

- **HTTP:** What does the client want, and what did the server return?
- **TCP:** How can data be moved reliably between endpoints?
- **IP:** How can packets be addressed and forwarded across networks?
- **DNS:** How can a domain name be resolved to an IP address?
- **HTTP methods:** What kind of operation is the client requesting?
- **HTTP headers:** What extra information accompanies the message?
- **HTTP status codes:** What was the outcome?
- **HTTP body:** What content is being sent?
- **Cookies and sessions:** How can an application tie successive requests to one user's session?

2. Why does loading one web page usually trigger many HTTP requests?
3. You send the identical `DELETE /products/42` twice. Why is the *intended* end state the same as sending it once? Why is this not guaranteed for `POST`?
4. A site says HTTP is stateless, yet it remembers you after login. What mechanism bridges the gap?
5. Which part of the journey is **not** HTTP: resolving `example.com` to an IP address, or sending `GET /products`?

<summary>Answers</summary>

2. The HTML document references CSS, JavaScript, images, and fonts, and each of those is fetched with its own request.
3. DELETE is idempotent: once product 42 is gone, repeating the request leaves the same state. POST has no general idempotence guarantee, so repeating it may create a second resource.

## 🌀 Deepest Realization

When your browser opens a website, it does not magically download "the website" in one mysterious operation.

It **asks**, the server **answers**, and when the answer says *"I also need an image, a stylesheet, and a script,"* it asks again. A page is the result of a long polite conversation, and every sentence of that conversation has the same anatomy: a method, a target, some headers, maybe a body, and a status code coming back.

Once you can read that anatomy, the web stops being a black box. DevTools becomes a window, APIs become ordinary conversations, and your ML model becomes just another server that answers when someone asks in the right language.

---

## ✅ Final Takeaway

> **"HTTP is not the road, the address, or the delivery truck. It is the language on the letter, the agreement that gives every request and every response its meaning."**
