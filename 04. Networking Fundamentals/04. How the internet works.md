## 🙋 Someone Asks, Someone Answers: Client-Server Architecture

> 💭 *"What is a client? And what is a server?"*

A **client** is a device or software application that **requests** a service or resource from another system.

* 🌐 Google Chrome requesting a webpage
* 📱 A mobile app requesting weather information
* 🐍 A Python program requesting data from an API
* 🎮 A game requesting information from an online game server

A **server** is a system or application that **provides** services or resources to clients.

* 🖥️ A web server providing webpages
* 🗄️ A database server providing stored information
* 🔌 An API server providing data to applications
* 🎯 A game server coordinating online gameplay

Think of the client as *the one asking*, and the server as *the one answering*.

Picture the ML application you will eventually build: a model that predicts whether a message is spam. You deploy it behind an API. A user submits a message, your application processes it, and a prediction comes back.

* Your browser or frontend is the **client**.
* Your API application is the **server**.
* Your ML model does the **prediction**.

> 💭 *"Does a server have to be some giant computer in a data center?"*

No. A server can be software running on an ordinary laptop. ***What matters is the role being performed, not the size of the machine.***

### 🛤️ The Simplest Journey: Visiting Google

> 💭 *"How does client-server communication actually work?"*

Here is the simplified version of what happens when you visit Google:

1. **You enter a website address.** You type `google.com` and press Enter.
2. **Your browser initiates communication.** It works out how to reach the website and sets up the network connections it needs.
3. **Your browser sends a request** for the webpage or another resource.
4. **The server processes the request** and decides how to respond.
5. **The server sends a response.** It might be HTML, JSON, an image, or another resource.
6. **Your browser displays the result.** It processes what it received and renders the page.

```text
  CLIENT (your browser)                         SERVER (Google)
         |                                             |
         |  ---- "Give me the page for /" ---------->  |
         |                                             |  (processes the request)
         |  <---- "Here's the HTML, CSS, JS..." -----  |
         |                                             |
   (renders the page)
```

One detail is easy to miss. Loading a modern website is rarely one request. The browser may ask for HTML, JavaScript, CSS, images, fonts and data **separately**. Hold on to that thought, because in a moment you'll *see* it with your own eyes.

### 🧪 Your Own Server, Right Now

Suppose you write this FastAPI endpoint:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/hello")
def hello():
    return {"message": "Hello, Dharan!"}
```

You run it locally and visit `http://127.0.0.1:8000/hello`. Here is who plays which role:

| Component                       | Role                |
| ------------------------------- | ------------------- |
| Your browser                    | Client              |
| FastAPI application             | Server              |
| `/hello`                        | Requested endpoint  |
| Python function                 | Handles the request |
| `{"message": "Hello, Dharan!"}` | Response data       |

Notice something that surprises many beginners: ***you can run both the client and the server on the same computer.*** That leads to a very practical idea.

### 🏠 The Address That Means "Me"

> 💭 *"What is localhost?"*

`localhost` refers to **your own computer**. The IPv4 loopback address commonly used for it is:

```text
127.0.0.1
```

When you run FastAPI on your laptop and open `http://127.0.0.1:8000`, your browser is the client and your FastAPI process is the server, both on one machine. This is how you develop APIs, websites, database applications, ML services and backend systems.

⚠️ **Important distinction:** `localhost` does *not* mean your app is publicly accessible on the internet. It normally refers to your own machine. If a service is bound only to `127.0.0.1`, other devices on your Wi-Fi generally cannot reach it through your laptop's LAN address.

🐳 **Why this matters for Docker:** your ML app inside a container might listen on port `8000`. Docker can *publish* that port so you can reach it from your host machine. It is the same client-server story, with container networking added on top.

## 🔍 Watching the Conversation: Browser Developer Tools

> 💭 *"I keep saying 'the browser sends requests.' Can I actually watch it happen?"*

Yes, and it is one of the most useful skills you can pick up. It lets you **observe** real network communication instead of trusting that it works.

1. Open a website in Chrome.
2. Press `F12`.
3. Select the **Network** tab.
4. Reload the page.
5. Inspect the requests that appear.

Each row has columns: Request Method, Status Code, Domain, Initiator, Type, Transferred, Size and Time. Let's decode them one at a time.

### 📮 Request Method: *What do you want me to do?*

The request method describes the operation the client wants performed. Two common ones:

**GET** retrieves a resource.

```http
GET /products HTTP/1.1
Host: example.com
```

A possible response:

```json
{
    "products": [
        "Laptop",
        "Keyboard",
        "Mouse"
    ]
}
```

**POST** submits data for processing, or creates a resource. Imagine your spam classifier receiving a message:

```http
POST /predict HTTP/1.1
Content-Type: application/json
```

With a request body:

```json
{
    "message": "Congratulations! You won a prize."
}
```

The server processes it and might return:

```json
{
    "prediction": "spam"
}
```

That is exactly the client-server shape you'll use when building ML APIs.

> 📌 **Remember:** GET and POST are HTTP **methods**. GET is not a different *protocol* from POST.

### 🚦 Status Code: *How did it go?*

A status code tells you the outcome of an HTTP request.

| Status code                 | Meaning                              | Example                                      |
| --------------------------- | ------------------------------------ | -------------------------------------------- |
| `200 OK`                    | Request succeeded                    | Webpage retrieved successfully               |
| `201 Created`               | Resource created                     | New record created through an API            |
| `301 Moved Permanently`     | Resource has permanently moved       | Website redirects to another URL             |
| `400 Bad Request`           | Request is invalid                   | Incorrect request data                       |
| `401 Unauthorized`          | Authentication is required or failed | Missing or invalid login credentials         |
| `403 Forbidden`             | Access is refused                    | User lacks permission                        |
| `404 Not Found`             | Resource not found                   | Incorrect API endpoint                       |
| `500 Internal Server Error` | Server encountered an error          | Unexpected backend failure                   |
| `503 Service Unavailable`   | Service is unavailable               | Server temporarily unable to handle requests |

The lesson highlights `200`, which generally means the request succeeded.

> ⚠️ *A status code describes the **HTTP-level** result, not the quality of your ML.* A `200 OK` doesn't mean your model predicted correctly. It means the HTTP request succeeded according to the server. Your application can happily return a wrong prediction with status `200`. **Computers are excellent at completing the wrong task successfully.**

### 🏷️ Domain: *Who am I talking to?*

The domain is the human-readable name that identifies a website: `google.com`, `github.com`, `openai.com`. A domain name is **not** itself the server's IP address. The **Domain Name System (DNS)** helps resolve names to IP addresses. We'll meet it properly soon.

### 🎯 Initiator: *Who caused this request?*

The initiator shows what triggered a particular request. For example:

* The browser's HTML parser discovered an image
* A JavaScript file requested some data
* A stylesheet referenced a font
* A script started an API request

This is how you finally understand why one page load makes dozens of requests.

### 🗂️ Type: *What kind of thing is this?*

| Type         | Purpose                                 |
| ------------ | --------------------------------------- |
| `document`   | HTML document                           |
| `script`     | JavaScript file                         |
| `stylesheet` | CSS stylesheet                          |
| `image`      | Image resource                          |
| `fetch`      | Resource requested using the Fetch API  |
| `xhr`        | Resource requested using XMLHttpRequest |
| `font`       | Font resource                           |

### 📦 Transferred vs. Size: *Two different numbers*

* **Transferred** is the amount of data moved over the network for that resource.
* **Size** is the resource's size as reported by the browser, often its decoded or uncompressed size.

Compression, caching and browser implementation affect both. An HTML file might be 100 KB uncompressed but need much less data on the wire when compressed.

### ⏱️ Time: *How long did it take?*

Time is how long the request took, by the browser's own timing. It can be affected by network latency, server processing time, data transfer speed, connection establishment, caching and browser scheduling.

> 💭 *"Why should I learn this?"*

Suppose your deployed FastAPI app takes five seconds to return an ML prediction. The Network panel helps you investigate whether the delay comes from the request, the connection, the server's response or the data transfer. **A slow request doesn't automatically mean a slow server.** The network or something else may be responsible. This is one of the first tools to reach for when debugging a web application.

## 📜 The Rules of the Road: Protocols

> 💭 *"Two computers want to talk. What stops it from becoming a mess?"*

Imagine one computer sends data in a format the other doesn't understand. They disagree about how to start a connection, how to name the destination, or how to read the message. Communication collapses.

A **protocol** is a defined set of rules governing communication between systems. It specifies things like:

* Message formats
* Communication procedures
* Addressing
* Error handling
* Data delivery behavior

The lesson introduces three protocols that appear everywhere: **TCP, UDP and HTTP**.

### 📬 TCP: The Careful Courier

**TCP (Transmission Control Protocol)** provides **reliable, ordered delivery of a byte stream** between applications communicating over a network. Its responsibilities include:

* Establishing a connection
* Keeping track of transmitted data
* Detecting missing data
* Retransmitting data when necessary
* Delivering received data in order

🧠 **Analogy:** you're sending a 100-page document to someone. You want every page to arrive, in the right order. TCP provides the mechanisms that make that reliable delivery possible. If part of the data is lost along the way, TCP can retransmit the missing portion, so the receiving application gets the complete byte stream in order, *assuming the connection succeeds*.

⚠️ Two honest limits:

* TCP doesn't guarantee every connection will succeed. Network failures can still prevent delivery.
* TCP doesn't guarantee the destination application will *process* the information successfully. It gives **transport-level reliability, not application-level success.**

TCP is commonly used by HTTPS connections, SSH, many database connections, and anything that needs reliable, ordered delivery.

### 📡 UDP: The Speedy Announcer

**UDP (User Datagram Protocol)** is a **connectionless** transport protocol. It sends individual datagrams without TCP-style guarantees of reliable delivery or ordered arrival. A datagram might be lost, duplicated or arrive out of order, and UDP doesn't automatically retransmit.

> 💭 *"Why would anyone use something that can lose data?"*

Because some applications care more about **timely** information than about recovering every missing piece. Think of a live video call. If a tiny piece of video is lost, waiting for it to be retransmitted could delay everything after it. Depending on the application, carrying on with the latest information may be better.

UDP can be useful for:

* 🎙️ Real-time voice communication
* 📺 Live media
* 🎮 Online games
* 🔎 DNS queries
* Certain transport protocols and network services

⚠️ UDP does **not** inherently make an application faster. Actual performance depends on the application, network conditions and protocol design. Some applications even build their own reliability mechanisms on top of UDP.

### ⚖️ TCP vs. UDP, Side by Side

| Feature                        | TCP                              | UDP                          |
| ------------------------------ | -------------------------------- | ---------------------------- |
| Connection model               | Connection-oriented              | Connectionless               |
| Built-in reliable delivery     | Yes                              | No                           |
| Built-in ordered delivery      | Yes                              | No                           |
| Retransmission of missing data | Supported                        | Not provided automatically   |
| Data representation            | Ordered byte stream              | Individual datagrams         |
| Common uses                    | HTTPS, SSH, database connections | DNS, real-time media, gaming |

***TCP provides reliable, ordered byte-stream delivery. UDP provides datagram delivery without built-in guarantees of reliability or ordering. Neither is universally better. The right choice depends on what the application needs.***

### 🧾 HTTP: The Language of the Web

**HTTP (Hypertext Transfer Protocol)** is an **application-layer** protocol for communication between web clients and servers. It defines how requests and responses are structured, and how methods and status codes are interpreted.

A simplified request:

```http
GET /products HTTP/1.1
Host: example.com
Accept: application/json
```

A simplified response:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
    "product": "Laptop"
}
```

Reading the request:

| Component   | Meaning                           |
| ----------- | --------------------------------- |
| `GET`       | HTTP method                       |
| `/products` | Requested path                    |
| `HTTP/1.1`  | HTTP version                      |
| `Host`      | Host name being requested         |
| `Accept`    | Media types the client can accept |

Reading the response:

| Component      | Meaning                       |
| -------------- | ----------------------------- |
| `HTTP/1.1`     | HTTP version                  |
| `200 OK`       | Status code and reason phrase |
| `Content-Type` | Type of content returned      |
| JSON body      | Actual response data          |

HTTP isn't limited to HTML. It can also carry JSON, images, documents, video data and other representations of resources. **That is exactly why HTTP is fundamental to APIs.**

### 🔒 HTTP vs. HTTPS

**HTTPS is HTTP protected by TLS**, which provides encryption and authentication properties for the connection. With a properly configured HTTPS service, TLS helps protect communication against eavesdropping and tampering.

```text
http://example.com     →  HTTP without TLS protection
https://example.com    →  HTTP over TLS
```

Modern websites and APIs commonly use HTTPS.

### 🧅 How Do TCP and HTTP Work Together?

Consider an HTTPS request using HTTP/1.1 or HTTP/2 over TCP. A simplified view:

```text
Your browser
     |
     | HTTP request
     v
TLS protection
     |
     | TCP connection
     v
IP network
     |
     v
Web server
```

⚠️ The actual layering depends on the HTTP version. **HTTP/3 uses QUIC, which operates over UDP rather than TCP.** So don't memorize the simplistic idea that all HTTP traffic must use TCP.

The essential split of jobs:

* **HTTP:** defines application-level web communication
* **TCP:** provides reliable transport, for protocols that use it
* **IP:** handles addressing and packet forwarding between networks

Now to the part that connects everything: how does the data physically get there?

## 🧩 Breaking the World Into Pieces: Bits and Packets

> 💭 *"How is data actually transferred across the internet?"*

At the lowest level, computers represent information using binary values, `0` and `1`. A single binary digit is a **bit**, and eight bits form one **byte**.

```text
01001000
```

That's eight bits. Interpreted as ASCII, it represents the character `H`. Images, videos, documents, programs and network messages are all, ultimately, binary data.

Now the practical problem. Suppose you want to download a 1 GB file. Sending and handling it as one giant unit would be impractical. So network protocols **divide data into smaller units** and use mechanisms to transmit and reconstruct it. The details depend on the protocol.

> 💭 *"What is a packet?"*

A **network packet** is a unit of data carried by a network-layer protocol such as IP. Data may be divided into smaller units, with headers added to carry what delivery needs. An IP packet generally contains:

* An **IP header** (including the source and destination IP addresses)
* A **payload** carrying data from a higher layer

```text
+----------------------------------+
| IP Header                        |
| Source IP                        |
| Destination IP                   |
+----------------------------------+
| Payload                          |
| Data carried by the packet       |
+----------------------------------+
```

⚠️ **Packets are not always application messages.** One application request can involve multiple transport segments or packets, and one application message doesn't necessarily map to exactly one IP packet. A large HTTP response might be carried across many packets, and the receiving system reassembles or processes the data according to the relevant protocols.

> 💭 *"Why use packets at all?"*

Packet-based communication lets many devices **share** network infrastructure. Routers forward packets toward their destinations, and different packets can take different network paths. Packets also help with:

* Handling large transfers
* Sharing network capacity
* Detecting certain transmission errors
* Recovering from loss, at protocols that support retransmission

***Think of packets as individual pieces of a larger communication, not necessarily complete application messages.***

## 📇 Every Traveler Needs an Address: IP Addresses

An **IP address** identifies a **network interface** within the addressing system of the Internet Protocol. It helps networks decide where packets should be delivered.

The lesson notes compare IP addresses to phone numbers saved under contact names. Humans prefer names. Systems need numbers. The comparison explains why both exist.

### 4️⃣ IPv4

IPv4 addresses are **32 bits** long, written as four decimal numbers separated by dots:

```text
192 . 168 . 1 . 10
  |     |   |   |
  8     8   8   8 bits
```

Each number is eight bits, so it ranges from `0` to `255`. In total:

$$
8+8+8+8=32
$$

That allows:

$$
2^{32}=4{,}294{,}967{,}296
$$

possible IPv4 address values. Not all of them are available for ordinary public host assignment. Some are reserved for special purposes, and allocation rules govern how addresses are used.

### 6️⃣ IPv6

IPv6 uses **128-bit** addresses, such as:

```text
2001:db8::1
```

IPv6 was developed partly to address the limits of IPv4's address space. With 128 bits, the number of possible addresses is:

$$
2^{128}
$$

An enormous address space. IPv4 and IPv6 **coexist** across the internet, and a device or service may support one or both.

## 📖 The Internet's Phone Book: DNS

> 💭 *"How does `google.com` become an IP address?"*

Humans prefer memorable names. Computers need network addresses. The system that bridges the gap is **DNS, the Domain Name System**: a distributed naming system that lets applications discover information associated with domain names.

```text
You enter:
google.com
     |
     v
Your computer needs address information
     |
     v
DNS resolution
     |
     v
One or more IP addresses are returned
     |
     v
Your browser can attempt to connect
```

The exact process may involve browser caches, operating-system caches, a configured DNS resolver and authoritative DNS servers. DNS doesn't necessarily contact an authoritative server every time. **Cached answers may be reused** according to their time-to-live settings.

A domain name also doesn't necessarily correspond to **one fixed IP address**. A website may use:

* Multiple IP addresses
* Load balancers
* Content delivery networks
* Different answers depending on location or network conditions

⚠️ **DNS resolution and establishing a connection are separate operations.** DNS discovers address information. After that, the client must still establish communication with the destination. For HTTPS, the browser may set up a TCP connection followed by TLS negotiation, or use a different transport setup such as QUIC for HTTP/3. DNS is the address-discovery step, **not the entire process** of loading a website.

## 🏘️ Four Devices, One Wi-Fi: Public vs. Private IPs

Suppose your home has four devices: a laptop, a phone, a television and a tablet, all connected to the same Wi-Fi router.

> 💭 *"Do they all have the same IP address?"*

Here is the precise answer:

> **They typically have different *private* IP addresses on the home network, while sharing one *public* IPv4 address for many internet communications when the router uses NAT.**

Let's see why.

### 🌍 Public IP Address

A public IP address is used for communication across the public internet. Your internet connection may use a public IPv4 address assigned by your internet service provider. Imagine your router has:

```text
203.0.113.10
```

(An illustrative address from a range reserved for documentation, not a real one to use.) When your laptop accesses an internet service, the destination may see this public address as the source of the connection, after network address translation.

⚠️ **An exception worth knowing:** some ISPs use **carrier-grade NAT**. The address visible to an external service may then belong to an upstream, provider-operated NAT device rather than directly to your home router.

### 🏠 Private IP Address

Private IPv4 addresses are used within private networks. Three commonly used ranges:

| Range                              | Common use       |
| ---------------------------------- | ---------------- |
| `10.0.0.0` to `10.255.255.255`     | Private networks |
| `172.16.0.0` to `172.31.255.255`   | Private networks |
| `192.168.0.0` to `192.168.255.255` | Private networks |

Your home network might look like this (illustrative, not your real configuration):

| Device                 | Private IP address |
| ---------------------- | ------------------ |
| Laptop                 | `192.168.1.10`     |
| Phone                  | `192.168.1.11`     |
| Television             | `192.168.1.12`     |
| Tablet                 | `192.168.1.13`     |
| Router's LAN interface | `192.168.1.1`      |

Each device has a different private address while sharing one internet connection. Private addresses are **not globally unique** and are **not ordinarily routed across the public internet**.

```text
Laptop:  192.168.1.10 ----\
Phone:   192.168.1.11 -----\
TV:      192.168.1.12 ------> Wi-Fi Router
Tablet:  192.168.1.13 -----/       |
                                   |
                             NAT / Routing
                                   |
                                   v
                               Internet
```

Devices use private addresses inside the local network. The router forwards traffic toward external networks, and NAT may translate the addresses and transport-layer ports used by those connections. Two mechanisms make this whole picture work. The first answers *"where did each device get its address?"*

## 🎟️ Who Hands Out the Addresses? DHCP

> 💭 *"How do devices get their IP addresses?"*

The lesson introduces **DHCP (Dynamic Host Configuration Protocol)** as the mechanism through which a router assigns local IP addresses. It lets a device obtain network configuration **automatically**. Without it, you'd configure network settings by hand.

A DHCP server can provide:

* An IP address
* A subnet mask
* A default gateway
* DNS server addresses
* A lease duration

You connect your laptop to your home Wi-Fi. If your router provides DHCP service, the laptop can obtain something like:

```text
IP address:      192.168.1.10
Subnet mask:     255.255.255.0
Default gateway: 192.168.1.1
DNS server:      192.168.1.1
```

(Example values. Your real configuration may differ.) The **default gateway** is typically the router's local address and provides a next hop for traffic that needs to leave the local network.

### 🎭 DORA: The Four-Message Handshake

In a typical IPv4 DHCP exchange, four messages are commonly described as **DORA**:

1. **D**iscover: the client searches for DHCP servers.
2. **O**ffer: a DHCP server offers configuration.
3. **R**equest: the client requests the offered configuration.
4. **A**cknowledgment: the server confirms the assignment.

Details can vary with network state and DHCP configuration.

### 🆚 DHCP vs. DNS

Two protocols, two completely different jobs:

| Protocol | Main purpose                                         |
| -------- | ---------------------------------------------------- |
| DHCP     | Obtains network configuration                        |
| DNS      | Resolves domain names and provides other DNS records |

* DHCP helps your laptop get its local IP address and DNS server configuration.
* DNS helps your browser discover address information for `google.com`.

They complement each other. They are not interchangeable.

## 🔄 One Public Address, Many Devices: NAT

> 💭 *"If my laptop and phone both have private addresses, how does a website's reply find the right one?"*

**NAT (Network Address Translation)** modifies address information in network packets as they pass through a translating device. The lesson refers to it when explaining how the router decides which device should receive returning data. (The standard expansion is *Network Address Translation*, not "Network Access Translator.") A common home setup uses source NAT, often **with port translation**, so many private devices can communicate through one public IPv4 address.

Let's follow one connection.

### 📤 Going Out

Your laptop has the private IP `192.168.1.10`. Your router has the illustrative public IP `203.0.113.10`. You open Chrome and visit a website. Before NAT, the connection might look like this:

```text
Source IP:        192.168.1.10
Source port:      51514
Destination IP:   198.51.100.20
Destination port: 443
```

(Again, documentation-range addresses. Port `443` is commonly used for HTTPS.) The router may translate the source address and source port into a public-side mapping:

```text
Source IP:        203.0.113.10
Source port:      62001
Destination IP:   198.51.100.20
Destination port: 443
```

(The translated port is an example.) The router **remembers the mapping** so returning traffic can be matched to the right internal connection.

### 📥 Coming Back

The external server replies to the public address and port tied to the connection. The router checks its NAT mapping, translates the destination back to the laptop's private address and port, and the laptop receives the reply.

```text
LAPTOP
192.168.1.10:51514
        |
        | Outgoing connection
        v
ROUTER WITH NAT
        |
        | Translated connection
        v
203.0.113.10:62001
        |
        v
EXTERNAL SERVER
198.51.100.20:443
        |
        | Response
        v
ROUTER LOOKS UP NAT MAPPING
        |
        v
LAPTOP
192.168.1.10:51514
```

### 🔢 Why Does NAT Need Port Translation?

> 💭 *"What if my laptop and my phone both visit the same website?"*

Your laptop might initiate from `192.168.1.10:51514`. Your phone might initiate from `192.168.1.11:51514`. Both can use the **same source port number**, because they have different private IP addresses. When translating, the router assigns **distinct public-side mappings**:

```text
Laptop connection:  203.0.113.10:62001
Phone connection:   203.0.113.10:62002
```

The router tracks both and uses them to steer each reply to the right internal connection. That is why NAT with port translation works so well for home networks.

> ⚠️ **One critical correction:** NAT does **not** automatically make your home network secure. A typical home router's stateful firewall often restricts unsolicited incoming traffic, but **NAT and firewall filtering are distinct functions.** A network can use NAT without having every security property you might expect from a properly configured firewall.

## 🚪 Which Door Inside the House? IP Address vs. Port

The lesson explains that IP addresses identify the destination device, while port numbers help direct traffic to the right application or transport endpoint. Let's make that precise.

> 💭 *"What is a port?"*

A transport-layer **port number** helps identify the communication endpoint associated with an application. TCP and UDP each use **16-bit** port numbers, so each has port numbers from:

$$
0 \text{ to } 2^{16}-1
$$

And since:

$$
2^{16}=65{,}536
$$

each protocol's port space holds 65,536 numbers, in the range `0–65535`. TCP port `8000` and UDP port `8000` are **distinct** transport endpoints. They don't automatically refer to the same service.

> 💭 *"Why do we need ports if we already have IP addresses?"*

Imagine your laptop is running Chrome, a FastAPI application, a database client and an online game. They may all share the same network interface and IP address. The IP address alone can't say which endpoint should receive a connection. **Ports distinguish them.**

| Application or service             | Example port |
| ---------------------------------- | -----------: |
| HTTP                               |           80 |
| HTTPS                              |          443 |
| SSH                                |           22 |
| PostgreSQL                         |         5432 |
| MySQL                              |         3306 |
| Typical FastAPI development server |         8000 |

These are common **defaults, not requirements**. Applications can use other ports.

🏢 **Mental model:** the IP address identifies the network destination, like a building. The port identifies a transport endpoint on it, like one specific door.

```text
192.168.1.10:8000
      |        |
      |        └── Port: 8000
      └─────────── IP address: 192.168.1.10
```

If your FastAPI server listens on port `8000`, a client on a network that can reach your laptop may connect to `http://192.168.1.10:8000`, **provided that**:

* The server is listening on the relevant network interface
* The devices have appropriate network connectivity
* Firewall rules permit the connection
* The address and port are correct

And remember: if the server listens only on `127.0.0.1`, another device generally cannot reach it through `192.168.1.10`.

### 🔬 A Technical Detail That Trips People Up

A complete communication endpoint depends on the **transport protocol** as well as the address and port:

```text
TCP: 192.168.1.10:8000
UDP: 192.168.1.10:8000
```

These are different transport endpoints. And a connection is **not identified solely by its destination port**. TCP connections are distinguished using the source and destination IP addresses, the source and destination ports, and the transport protocol.

## 🧵 Pulling Every Thread Together: You Ask an AI a Question

> 💭 *"So what actually happens when I open a browser, enter an address and submit a question to an online AI service?"*

Time to connect everything. The exact implementation varies by service, and the specific internal infrastructure behind any particular service can't be confirmed from this lesson. What follows is the high-level, protocol-level story.

**1️⃣ You enter a URL.** The browser identifies the scheme (`https`), the host (`example.com`) and the path (`/`) in something like `https://example.com/`.

**2️⃣ DNS resolution.** The browser or operating system may need an IP address for the hostname. Resolution may use cached information or a DNS resolver, and the result tells the browser where to attempt a connection.

**3️⃣ Connection establishment.** For HTTPS over HTTP/1.1 or HTTP/2, the client establishes a TCP connection and negotiates TLS. For HTTP/3, it uses QUIC over UDP instead. The details depend on what the client and server support.

**4️⃣ Your browser sends a request.** Depending on the service, it may include a requested path, HTTP headers, authentication information, and a request body containing your submitted data.

**5️⃣ Data travels through networks.** The system divides and encapsulates data according to the relevant protocols. IP packets are forwarded toward the destination, routers examine packet headers and forward traffic according to their routing information, and your home router may translate private address and port information through NAT.

**6️⃣ The server receives the request.** Networking and application software process the connection and the HTTP request. For an AI service, generating the response could involve application logic and model inference, though the specifics depend on the service.

**7️⃣ The server sends a response.** An HTTP response carrying JSON, HTML or other content travels back through the network.

**8️⃣ Your browser processes the response.** For a conventional webpage it renders HTML and may request more resources. For a web application it may process JSON and update the interface. For a chat application, the interface displays the returned answer.

### 🐳 What Changes With Docker?

Your application might listen on port `8000` inside a container. Docker can publish that port to the host machine:

```bash
docker run -p 8000:8000 your-image
```

This requests publication of host port `8000` to container port `8000`. Whether it's actually reachable still depends on the host binding, firewall rules and network configuration. This is the `127.0.0.1` / port / firewall checklist from earlier, wearing a Docker costume.

### ☁️ What Changes in the Cloud?

Your application may run on a virtual machine, a container platform or a managed service. Users might reach it through a public endpoint or a load balancer. DNS can map a domain to the relevant service address, and HTTPS protects the connection. Cloud networking adds new vocabulary:

* Virtual private clouds and virtual networks
* Subnets
* Route tables
* Security groups and network access controls
* Load balancers
* Public and private endpoints

You don't need to master those yet. The fundamentals you just learned are the foundation they're built on.

## 🛠️ Sanity Check: Where Simple Pictures Lie

The introductory pictures are useful, but real networks are more flexible than the diagrams. Here are the statements that most need precise reading:

| Common statement                                               | Correct understanding                                                                                                                                                                                  |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Every device has an IP address                                 | Network interfaces use IP addresses when communicating through IP, but a device can have multiple interfaces and addresses, and some interfaces may not have an assigned address.                      |
| Every internet device has a public IP                          | Not necessarily. Devices often use private addresses behind NAT, and IPv6 connectivity has different addressing possibilities.                                                                         |
| All devices on the same Wi-Fi have the same IP                 | They commonly share a public IPv4 address for outbound traffic through NAT, but use different private addresses on the LAN.                                                                            |
| The router assigns IP addresses                                | A DHCP server often supplies configuration. The router commonly provides DHCP service on a home network, but the DHCP server can be elsewhere.                                                         |
| HTTP always uses TCP                                           | Not always. HTTP/3 uses QUIC over UDP.                                                                                                                                                                 |
| UDP is always faster than TCP                                  | Not guaranteed. Performance depends on the application and network conditions.                                                                                                                         |
| One request equals one packet                                  | No. One request can span multiple packets, and a packet need not contain a complete request.                                                                                                           |
| A port identifies a particular application                     | More precisely, a transport-layer port helps identify a transport endpoint. Multiple applications can use the same port number under different conditions, and one application may use multiple ports. |
| NAT and firewalls are the same thing                           | No. NAT translates addresses; firewalls enforce traffic policies. A router may perform both functions.                                                                                                 |
| An IP address always identifies one specific physical computer | No. Addresses are associated with network interfaces and may change, be shared through translation, or belong to virtualized infrastructure.                                                           |

## 📋 The 80/20 Revision Sheet

If you keep only twelve ideas from this chapter, keep these:

1. **Client-server architecture:** a client requests a service or resource; a server provides it.
2. **Request and response:** the client sends a request, the server returns a response.
3. **HTTP:** an application-layer protocol defining web requests, responses, methods, headers and status codes.
4. **TCP vs. UDP:** TCP gives reliable, ordered byte-stream delivery; UDP sends datagrams without built-in reliability or ordering.
5. **IP addresses:** identify network interfaces for communication and support packet delivery across networks.
6. **DNS:** translates domain names into address information and provides other records associated with names.
7. **Packets:** carry data through IP networks. One application request may involve multiple packets.
8. **Public vs. private IP:** private IPv4 addresses live inside private networks; public IPv4 addresses are used across the public internet.
9. **DHCP:** automatically provides network configuration, including IP addresses and other settings.
10. **NAT:** translates network address information. Home routers commonly use NAT with port translation so many internal devices can communicate through one public IPv4 address.
11. **Ports:** port numbers help identify transport endpoints associated with network applications.
12. **Localhost:** `127.0.0.1` is the IPv4 loopback address commonly used to reach your own computer.

## 🌀 Deepest Realization

Look back at everything you just learned and notice what *isn't* there: a single clever, all-knowing mechanism. Nothing in this chapter does everything. **Each piece answers exactly one question.**

* **Client-server architecture:** *Who requests, and who provides?*
* **DNS:** *How do we discover the destination's address?*
* **IP:** *How is traffic addressed and forwarded between networks?*
* **TCP or UDP:** *How is data transported?*
* **Ports:** *Which transport endpoint should receive the data?*
* **HTTP:** *What request is being made, and what response is returned?*
* **NAT:** *How can address information be translated between networks?*
* **DHCP:** *How does a device obtain its network configuration?*

And so the sequence you can now recite in your sleep is:

**Client → DNS → Connection → HTTP Request → IP Packets → Server → HTTP Response → Client**

Once these concepts fit together, networking stops looking like a pile of unrelated acronyms. It becomes a system in which every protocol has one specific responsibility. And because each layer only has to be good at its own job, the whole thing scales from your laptop's `127.0.0.1` to the entire planet.
